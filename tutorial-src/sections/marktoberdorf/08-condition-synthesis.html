CoSyn: Condition Synthesis and its Realizability via Constrained Horn Clauses

Lecture by Orna Grumberg (Technion). Deck: Constrained Horn Clauses and their Applications, lecture 4. The work presented is by Bat-chen Rothenberg, Orna Grumberg, Yakir Vizel and Eytan Singher, published at NFM 2023.

The previous two sections used constrained Horn clauses for verification. You hand the encoder a complete program and a specification, and a satisfying interpretation of the clause set is an inductive invariant. This lecture keeps the machinery and changes the question. Here the program is incomplete: the conditions of its if and while statements are missing, and the task is to fill them so that the assertions hold. The system is called CoSyn. The idea that makes the problem fit into CHC is a change of subject. Instead of asking directly whether a good set of conditions exists, which is a question about the existence of a function, CoSyn asks whether a hopeless initial state exists, which is a question about the existence of a state. The second question is a plain CHC satisfiability query, and the theorem is that the two questions have opposite answers.

The condition synthesis problem slide 3

The input is a partial program: a program in which the conditions of conditional branches, that is, of if and while statements, are missing and are written as holes. Alongside it comes a specification, given in the deck's setting as assertions placed in the code. A solution is a set of conditions, one per hole, such that the program obtained by filling the holes meets the specification.

The motivation the deck names is automated program repair. A repair tool often knows, or can guess, which branch condition is wrong, and the interesting part of the job is then not finding where the fault is but working out what the condition should have been. Note also what is not being synthesised. The control structure is fixed, the assignments are fixed, the assertions are fixed. Only the branch conditions are unknown, and that restriction is what buys the clean theory that follows.

Invariant existence against choice existence

It is worth being precise about how this differs from what came before, because the clause sets look superficially alike.

In verification the unknowns are the predicates themselves. The encoder gives one uninterpreted predicate per location, meaning "this state is reachable here", and the solver is asked whether there is an interpretation, that is, a formula per predicate, that makes every clause valid. Satisfiability of the set is the existence of an inductive invariant.

In synthesis the unknown is of a different type. What we want is a choice function: for each hole, a predicate over the program state that decides, at that point, which way control goes. Stated naively this is a quantifier alternation, "there exist conditions such that for all inputs the assertions hold", and quantifier alternation is exactly what Horn clauses cannot express, since a CHC system is one big implicitly universally quantified conjunction whose only existential is the outer "is there an interpretation".

Key idea CoSyn dodges the alternation by negating the question. Rather than searching for a choice function that always succeeds, it searches for a single state that defeats every choice function. Searching for a state is an ordinary reachability-style question, and reachability-style questions are what CHC solvers do.

Doomed initial states, and the realizability theorem slide 4

Definition An initial state is doomed if it eventually reaches an error state along every run of the program. More generally, a state is doomed at location ℓ if along every path from ℓ to the assertion, the assertion fails.

The force of the definition is in the word "every". Conditions in a partial program control which run the program takes, so filling a hole is a way of steering a state onto one path rather than another. For a doomed state σ there is nothing to steer towards: whichever path the conditions push σ down, it ends in failure. No assignment of conditions to holes can save it.

That observation is also a completeness argument in the other direction, and the deck states the resulting characterisation as one line:

The problem is unrealizable  iff  there exists a doomed initial state.

One half is the paragraph above: a doomed initial state means no solution. The other half says that if no initial state is doomed, then at every reachable point at least one successor avoids failure, and choosing those successors is precisely what a set of conditions can do. The problem of finding conditions has been converted into the problem of deciding a property of the state space.

What CoSyn hands back in each case slide 5

Before the mechanism, the interface. CoSyn takes a condition synthesis problem and returns one of two verdicts, and in both cases the verdict comes with evidence that can be checked independently of the tool.

VerdictEvidence returnedWhat you can do with it
Unrealizablea doomed initial stateRun the program from that state and watch it fail on every branch choice. The verdict is checkable and it is final: no condition in any language repairs this program.
Realizablea range of conditions for each holeNot one solution but the whole space of them, described by two bounds per hole. Any condition inside the range is a correct fill.

The second row is the more unusual one, and it is what later lets CoSyn cooperate with a syntax-directed synthesiser. Returning a range rather than a witness is possible because the doomed sets computed by the reduction carry more information than a yes or no answer.

The reduction to CHC slides 6-7

To decide whether a doomed initial state exists, CoSyn reduces the question to CHC satisfiability. The reduction runs backwards. Where the verification encoding of the earlier sections starts at the entry with the precondition and pushes reachability forwards along the edges, this one starts at the negation of the assertion and pushes doomedness backwards along the edges. The predicates therefore mean something different: Dℓ(v) is read as "the state v at location ℓ is doomed", not "is reachable".

Build the control flow graph of the partial program, including the error location that the failing assertion leads to. Introduce one uninterpreted predicate Dℓ per location, with the program variables as arguments. As always in CHC encoding, the predicates are the unknowns and the solver's job is to interpret them.

Add the fact true → Derr(v). Every state at the error location is already a failure, so every state there is doomed. This is the only clause with an empty body, and it is where the backward computation starts.

For an edge from ℓ to ℓ′ whose transition relation is ρ(v, v′), add Dℓ′(v′) ∧ ρ(v, v′) → Dℓ(v). If the state you land in is doomed and the edge is the only way out, the state you started from is doomed too. An assignment res := x contributes the constraint res′ = x.

An edge into the error location carries the negation of the assertion as its guard. In the example below the assertion is res ≥ 0, so the edge into the error location is guarded by res < 0, and that guard sits in the body next to Derr. Where the guard fails there is simply no clause, which is correct: those states terminate safely and are not doomed.

This is the step that encodes the synthesis. At a location whose two outgoing edges are governed by a hole, both successors go into the body of a single clause: Dℓ2(v) ∧ Dℓ3(v) → Dℓ1(v). The state is doomed at ℓ1 only if it is doomed whichever way the eventual condition sends it. Since the head still holds a single predicate application, the clause is Horn.

Add Di(v) → false, where ℓi is the entry location, restricted to the initial states. This is the only clause whose head is not a predicate application. It asserts exactly the property we want: no initial state is doomed.

SAT means the clause set has a model in which the entry predicate is empty, so no initial state is doomed and the problem is realizable. The model also gives, for each location, a formula describing the doomed states there, and those formulas are what the range computation consumes. UNSAT means every candidate interpretation forces some initial state into Di. The refutation exhibits that state, and it is the doomed initial state returned as evidence for unrealizable.

Key idea Look at the asymmetry between step 3 and step 5. In the forward verification encoding, a location with two incoming edges produces two clauses with the same head, which is a disjunction: reachable by this edge or by that one. In the backward doomed encoding, a hole produces one clause with two predicates in the body, which is a conjunction: doomed down this branch and down that one. The universal quantification over the synthesiser's choice has turned into a conjunction, and conjunction in the body is exactly what the Horn fragment allows for free. That is why the synthesis question fits in CHC at all.

The running example: abs(x) with one hole slides 8-10

The deck carries a single example through the whole reduction. The partial program computes an absolute value, and the branch condition has been removed:

  1. res = 0
  2. if (?)
  3.   res = x
  4. else
  5.   res = -x
  6. assert (res >= 0)

Its control flow graph has six locations. ℓi is the entry, the edge to ℓ1 performs res := 0, and ℓ1 is the hole: the edge labelled ? goes to ℓ2 and the edge labelled ¬? goes to ℓ3. From ℓ2 the assignment res := x leads to ℓ4, from ℓ3 the assignment res := −x leads to the same place, and from ℓ4 an edge guarded by res < 0, the negation of the assertion, leads to ℓerr. Applying the steps above gives the seven clauses on the slide:

D1(x, res′) ∧ res′ = 0  →  Di(x, res)
D3(x, res) ∧ D2(x, res)  →  D1(x, res)
D4(x, res′) ∧ res′ = x  →  D2(x, res)
D4(x, res′) ∧ res′ = −x  →  D3(x, res)
Derr(x, res) ∧ res < 0  →  D4(x, res)
true  →  Derr(x, res)
Di(x, res)  →  false

Six of the seven are mechanical transcriptions of edges. The second is the interesting one, the hole clause, and it is the only place where the two branches meet.

The model the solver returns is worth reading line by line, because each entry is a statement about the program that a person can check.

PredicateInterpretationReading
DerrtrueEvery state at the error location has already failed.
D4res < 0Just before the assertion, a state is doomed exactly when the assertion is about to fail.
D2x < 0Take the ? branch and res becomes x, which is negative exactly when x < 0.
D3x > 0Take the ¬? branch and res becomes −x, which is negative exactly when x > 0.
D1falseNo state is doomed on both branches, since x < 0 and x > 0 cannot hold together.
DifalseNo initial state is doomed, so the query is discharged and the problem is realizable.
What would have to change for this example to come out unrealizable

Strengthen the assertion to res > 0. Then the edge into the error location is guarded by res ≤ 0, so D4 becomes res ≤ 0, D2 becomes x ≤ 0 and D3 becomes x ≥ 0. Their conjunction is x = 0, which is not empty, so D1 and then Di are non-empty and the query fails. The solver reports UNSAT and the refutation names the doomed initial state x = 0. That is the honest answer: abs(0) is zero on either branch, and no branch condition can make it positive.

From one model to a range of conditions per hole slides 11-12

Knowing that the problem is realizable is not yet a repair. The last part of CoSyn turns the doomed sets into the range of legal conditions for each hole, and it does so with local reasoning at the hole.

Fix the hole at ℓ1, with the ? edge going to ℓ2 and the ¬? edge going to ℓ3, and let ψ be the condition to be synthesised, understood throughout as the condition that sends control to ℓ2. The deck states the principle in one sentence: freedom is obtained from states that are not reachable at ℓ1, and from states that are not doomed at either ℓ2 or ℓ3. Writing R1 for the states reachable at ℓ1, that sentence fixes the two bounds:

ψf  =  R1 ∧ D3     (a reachable state doomed on the else branch must be sent to ℓ2)
ψt  =  ¬(R1 ∧ D2)     (a reachable state doomed on the then branch must not be sent to ℓ2)
every ψ with   ψf → ψ → ψt   is a solution

Notice that reachability is a forward property, so R1 is not read off the backward clause set: it comes from the ordinary forward encoding of the earlier sections. The deck does not detail how CoSyn obtains it, but it names non-reachability explicitly as one of the two sources of freedom.

Apply this to abs. At ℓ1 the assignment res := 0 has just run, so R1 is res = 0. With D3 equal to x > 0 and D2 equal to x < 0, the bounds collapse to x > 0 → ψ → x ≥ 0. Both endpoints are legal fills, and so is anything between them. That matches the two versions of abs a programmer would write by hand, and it explains why neither is more correct than the other: on x = 0 the two branches agree, so the condition is free there.

The picture also closes the loop with the theorem. The two bounds are consistent, that is ψf implies ψt, exactly when R1 ∧ D3 ∧ D2 is empty, which is to say when no reachable state is doomed at ℓ1. A reachable doomed state at the hole traces back to a doomed initial state, so the range is non-empty at every hole precisely in the realizable case.

Combining CoSyn with SyGuS slides 13-15

A range of conditions is a semantic object. It says which sets of states are acceptable, not which expressions a programmer would want to read. Syntax-guided synthesis, SyGuS, is the prominent framework for the other half of that: it synthesises a program with respect to a formal specification while restricting the search space to a user-supplied grammar G. CoSyn on its own cannot deliver a solution inside a given grammar, but the deck shows that the two combine, and that each covers the other's weakness.

The combined pipeline runs CoSyn first. If CoSyn answers unrealizable, the pipeline stops there and the answer is definitive. If CoSyn answers realizable, the ranges it produced are passed to the SyGuS solver together with the grammar G, and SyGuS looks for a condition inside G that lies inside the range. It may still fail, but its failure means only that G is too poor, not that the problem has no solution.

Key idea The ranges also decouple the holes. Each hole's range is a self-contained specification for that hole alone, so the synthesis of different holes can be split into different SyGuS queries instead of one joint search over all of them. The deck flags this as the main performance benefit of the combination.

Worth noticing The two "unrealizable" verdicts in this pipeline are not the same statement. CoSyn's unrealizable is grammar independent: a doomed initial state rules out every condition expressible in any language whatsoever. SyGuS's unrealizable is relative to G: no condition in that grammar falls inside the range. The deck's summary of the benefit is exactly this pair, a definite result for the unrealizable cases and more syntactically appealing conditions for the realizable ones.

Beyond safety: existential Horn clauses and CTL* slides 18-24

The last part of the lecture sketches a second non-standard application of Horn clauses, from "CTL* Verification and Synthesis using Existential Constrained Horn Clauses" by Mishel Carelli and Orna Grumberg, ATVA 2024. The setting is infinite-state programs with a first-order CTL* specification, for example AF(a ≤ b) or EG(a = b), and the goals are both verification against such a specification and synthesis of a partial program into a full one that satisfies it.

The deck lists four differences from CoSyn. The specification is a CTL* formula rather than assertions in the code. In the partial programs of this second setting, assertions as well as conditions may be missing. The computation runs forwards rather than backwards. And, most importantly, standard CHCs are not enough.

The reason is a limitation worth remembering. CHCs cannot express liveness or existential properties such as AFp and EGp. Existentially quantified Horn clauses, EHC, are a Horn-like family that adds two things: existential quantification, and well-foundedness, that is, the requirement that no infinite decreasing chain exists. Well-foundedness is what a termination or eventuality argument needs, and existential quantification is what an E path quantifier needs. Both the CTL* verification problem and the CTL* partial synthesis problem are translated into EHC satisfiability, and the deck states that both translations are sound and complete.

Careful The deck is candid that this second application is not implemented, because the EHC solver is no longer active. It points to pfwCSP, by Unno, Terauchi and Koskinen, as a possible substitute for future work, and notes that the authors conjecture pfwCSP and EHC to be inter-reducible. A sound and complete translation is only as useful as the back end it targets.

What the series adds up to slides 16 and 25

The contribution claimed for CoSyn is a novel approach to deciding the realizability of condition synthesis: via the existence of doomed initial states, and via a reduction of that existence question to CHC. It answers with evidence in both directions, a doomed initial state when unrealizable and a range of conditions per hole when realizable, and the range is what lets a SyGuS solver finish the job inside a grammar of the user's choosing. The deck presents these as qualitative claims and does not report benchmark numbers here; the measurements are in the NFM 2023 paper.

Grumberg closes the four lectures by naming the three things they covered. First, a theory-modular approach to solving CHCs that treats CHC solvers as a black box, which was the subject of the previous section. Second, a non-standard use of CHCs for synthesis rather than verification, which is CoSyn. Third, a variation on CHCs, namely EHC, that can express much more than standard CHCs, with the standing caveat that it needs a working solver. Taken together the message is that the clause format is more of a general-purpose interface than it first appears, and that most of the engineering effort now sits on either side of it: in the encoding that produces the clauses, and in the solver that consumes them.
