Constrained Horn Clauses: Turning "Find the Invariant" into a Satisfiability Question

Lecture by Orna Grumberg (Technion). Slides: Constrained Horn Clauses and their Applications, lecture 1 of 3.

Proving that a program meets its specification almost always comes down to one hard step: finding an inductive invariant for the loops. This lecture follows that single step through sixty years. In 1967, after Floyd and Hoare, a person wrote the invariant by hand and a checker confirmed it. From the 2000s a solver finds it, because the whole verification problem can be written as a set of constrained Horn clauses, and satisfiability of that set is exactly the existence of an invariant. Today a language model can produce candidates too, but the checking half of the arrangement does not change.

The verification problem, and who supplies the invariant slides 3-6

The problem statement is short. You are given a program and a formal specification, that is, a logical formula, and you must answer whether the program satisfies the specification. This question is not decidable. Floyd and Hoare, in the late 1960s, gave methods for verifying input-output specifications, and those methods remain the backbone of the field.

Undecidability does not make the situation hopeless. It means no single method can be automatic, complete and always terminating at the same time. The methods in this lecture give up guaranteed termination: they are automatic, and when they answer the answer is sound, but they may run forever.

The specification of the running example is an input-output pair: if the precondition x > 0 holds at the start, then the postcondition a*b < 0 must hold at the end. Around it the deck frames the history as one question with three answers. In 1967 a human writes the invariant, in the 2000s a solver finds it, and today a language model is one more guesser. What stays fixed is the set of proof obligations the candidate has to pass.

Floyd's three obligations on one small program slides 7-8

The program is drawn as a control flow graph with five locations:

  1. ℓ0: entry
  2. ℓ1: a := 0 ; b := 0
  3. ℓ2: a < x ? (loop head; true goes to ℓ3, false goes to ℓ4)
  4. ℓ3: a := a+1 ; b := b−1 (then back to ℓ2)
  5. ℓ4: return(a*b)

Floyd's method asks you to place an assertion Inv at the loop head ℓ2, and then to discharge three obligations. Written with the primed variables standing for the values after the loop body, they are:

Initiation:   Pre ∧ (a=0 ∧ b=0)  →  Inv(x, 0, 0)
Consecution:   Inv(x, a, b) ∧ a < x ∧ a′ = a+1 ∧ b′ = b−1  →  Inv(x, a′, b′)
Safety:   Inv ∧ ¬(a < x)  →  Post

If all three are valid, the program satisfies the specification, written as the pair 〈Pre, Post〉, and Inv is an inductive invariant: it holds whenever execution reaches ℓ2. Initiation says the invariant is true on first arrival at the loop head, consecution says one pass through the body cannot break it, and safety says that whatever the invariant still allows on exit is enough to imply the postcondition.

Definition Inductive invariant. An assertion attached to a program location that is implied by the initial condition, is preserved by every transition back to that location, and is strong enough to imply the property you want. The three conditions are checked without ever running the program, which is why the check is finite even though the set of executions is not.

Why finding the invariant is hard slides 9-10

The deck now tries the obvious candidate, a+b = 0. It looks right: the loop increments a and decrements b in lockstep from a = b = 0, so their sum stays zero, and initiation and consecution both go through.

The answer on the slide is no, and the reason is the safety obligation. That obligation quantifies over every state satisfying Inv, not only over the states the program can reach, and a+b = 0 has forgotten everything about x. Take x = −5 with a = b = 0. The guard a < x is false, so this state satisfies Inv ∧ ¬(a < x), and yet a*b = 0, which is not < 0. The safety check fails.

A correct invariant has to carry the precondition forward with it:

x > 0 ∧ a + b = 0

Now the safety check works. On exit we know a ≥ x and x > 0, so a > 0; from a + b = 0 we get b = −a < 0; therefore a*b < 0. The lesson the deck draws is blunt: finding the invariant is hard. The obvious candidate was too weak by one conjunct, and nothing in the program text points at the missing piece.

Two ways to make it automatic slides 11-13

If a human should not have to supply the invariant, the machine must. The deck lays out two strategies for that.

Model checking, due to Clarke, Emerson and Sifakis in the early 1980s, takes a finite-state model together with a temporal-logic property and answers yes, or no with a counterexample. The procedure is fully automatic and it always terminates, because the state space it explores is finite. The price is in the first word: the model has to be finite state, and programs with integer variables, heaps and recursion are not.

The second strategy keeps the program as it is and represents both the program and the specification symbolically, as logical formulas. Verification is then reduced to a single question: is this formula satisfiable? Very strong solvers answer that question. The deck traces the line SAT, then SMT, then CHCs. At the last step the invariant itself becomes the unknown that the solver is asked to find, rather than an input the user has to provide.

The second route is what the rest of the lecture develops. Structurally it splits the verifier into two independent pieces. An encoder knows the programming language and turns the program plus the specification into a set of constrained Horn clauses. A CHC solver knows nothing about programs and only decides satisfiability of clause sets. Satisfiable means safe, unsatisfiable means buggy. slide 14

Careful The polarity here is the opposite of the one used for verification conditions. When a tool sends a negated property to an SMT solver, unsat is the good news. With CHCs, sat is the good news, because a satisfying interpretation is a proof. Read the verdict against the encoding that produced it.

What a constrained Horn clause is slide 15

A constrained Horn clause is a first order logic formula of the form

∀x.   B(x)  →  H(x)

where the body and the head are restricted as follows:

B(x)  :=  p1(x1) ∧ … ∧ pk(xk) ∧ φ
H(x)   is either   pk+1(xk+1)   or   φ′

Three ingredients deserve names. The symbols p1, …, pk+1 are uninterpreted predicates: they have an arity and nothing else, and giving them a meaning is precisely the solver's job. The formulas φ and φ′ are constraints, written in a fixed background theory such as linear integer arithmetic, so their meaning is fixed in advance. The whole clause is universally quantified over its free variables, which is why the quantifier is usually left implicit.

The Horn restriction is the part that matters: the body may contain any number of predicate applications, but the head contains at most one. That is what keeps a satisfying interpretation constructible rather than requiring a case split on which disjunct in the head to make true. The example on the slide is

∀x, y, z.   p1(x, y) ∧ p2(y, z) ∧ z = x + y  →  p3(x, z)

Here z = x + y is the constraint and the three p symbols are uninterpreted.

Definition Three shapes of clause. A clause whose body has no predicate applications at all, so the body is just a constraint, is a fact: it asserts something unconditionally. A clause with predicates in both body and head is a rule. A clause whose head is a constraint φ′ rather than a predicate application is a query, also called a goal clause: it states an obligation that the predicates must be strong enough to discharge. Every program encoding uses all three.

Key idea Satisfiability of a CHC system. A set of clauses Π is satisfiable if there is an interpretation I that assigns to every uninterpreted predicate a relation, given as a formula over the background theory, such that every clause in Π becomes valid. Satisfiability is a property of the whole set, not of a single clause, because the same predicate can occur in many clauses and one interpretation must serve them all.

Encoding the example program slides 16-17

The encoder introduces one uninterpreted predicate per program location of interest, with the program variables as arguments. For the running example it needs two: p(x, a, b) for the loop head ℓ2, and q(x, a, b) for the exit ℓ4. Reading the predicate as "this state is reachable at that location" is the right intuition. The four clauses it emits are exactly the ones on the slide:

x > 0 ∧ a = 0 ∧ b = 0  →  p(x, a, b)
p(x, a, b) ∧ a < x  →  p(x, a+1, b−1)
p(x, a, b) ∧ ¬(a < x)  →  q(x, a, b)
q(x, a, b)  →  a*b < 0

Nothing in this list required creativity. The first clause is the entry edge with the precondition and the initialisation of a and b; it is a fact, since its body is only a constraint. The second is the loop body edge taken when the guard holds, with the assignment written directly into the arguments of the head. The third is the exit edge taken when the guard fails. The fourth is the query: it carries the postcondition, and it is the only clause whose head is not a predicate application.

Derivations, and why an interpretation is better slides 18-19

There are two ways to think about what satisfiability of the clause set means. The first is operational. A derivation starts from a fact and applies rules, building ground atoms as it goes. Intuitively, the clause set Π is satisfiable if all derivations satisfy the query, and dually it is unsatisfiable if there exists a derivation that leads to a query violation. A derivation reaching the query with a violated constraint is a concrete failing execution of the program, which is why UNSAT comes with a counterexample.

Start from the first clause with x = 1. Its body x > 0 ∧ a = 0 ∧ b = 0 is true in the theory, so its head gives us the atom p(1, 0, 0).

Apply the second clause to p(1, 0, 0). The guard 0 < 1 holds, so the head yields p(1, 0+1, 0−1), that is p(1, 1, −1). This is one pass through the loop.

Apply the third clause to p(1, 1, −1). Now ¬(1 < 1) holds, so the loop is finished and we derive q(1, 1, −1).

The fourth clause demands a*b < 0 for this atom. Substituting gives 1 * (−1) < 0, which is true, so this derivation satisfies the query. No violation on this path.

One derivation proves nothing. There is one derivation per input value and per number of loop iterations, so there are infinitely many, and enumerating them is usually infeasible. This is why solvers do something else.

The second way is symbolic, and it is the one CHC solvers actually use. Instead of enumerating derivations, the solver searches for an interpretation of the uninterpreted predicates, given as formulas in the background theory, that makes every clause valid at once. For the example the slide gives such an interpretation:

I(p)(x, a, b)  ↦  x > 0 ∧ a + b = 0
I(q)(x, a, b)  ↦  a > 0 ∧ b < 0

Substitute these into the four clauses and check them one at a time. Clause 1 becomes x > 0 ∧ a = 0 ∧ b = 0 → x > 0 ∧ a+b = 0, which is valid. Clause 2 becomes (x > 0 ∧ a+b = 0) ∧ a < x → x > 0 ∧ (a+1)+(b−1) = 0, again valid. Clause 3 becomes (x > 0 ∧ a+b = 0) ∧ a ≥ x → a > 0 ∧ b < 0, valid because a ≥ x > 0 forces a > 0 and then b = −a. Clause 4 becomes a > 0 ∧ b < 0 → a*b < 0, valid in arithmetic. All four hold, so the set is satisfiable and the program is safe.

Key idea Look at what the solver returned for p: the formula x > 0 ∧ a + b = 0. That is character for character the correct invariant from the earlier slide, the one that a human had to invent by hand after the obvious guess failed. I(p) is an inductive invariant. The solution to the satisfiability problem is not a hint about the invariant, or a certificate that one exists; it is the invariant itself.

The correspondence is worth stating precisely, because it is the reason this encoding is used at all. The clauses about p are, one for one, Floyd's obligations with Inv replaced by the unknown p. Validating the fact means p is implied by the precondition at the loop head, which is initiation. Validating the loop rule means p is preserved by the body, which is consecution. Validating the exit rule together with the query means p is strong enough to give the postcondition, which is safety. A satisfying interpretation therefore exists if and only if an inductive invariant exists, and the two are the same formula.

The same three obligations, sixty years apart slide 20

The deck places the 1967 form and the modern form side by side, and they line up row by row.

Obligation1967: the user supplies InvToday: the solver supplies p
InitiationPre ∧ init → Invx>0 ∧ a=0 ∧ b=0 → p(x,a,b)
ConsecutionInv ∧ guard ∧ body → Inv′p(x,a,b) ∧ a<x → p(x,a+1,b−1)
SafetyInv ∧ ¬guard → Postp(x,a,b) ∧ ¬(a<x) → a*b<0

The formulas are the same formulas. The only thing that changed is who produces the invariant. In the left column Inv is given and the tool checks three implications. In the right column p is an unknown and the tool solves for it. This is also why the split into encoder and solver pays off: the encoder can be rewritten for a new language, and every improvement in the solver is inherited by all the front ends at once.

Solvers and applications slides 21-22

The back end of the pipeline is a competitive area with several mature implementations. The deck names Spacer, Eldarica, Golem and FreqHorn. They all consume a set of CHCs and return SAT with an interpretation or UNSAT with a counterexample derivation, so a front end can in principle switch between them.

The clause set is a general interface, not a program-specific one. The applications slide shows three inputs producing the same kind of object: a program with a property, a piece of hardware with a property, and a concurrent system with a property, all encoded into CHCs and all answered as SAT or UNSAT. Any task that can be phrased as "does there exist an inductive assertion covering all behaviours" fits this shape.

What the answer guarantees, and what it does not slide 23

The lecture is explicit about the limits. SAT means the system meets its specification on all behaviours, which is a much stronger statement than any amount of testing can give. UNSAT means there is a bug, and it comes with a counterexample. But both are guaranteed only relative to three things.

  • Encoding Does the model say what the code really does? A wrong encoding proves a true statement about the wrong program.
  • Specification Is the property the one we actually wanted? A verified program can still be useless if Post is too weak.
  • Termination CHC solving is undecidable, so the solver may never answer at all.

These three gaps are, in the deck's framing, exactly where a language model can help, and exactly where it must not be trusted.

A language model as one more guesser slides 24-27

The final part of the lecture puts the history back together. If the hard part is producing a candidate invariant and the easy part is checking one, then any generator can fill the generating position, including a language model. The arrangement is a loop: a generator proposes a candidate, a checker tests it, and on failure the candidate together with the counterexample goes back so the generator can try again.

Two points deserve emphasis. First, the feedback on failure is not new: it is the same information Floyd's checks gave a human in 1967, namely which obligation broke and on which state. Second, the checker is the part that carries the guarantee. A generator that is right most of the time is useful; a generator trusted without checking removes the point of the exercise.

The conclusion the deck draws is deliberately modest. This is a limited view of formal verification, invariant finding for proving program correctness, while the Floyd method and modern solvers handle far richer program structures and more complex specifications. Recent work applies language models in several ways to assist formal methods, not to replace them, and such models guarantee nothing unless their output is checked by a formal checker. The closing slide completes the three-line history: in 1967 a human writes it, in 2000 a solver finds it, and now a language model guesses it and a solver still checks it.

Why the Horn restriction is what makes solving possible

Suppose heads could be disjunctions of predicate applications. Then a satisfying interpretation would have to choose, for each situation, which disjunct to make true, and those choices interact across clauses. With at most one predicate in the head, each clause reads as a lower bound on one predicate: whatever the body allows must be inside the head predicate. There is then a well defined least interpretation, the set of atoms derivable from the facts by the rules, and the whole question is whether that least interpretation satisfies the queries. Solvers do not compute it directly, since it is generally infinite, but its existence is what lets them search for an over-approximation of it that is still strong enough for the query. The invariant they return is exactly such an over-approximation.
