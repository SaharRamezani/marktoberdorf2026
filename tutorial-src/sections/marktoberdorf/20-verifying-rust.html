The tape is heavily garbled in places; where a name or a detail could not be recovered with confidence it is described rather than guessed at, or left out.

The previous section ended with linearity, ownership and borrowing treated as language design. This one turns that design into a verification story. The engineering half is getting real Rust, the kind that arrives as a crate with dependencies rather than as a single file, into a form a proof tool can read. The conceptual half is the payoff: because safe Rust forbids observable aliasing, a Rust function can be modelled as a pure function of its inputs, so verification proceeds with no heap and no separation logic.

Getting real Rust out of the compiler

The Rust compiler lowers a program through intermediate representations whose names, as the lecturer put it, are pleasingly unimaginative: a high-level one, then a typed high-level one, then a mid-level one . The mid-level IR is the target worth having, because surface syntax has been elaborated away and borrow information is present. Reaching it is a great deal of engineering, and none of it is research.

Four difficulties came up. The compiler's internals move, so anything built against them has to be chased through releases. A real crate is not a file you can hand to the compiler: the build system decides the exact invocation, with the right options and paths, so the practical way in is to sit inside the build and intercept that invocation rather than reconstruct it. The mid-level IR is shaped for a compiler that monomorphises, whereas a verifier wants functions before specialisation with their type parameters still visible, so that one proof covers every instantiation. And it is a control flow graph, while rules and proofs are far easier over a syntax tree, so control flow has to be rebuilt on the way out . Representation detail such as the internal encoding of constants can be discarded entirely.

Key idea Going through the build system is not a shortcut, it is the only honest entry point. Parsing source directly means reimplementing dependency resolution, feature selection and trait resolution, and making them agree with the compiler exactly. Riding inside the build lets the compiler do that work and reads off the result.

The tool that does this is Charon. It takes the arguments you would give the compiler or the build system, drives the build, and writes out a file in LLBC, the Low-Level Borrow Calculus, as plain JSON. That deliberately boring format means an analysis can be written against LLBC without linking against the compiler. Charon also pretty-prints, and printed that way LLBC shows a program with the sugar removed: reborrows and two-phase borrows explicit, trait resolution already done, every variable declared at function entry. The stage is shared infrastructure rather than a private component: the recording names Aeneas as the main consumer, plus a Rust to C compiler and further research projects on the same output .

Entered the way a build is entered, with compiler or build-system arguments. The build resolves dependencies, features and targets; the tool intercepts the resulting compiler invocation.

Aeneas reads LLBC and produces the pure functional model that goes to the proof assistant. Other back ends read the same file for other purposes.

What the borrow calculus makes explicit

Definition LLBC, the Low-Level Borrow Calculus, is a statement language with a separate category of operands. It distinguishes right-hand from left-hand values, in the sense the terms have in C, and addresses memory through places, which are paths rooted at a variable: x, *x, x.f. Moves and copies are written out rather than inferred, intermediate subexpressions are lifted into named temporaries, and every local, every argument and a distinguished return variable is declared at function entry .

The feature that matters most is that a borrow carries its flavour in the syntax: the term itself records whether it is shared or mutable. The recording is explicit that this is not decoration, and that the reason is the treatment of moves. Take the copy rule. Copying out of a place is allowed only when the value there is not moved out, not loaned out, and not mutably borrowed. Each premise is a soundness condition: copying a moved-out value reads something that no longer exists, duplicating a loan destroys the accounting that says exactly one borrow is outstanding, and duplicating a mutable borrow breaks the mutable-exclusive-or-shared discipline outright. Shared borrows are the exception and may be duplicated, since a shared borrow is by definition not unique . Moves obey a slightly more permissive rule than copies, because moving out of a borrowed value can be sound where copying it is not.

Why distinguish a move from a copy at all, if the information is the same?

The lecturer raised this himself. Move an array or copy an array and the bits at the destination are identical, so nothing turns on the distinction informationally. His answer was about optimisation. If reading a variable after it has been moved out is undefined behaviour, a compiler can exploit that during code generation, and it can only do so if the move is recorded rather than reconstructed. He noted this has been the subject of a long-running and still contested language proposal .

The second decision is more radical. The operational semantics has no memory, no addresses, no byte layouts and no pointer type. An environment maps variables directly to values, which makes it read almost exactly like the semantics of a functional language . Borrowing is expressed by two special values: a borrow, tagged with a loan identifier and its flavour, and a loan, marking a value as lent out. Taking a second shared borrow from an already shared place grows the loan set by one fresh identifier rather than replacing it .

What that buys is that the borrow relationship is a fact of the semantics rather than something recovered afterwards. At every program point the environment says which places are loaned out, under which identifiers, and which borrows hold them. A semantics built on addresses would first commit to a model of memory and then need an alias analysis to reconstruct the very relationship the language had already guaranteed. Here the graph of who points at what is apparent by inspection, and the analysis is flow sensitive by construction rather than a global system of constraints to be solved . Two consequences follow: the semantics is strong enough to stand in for the borrow checker, since the soundness conditions live in the premises of the rules; and being semantic rather than tied to lifetime annotations, it accepts, and can explain, examples the real checker rejects .

Rules you may apply whenever you like

Environments are deliberately kept in an exploded form, with the whole chain of loans and borrows spelled out, and are folded back into ordinary values only when something forces the issue . A separate family of rules does the tidying. They do not fire at particular program points; they state which manipulations of an environment are legal, and an implementation applies them when convenient . Ending a mutable borrow is allowed when the borrow is not itself lent out further: the borrow is lost and the matching loan regains the full value. Ending a shared borrow either restores full ownership, if you were the last borrower, or simply shrinks the loan set by one.

One rule took real effort to get right. If a place is lent out but only through shared borrows, you may still read from it. That sounds like a violation and is not: since every outstanding borrow is shared, nobody can mutate the value underneath you, so the read is sound .

I used to hate declarative semantics. I wanted someone to just give me the algorithm for implementing the thing. I came round to these rules, because they encode the truth of the system: they say what is legal and what is not, and they leave the strategy to you.

Two-phase borrows, stated rather than computed

Two-phase borrows were his worked example of why the declarative style is worth having. The official description is thoroughly operational: treat them as mutable borrows, except that at each location you check whether a two-phase borrow has been activated, look for conflicting live mutable borrows between the reservation point and the activation point, and use dominators to find those points . His verdict was that this is correct and destroys the intuition, which is simply that a borrow should begin under the restrictions of a mutable borrow and later become shared.

In the calculus that is two lines. There is a third flavour, a reserved borrow, and the rules give it exactly the restrictions a mutable borrow has, so in particular it cannot be duplicated. A separate rule permits a reserved borrow to be promoted to a shared one . Nothing is computed and no dominators appear; the operational description falls out as a consequence of the restrictions instead of being the definition.

The translation that makes verification easy

Since the semantics maps variables to values and never mentions memory, translating a Rust program into a pure function ought to be within reach. The example showing why it is not immediate is a function that picks one of two mutable references .

fn choose<'a, T>(b: bool, x: &'a mut T, y: &'a mut T) -> &'a mut T {
    if b { x } else { y }
}

let mut x = 0;
let mut y = 0;
let z = choose(true, &mut x, &mut y);
*z = *z + 1;
assert!(x == 1);

The assertion is obviously true and proving it modularly is genuinely hard. The caller may not look inside choose. Its interface says only that the returned reference shares a lifetime with both arguments, so the value behind it comes from x or from y without saying which, and yet the write through z has to be reflected back into whichever it was.

The resolution is to translate one Rust function into two pure functions. The forward function is the half you would write by hand. The backward function is the interesting half: it says what happens at the moment the borrow is given up, taking the final value behind the returned reference and handing back updated values for the inputs .

choose      (b : bool) (x : T) (y : T)         : T     = if b then x else y
choose_back (b : bool) (x : T) (y : T) (z : T) : T * T = if b then (z, y) else (x, z)

let z      = choose true x y in
let z      = z + 1 in
let (x, y) = choose_back true x y z in
assert (x = 1)

Read the backward function as a statement about ownership. Along the true branch the reference came from x, so the updated z becomes the new x and y is returned untouched; along the false branch the roles swap. The caller never learns which branch ran, because the pair of functions is the callee's interface and is derived once. The lecturer ran this through the tool in the last minutes of the session, with a proof assistant back end selected, and got back the forward and backward pair he had just written out by hand.

Why this means no separation logic

Safe Rust guarantees that a value is either shared and immutable or uniquely owned and mutable. There is therefore no observable aliasing, and without observable aliasing the effect of a function is a function of its inputs . So the model of a Rust program can be a pure functional program, and a proof about it is a proof about pure functions.

Compare the Viper lectures in section 5. There the heap is a first-class object of the reasoning: to say anything about a write you need an access permission for the location, and to say that an assertion about a different location still holds you need the separating conjunction, the device that lets you assert two things about disjoint parts of the heap and frame one across an operation on the other. All of that machinery exists to recover, inside the logic, a disjointness property the program does not otherwise guarantee.

Key idea A type system strong enough to forbid aliasing buys a verification setting in which permissions and the separating conjunction are not required. The disjointness is not proved by the verifier; it is enforced by the language, once, before verification begins. That is why the target of the translation can be a proof assistant's ordinary functional language rather than a program logic.

Two honest qualifications. The machinery has not vanished, it has moved: the care separation logic spends on permissions is spent here in the borrow calculus and in the discipline of backward functions, paid once by the toolchain rather than once per program. And the argument rests entirely on the guarantees of safe Rust, so unsafe code, raw pointers and interior mutability sit outside it .

What the recording settles, and what it does not

The lecturer was careful not to overclaim. He said outright that this is one style of semantics for Rust among several, that different tools reasonably sit at different levels, and that he was not arguing it is the only right account . His claim was narrower: it is a style you can build a functional translation on, and therefore a style you can verify Rust through.

The recording contains no list of unsupported features, so none is offered here. What it does flag as delicate is the condition on overwriting a value: writing to a place is fine when the loans sit underneath a borrow, since the old value is retained along with its ownership information, and unsound when the place itself is lent out, because the write would be visible through a borrow that expected the value to hold still. The session closed by naming what follows. The semantics here is concrete, with real values in the environment; the next lecture replaces it with a symbolic interpreter over the same rules, and the remaining two use that to synthesise the forward and backward pair systematically rather than by hand .
