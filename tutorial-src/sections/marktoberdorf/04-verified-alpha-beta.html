A Verified Alpha-Beta Game Player

Jean-Christophe Filliâtre, CNRS. Deck: The Why and How of Deductive Program Verification, lecture 4.

The first three lectures used Why3 to reason about programs. This one uses Why3 to write one. The example is the search engine of a two-player game, alpha-beta pruning, of the kind a machine would use to play Othello against a human. The code is about fifteen lines. The interesting part is the contract, because alpha-beta does not compute the min-max value of a position, and a specification that claims it does cannot be proved. Working out what is true instead, and why the top-level function is nevertheless exact, is the whole of this lecture.

Why3 as the implementation language

The deck opens with a remark rather than a definition: if you need a verified piece of software, it is much easier to implement it in a programming language that was designed with verification in mind, and Why3 can be used this way. In the earlier lectures WhyML mostly served as a vehicle for the weakest precondition calculus, a place to write annotated programs so that verification conditions could be generated from them. Here the direction is reversed. The program is written in WhyML because that is the language it is going to live in, it is proved there, and executable code is produced from it afterwards.

The concrete goal for the day is a two-player game, human against computer, where the machine side runs a verified alpha-beta pruning search. Othello is the game the deck names.

The game, and the tree

The model is deliberately thin. Two players, A and B, move in turn. For each game position, either the game is over, or there is a finite number of legal moves. Iterating that description gives a tree: the root is the current position, the children of a node are the positions reachable by one legal move, the levels alternate between A to move and B to move, and the leaves are finished games, won by A, won by B, or drawn.

If that tree is finite and not too big, tic-tac-toe being the standard example, every position can be evaluated exactly as winning, losing or drawn, and an optimal strategy follows. For a realistic game this is out of reach. So the descent is stopped at some point and the position reached there is evaluated heuristically. Everything that follows is about searching the truncated tree efficiently, not about the quality of the heuristic, which stays a parameter of the development.

Min-max, and the negamax reformulation

Fix all values as seen by player A. Then A maximises and assumes that B minimises, so the value of an internal node is the maximum of its children's values on A's turn and the minimum of them on B's turn, with the heuristic supplying the leaves. That is the min-max algorithm.

Alternating between two operations is a nuisance in code and worse in a proof, so the deck adopts the usual reformulation. Evaluate every position from the point of view of the player who is about to move, and assume that the other player's evaluation of the same position is the negation of ours. The two levels then look identical: the value of a node is the maximum, over its children, of the negation of the child's value. Only max is needed, and the picture from the previous slide reappears with alternating signs. This convention is called negamax, and the deck marks this slide as the point where it moves to a live demonstration.

Pruning: the interval that makes work unnecessary

Looking at a min-max tree, some subtrees clearly cannot influence the answer at the root, and the deck marks them in red on the slide immediately after the min-max picture. Alpha-beta turns that observation into an algorithm. The principle in one line: maintain an interval [α, β] outside which there is no need to compute the value of the position. The deck credits the classical analysis to Donald E. Knuth and Ronald W. Moore, "An analysis of alpha-beta pruning", Artificial Intelligence 6(4), 1975.

Read the two bounds as promises already extracted from work done elsewhere. α is the best value the side to move has already secured somewhere else in the tree, so any line worth less than α will simply not be chosen. β is the best the opponent can already hold us to higher up, so any line worth more than β will be avoided by the opponent before we ever get to play it. In both cases the exact value is irrelevant to the decision at the root, and computing it would be wasted effort.

The picture also makes the danger visible. The value reported for the middle child, whatever the implementation happens to return there, is not its min-max value. It is only known to be no better than 3. That inaccuracy is not a defect to be fixed; it is precisely what was bought by skipping the leaf worth 8.

Modelling the problem in Why3

The development takes the game itself as a parameter. A type of positions is declared with no structure at all, the sentinel value inf is declared as a positive constant, and the heuristic is declared as a function whose only stated property is that it stays within the sentinel bounds. 

type position

val constant inf: int
  ensures { 0 < result }

val function eval_position (_: position) : (v: int)
  ensures { -inf <= v <= inf }
Careful

These are val declarations, that is contracts with no body, and lecture 3 established that such a declaration is logically an axiom: the weakest precondition calculus adds the postcondition to the context at every call site without anyone having proved it. That is the right choice here, since the point is to verify the search and not the game, but it draws the boundary of the proof. If the heuristic ever returns a value outside the range it promises, the theorem below no longer applies to the running program.

The tree is an ordinary algebraic type, a position together with the list of the sub-games reachable from it, and the specification is the min-max evaluation written directly over it. 

type game = Node position (list game)

let rec function eval (g: game) : int
= match g with
  | Node p Nil -> eval_position p
  | Node _ gl  -> eval_list gl
  end
with function eval_list (gl: list game) : int
= match gl with
  | Nil        -> -inf
  | Cons g gl  -> max (- eval g) (eval_list gl)
  end

Three things about this pair are worth pausing on. First, it is written with let rec function, the technique from lecture 3: a terminating pure program that Why3 promotes to a logical symbol, so the specification rests on a definition rather than on axioms. Second, the negation in max (- eval g) (eval_list gl) is the negamax convention, and it is the only place where the zero-sum assumption enters. Third, eval_list Nil is -inf, the neutral element of max over the range in play, so a node with no children is the worst possible outcome for the side to move.

Worth noticing

game is an inductive type, so every value of it is a finite tree. The truncation of the search, the "we stop our descent at some point" from the earlier slide, is therefore built into the data rather than enforced by a depth counter inside the algorithm. Termination of both eval and the search comes for free from structural descent, and neither the specification nor the code carries a depth argument.

The goal is then stated in one line: the search should return the min-max value of the tree it is given. 

let alpha_beta (g: game) : (v: int)
  ensures { v = eval g }
= ...

The code

The implementation is a pair of mutually recursive functions, one for a game and one for a list of games, both carrying the current window as two extra arguments. 

let rec alpha_beta_g (a b: int) (g: game) : (v: int)
= match g with
  | Node p Nil -> eval_position p
  | Node _ gl  -> alpha_beta_l a b gl
  end
with alpha_beta_l (a b: int) (gl: list game) : (v: int)
= match gl with
  | Nil ->
      a
  | Cons g gl ->
      let a = max a (- alpha_beta_g (-b) (-a) g) in
      if a >= b then a else alpha_beta_l a b gl
  end

let alpha_beta (g: game) : (v: int)
= alpha_beta_g (-inf) inf g

Four details carry the algorithm. The recursive call on a child passes the window (-b, -a), negated and swapped, because the child's values are the negations of ours: our floor is the child's ceiling. The result of that call is negated on return. The let a = max a ... rebinds a locally, so each child that improves on the current best raises the floor for the children still to come, which is why move ordering matters so much in practice. And if a >= b then a is the cutoff: the function returns immediately, and the rest of the list is never traversed.

The recursion is structural, alpha_beta_g descending into the children of a node and alpha_beta_l moving along a strictly shorter list, so the slides carry no variant clause. This is the same structural descent that justified eval, and it is what makes the algorithm terminate whatever the heuristic does.

The contract that is actually true

Careful

The obvious move is to give the recursive worker the same postcondition as the entry point, ensures { v = eval g }. That specification is false, and it is false for exactly the reason alpha-beta is fast. When the running value reaches b, the function returns without looking at the remaining children, so it cannot possibly report the maximum over subtrees it never visited. Symmetrically, when every child is worth less than a, the function returns a, a floor supplied by the caller that has nothing to do with the value of this position. Pruning and exactness are two names for the same trade: work may be skipped precisely when the exact answer is not needed.

What is true is a case analysis on where the true value sits relative to the window. 

let rec alpha_beta_g (a b: int) (g: game) : (v: int)
  requires { -inf <= a < b <= inf }
  ensures  { -inf <= v <= inf }
  ensures  { eval g < a -> v <= a }
  ensures  { a <= eval g <= b -> v = eval g }
  ensures  { b < eval g -> v >= b }

The companion contract for the list function says the same thing in the shape that the recursion needs, with the clipping at a made explicit. 

with alpha_beta_l (a b: int) (gl: list game) : (v: int)
  requires { -inf <= a < b <= inf }
  ensures  { a <= v <= inf }
  ensures  { if eval_list gl <= b
             then v = max a (eval_list gl) else b <= v }

Note how much stronger this is than a bare bound. Below the ceiling the result is not merely close to the truth, it is max a (eval_list gl) exactly, the true value clipped from below at the incoming floor. That precision is what lets the caller reconstruct the exact value when the floor happens to be low enough, which is what happens at the root.

The precondition is -inf <= a < b <= inf: a genuine, non-empty window inside the range the heuristic can produce. The caller is saying that any value at or below a is already beaten elsewhere, and any value at or above b is already refuted by the opponent higher up. Both are promises about the rest of the tree, not about this subtree.

The child is searched with alpha_beta_g (-b) (-a) g. In negamax the child reports from the opposing point of view, so our floor becomes its ceiling and our ceiling becomes its floor. The precondition transfers: from -inf <= a < b <= inf it follows that -inf <= -b < -a <= inf, so the recursive call is legal.

let a = max a (- alpha_beta_g (-b) (-a) g) rebinds a for the remainder of this list. Each child that beats the current best raises the floor for the children still to come, which is why the windows narrow as the traversal proceeds and why examining strong moves first prunes more.

if a >= b then a returns immediately, abandoning the rest of the list. From this line onward the returned number is only a lower bound. This single test is the entire optimisation, and it is also the entire reason the naive postcondition fails.

Take a = 3, b = 4, and a first child worth 10 to us, that is with eval g = -10. It is searched with window (-4, -3). Since -10 < -4, the first clause applies and the call need only return some w <= -4. Negating, -w >= 4, so the new a is at least 4, the test a >= b fires, and we return. If the second child had been worth 100, then eval_list gl = 100 and the returned value is nowhere near it. All the contract claims is b <= v, and that is all a caller may use.

Take a = 3, b = 4 again, with two children worth 0 and 1 to us. Each is searched with window (-4, -3), each true value lies above the ceiling -3, so each call returns some w >= -3 and each -w is at most 3. The floor never moves, no cutoff fires, and the Nil case returns 3. Here eval_list gl = 1 <= b, so the contract demands v = max a (eval_list gl) = max 3 1 = 3, which is what happened. The answer is correct and is still not the min-max value.

The entry point calls alpha_beta_g (-inf) inf g. The precondition holds because inf is positive. Every value the heuristic produces lies in [-inf, inf], and a short induction over eval and eval_list carries that range to every node. So a <= eval g <= b holds at the root, the middle clause fires, and v = eval g. The theorem announced earlier, that alpha-beta computes the same value as min-max at the root, is the middle clause instantiated at the widest possible window.

Key idea

The exactness clause is stated on a closed interval, a <= eval g <= b -> v = eval g, and that is not cosmetic. Written with strict inequalities it would not cover a position whose value happens to be exactly -inf or inf, and the root call, which uses precisely those two bounds, would fall outside the exact case. The top-level postcondition v = eval g would then be unprovable even though the algorithm is correct.

Why this development needs no ghost code

Lecture 3 introduced ghost variables and lemma functions for cases where the specification needs information the code does not carry, or where a property needs an induction that SMT solvers will not perform. Neither is required here, and the reason is instructive. The information the specification needs, namely the min-max value, is available as the logical function eval, itself defined as a terminating pure program in the style of that lecture, so no ghost witness has to be threaded through the code. The induction is supplied by the recursion of the algorithm itself: because the contract is stated as three implications rather than one equality, the inductive hypothesis at each recursive call is already in the exact shape the caller needs. Getting the contract right removed the need for any proof scaffolding.

From a proved module to a program you can play

Once the module is verified, the Why3 code is translated to OCaml automatically, with a command of the form why3 extract -D ocaml64 alpha_beta.AlphaBeta. The extracted search is then linked with ordinary, unverified OCaml: the rules of Othello, the generation of legal moves, the heuristic evaluation, and the user interface. The whole thing can be compiled further to JavaScript so that the game runs in a browser.

This division is worth stating plainly, because it is what a verified component actually buys. What is proved is that the search returns the min-max value of the tree it was handed, under the negamax convention and the declared bound on the heuristic. What is not proved is that the tree correctly represents Othello, or that the heuristic is any good. The abstract type position and the val declarations from earlier mark that boundary exactly, and the extraction step is where the unverified side gets plugged in.

The same recipe scales beyond a teaching example. The Why3 site points to two larger case studies the deck names: a nontrivial subset of the algorithms of GMP, the GNU multiple precision library, verified with Why3 and then translated to C, by Guillaume Melquiond and Raphaël Rieu-Helft in 2020; and a checker for a railway information system, verified with Why3 and then translated to OCaml, by Boyer, Canva, Manighetti and Marché in 2025.

What deductive verification consists of

The deck closes by widening the view from this one example to the enterprise behind it. Deductive verification means designing several things at once: programming languages, with their semantics and type systems; specification languages, with their logic; and libraries, both the programming libraries a user writes code against and the logical theories a user writes specifications against. It also means implementing compilers, logical transformations, and, in the deck's own phrase, a lot of plumbing. The last slide of the series is a single line: it is a lot of fun.

The alpha-beta example makes that list concrete. The type system and effect discipline decided that eval could be promoted to a logical symbol. The specification language allowed the three-clause contract to be written at all, which is where the real work of this lecture happened. The logical theories supplied lists, integers and max. The verification condition generator turned the fifteen lines of code into proof obligations, transformations passed them to SMT solvers, and the compiler carried the result out to OCaml and then to JavaScript. A short program, and most of the toolchain used at once.

Key idea

The lesson of this lecture is not about games. It is that the hard part of verifying an optimised algorithm is usually finding the statement that the optimisation actually satisfies. The specification you first write down, here "alpha-beta returns the min-max value", tends to be the property of the unoptimised version. The optimised version satisfies something weaker, and the weakening is precisely the licence to skip work. Once that weaker statement is written correctly, and once it is strong enough to instantiate back to the original claim at the top-level call, the proof itself is routine.
