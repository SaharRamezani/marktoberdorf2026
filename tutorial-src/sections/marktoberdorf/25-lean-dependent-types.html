Lean and Dependent Type Theory

Lecture by Leonardo de Moura, the first of his series on Lean. His deck exists only as slide images with no text layer, so nothing in it can be quoted or cited, and this section is reconstructed from the recording alone. The audio is poor and preserves only part of the lecture, so passages that could not be decoded with confidence have been left out rather than guessed at.

Leonardo de Moura designed Lean, and before Lean he designed Z3, the SMT solver that sits under a good deal of the verification work in these lectures, so his name has already come up several times before he steps up to speak. The surviving part of this recording is about the most basic question a dependently typed system has to answer: how data is introduced, how functions over that data are written, and what exactly the kernel has to be convinced of before it accepts such a definition. The three answers are inductive types, definition by cases, and structural recursion, and the last of them is where the termination argument lives.

Inductive types: how data gets introduced

Data in Lean is introduced by declaring an inductive type. You give the type a name and you list its constructors, saying what arguments each one takes. That is the whole declaration. The two examples de Moura used are the two that every course uses, and for good reason: between them they show the two features that matter.

The natural numbers have two constructors. One is zero, which takes no arguments. The other is succ, which takes a natural and produces a natural. Lists also have two constructors: nil for the empty list, and cons, which carries a head of type α and a tail which is itself a list of α.

inductive Nat where
  | zero : Nat
  | succ : Nat → Nat

inductive List (α : Type) where
  | nil  : List α
  | cons : α → List α → List α

The exact surface syntax he used is not recoverable from the audio, so treat the code in this section as a rendering of the shape rather than as a transcription. The shape is the part that carries the content.

Two things follow from a declaration of this kind, and both get used immediately. The first is that the constructors are the only way to build a value of the type. Every natural is either zero or succ of some natural, and nothing else, so an analysis that covers those two possibilities has covered everything. The second is that a value is a finite tree of constructor applications. There is no way to write down an infinite descent of successors, because you would never finish writing it.

The α in the list declaration is a parameter, and de Moura drew attention to it. It is not a second copy of the declaration for each element type; it is one declaration that yields all of them. You get lists of natural numbers, lists of lists of natural numbers, and lists of whatever else you later declare, out of the same three lines.

Definition A parametric inductive type is an inductive declaration that abstracts over one or more types, so that a single declaration of the constructors gives a whole family of types. List is the standard example: one declaration, and List Nat, List (List Nat) and the rest all come from it.

Definition by cases over the constructors

Once the constructors are fixed, functions over the type are written by cases on them: one clause per constructor, with the constructor's fields available as names on the left of the clause and usable on the right. Addition on naturals is the recording's own example. It looks at the second argument. If that argument is zero, the result is the first argument. If it is succ of some y, the result is the successor of the sum with y.

Appending two lists follows the same pattern on the first argument. If the first list is nil, the result is the second list unchanged. If it is cons x xs, the result is x consed onto the append of xs with the second list.

def add : Nat → Nat → Nat
  | x, zero   => x
  | x, succ y => succ (add x y)

def append : List α → List α → List α
  | nil,       ys => ys
  | cons x xs, ys => cons x (append xs ys)

Nothing here has to argue that the cases are exhaustive. Exhaustiveness is a consequence of the inductive declaration rather than a property to be checked afterwards, because the declaration is precisely the statement that these constructors are all there is.

Structural recursion, and why it terminates

Both of those definitions call themselves, so both of them owe an argument that they finish. The argument is the same in both cases and it has a name that de Moura gave explicitly: structural recursion.

The condition is syntactic. In every clause, the recursive call must be made on an argument that is a field of the constructor matched in that clause. Look at where each definition recurses. In add the clause matched succ y, and the call is on y, which is the field that succ carries. In append the clause matched cons x xs, and the call is on xs, which is the tail field that cons carries. The definition is accepted, in de Moura's words, because xs is smaller.

Smaller in what order, though, is the question worth pausing on, because the answer is what makes this work without the user writing anything. The order is not supplied; it is built into the shape of the data. A value of an inductive type is a finite tree of constructor applications, and taking a field of a constructor moves strictly down that tree. There are no infinite descending chains, because there are no infinite trees. So a well founded order comes free with every inductive declaration, and structural recursion is the discipline of recursing along it.

Two clauses: add x zero = x, and add x (succ y) = succ (add x y). The recursion is on the second argument only. The first argument x is carried along untouched.

Evaluate add x (succ (succ zero)). The second argument is a succ, so the second clause applies, with y bound to succ zero.

The result is succ (add x (succ zero)). The recursive call sits on succ zero, which is the field that the matched succ was carrying. One constructor layer has been peeled off the argument and moved onto the result.

The second clause applies again, with y bound to zero. The result is succ (succ (add x zero)). Another layer peeled off the argument, another added to the result.

Now the second argument is zero, so the first clause applies and there is no further call. The answer is succ (succ x).

Read the chain of second arguments: succ (succ zero), then succ zero, then zero. Each is a field of the one before it, so each is strictly smaller in the constructor ordering. That chain cannot be extended forever no matter which value you start from, which is the termination argument, and it was never written down by the user.

It is worth setting this against the Filliâtre lectures in sections 1 to 4, because the obligation is the same one and only the way of discharging it differs. There, termination was handled by an explicit variant clause: the user writes a term, the verification condition generator emits an obligation that the term strictly decreases at every recursive call with respect to a well founded order, and a prover discharges it like any other proof obligation. Here the order is fixed in advance by the constructors of the type, the decreasing quantity is the argument itself, and the check is syntactic rather than proved. Same debt, paid in a different currency. The variant approach is more general, since the variant can be any term at all; the structural approach costs the user nothing when the recursion happens to follow the data.

What the kernel actually checks

The most striking claim in this part of the lecture is that none of the above is checked by the kernel. de Moura was explicit and repeated it: the kernel does not check for termination, it never checks for termination, and it has no built-in notion of recursion or of fixed points at all.

The way out is compilation. A definition written by cases with structural recursion is elaborated into a term built from the type's recursor, the elimination principle that comes with every inductive declaration. The recursor is not itself a recursive definition; it is a constant with a type, and applying it is an ordinary application that the kernel can typecheck by its ordinary rules. So the recursive definition never arrives at the kernel as a recursive definition. It arrives as a term with no recursion left in it, and checking that term is a routine job.

de Moura put the same point in a second way that is worth keeping, because it explains why the arrangement is designed like this: you have to provide a certificate that the definition terminates. The elaborator's job is to produce that certificate on your behalf, and the certificate is the recursor based term itself. You write equations, the machinery finds the term, and what is trusted at the end is only the small set of rules for applications and recursors. A termination checker is a large and delicate piece of software, and keeping it out of the trusted core is the whole point. He noted that the compiled form is not hidden: you can ask the system to show you what your definition turned into, and see how the recursor does the work.

When a function has no answer

The last piece the recording preserves clearly is what to do when a case genuinely has no value to return. His example is taking the first element of a list. On cons x xs the answer is obvious, but on nil there is nothing to give back, and a total language cannot simply fail.

The fix is to change the result type rather than the totality of the function. The function returns an Option α: none in the empty case, and some x when there is a head.

def first : List α → Option α
  | nil      => none
  | cons x _ => some x

Notice that this is the same mechanism applied one level up. Option is itself a parametric inductive type with two constructors, so the partiality has been encoded as data. The function stays total, the definition stays a definition by cases, and every caller is forced to say what it does in the empty case, because the only way to get at the value is to case on the two constructors of the result.
