Automating Separation Logic Proofs with Viper

Peter Mueller, ETH Zurich. Deck: "Automating Separation Logic Proofs with Viper", with the opening lecture, the second lecture's live demos and the questions that followed both taken from the recordings.

This lecture is about one problem and one answer. The problem is that modular verification, where each procedure is verified once and independently of its callers, stops working as soon as procedures share a heap: the caller cannot tell what the callee left alone. The answer is separation logic, in the concrete form of access permissions and a separating conjunction, and the lecture shows how those ideas are turned into an automated tool. Viper is presented as an intermediate verification language: front ends for Rust, Go, Python and other languages encode their programs into it, and back ends discharge the resulting proof obligations with an SMT solver. The four parts of the deck follow that path, from the frame problem to the SCION router verification.

The opening demo: writing a specification badly, three times

The lecture began not with a definition but with a live session in Visual Studio Code, where a plugin runs the verifier in the background while you type. The point of the demo was not the tool. It was that writing a correct specification is harder than it looks, and that the verifier is what tells you so. The method is indexOf, which takes a sequence of integers and an element, and returns the index where the element occurs.

The first version checks whether the first element of the sequence is the one being looked for, returns 0 if it is, and otherwise searches the tail recursively. The verifier immediately underlines the condition: indexing into the sequence at 0 may exceed its length. That is right, because the sequence may be empty. Note what has happened already. No specification has been written yet, and the tool has still found a real bug.

Adding a check for an empty sequence, returning -1 to mean not found, makes verification succeed. What that success means is narrow but genuine: the program cannot crash. No out of bounds access, no null dereference, no division by zero. Nothing yet has been proved about what the method computes.

To say anything about behaviour you have to state it. The first postcondition is the negative case: if the result is negative, the element does not occur in the sequence. That verifies.

The positive case says that if the result is not negative then it is a valid index and the sequence holds the element there. This fails, and the reason is a genuine bug: the recursive call searches a shorter sequence and its index is returned unchanged, so the method can only ever return 0. Adding one to the recursive result fixes that and the postcondition still fails, because of a second bug hiding behind the first. When the recursive call returns -1 for not found, adding one turns it into 0, which claims the element was found at the front. The increment has to apply only when the recursive call actually succeeded.

With the method verified, the lecture made a point of general method: write a client and reason about it, to check that the specification says what you meant. Searching for 2 in the sequence 1, 2, 3 lets the client prove the result is 1.

Change the sequence to 1, 2, 3, 2 and the same assertion no longer verifies, even though the implementation would still return 1. Verification in Viper is modular, so the client is checked against the specification alone and never looks at the body. The specification promises an index where the element occurs, not the smallest one, so as far as the caller can prove, the answer could be 1 or 3. The specification is weaker than the code, and only a client exposes that.

Key idea A specification that verifies is not the same as a specification that is right. The habit worth taking from the demo is to write a small client against every specification you care about, because a proof about the implementation cannot tell you that you specified the wrong thing.

Modular reasoning and why the heap breaks it

The goal is to verify each procedure modularly, that is, independently of its callers. Each procedure is equipped with a specification: a precondition that constrains the parameters and a postcondition that constrains the results. Two proof obligations follow. The implementation must satisfy the specification, and every caller must be verified against the specification alone, proving the precondition at the call site and relying on the postcondition afterwards. 

method indexOf(s: Seq[Int], e: Int) returns (res: Int)
  ensures res < 0 ==> !(e in s)
  ensures 0 <= res ==> ...

var x: Int
x := indexOf(Seq(1, 2, 3, 2), 2)
assert x == 1 || x == 3   // succeeds
assert x == 1             // fails

The second assertion fails even though the obvious implementation returns 1, because the caller sees only the specification, which does not say which of the two matching positions is returned. That is the price and the point of modularity: what is not written down is not available.

Viper's own heap is deliberately simple. A heap is a set of objects, there are no classes, and every object carries every field declared anywhere in the program. The type rules of a source language can be encoded on top, and memory consumption is not a concern because Viper programs are never executed. Objects are reached through references, with field read and update as the only operations, and there is no explicit deallocation.

Now the trouble starts. Consider a method that writes one field.

field f: Int
field g: Int

method set(p: Ref, v: Int)
  requires p != null
  ensures p.f == v
{ p.f := v }

x.f := 0
x.g := 0
set(x, 5)
assert x.g == 0    // can the caller prove this?

The postcondition says what set establishes, but says nothing about what set leaves untouched, so the caller has no way to conclude that x.g is still 0. This is the frame problem, and the deck rejects the two obvious repairs. Inspecting the body of the callee to find out which locations it modifies is not modular and does not work for abstract methods with no body at all. Assuming conservatively that every location may change is worse: the callee would need a specification entry for every field location, including ones it never touches, and every specification in the program would have to be edited whenever a new field is declared.

Aliasing is the second half of the problem. A method that writes p.val := 5 and then q.val := 7 cannot promise p.val == 5, because p and q may be the same reference. Asking the programmer to spell out all non-aliasing facts explicitly does not scale: you cannot enumerate the disjointness conditions of an unbounded data structure, and stating them exposes the internal layout of a module, which violates information hiding.

Key idea The deck states three challenges for sequential heap verification, and the rest of the lecture is organised as answers to them: reasoning about aliasing, framing for dynamic data structures, and writing specifications that preserve information hiding. Concurrency adds more, such as data races.

Viper as an intermediate verification language

Before the logic, the architecture. Viper sits in the middle of a stack. On top is a source language with its own program, specification language and methodology, handled by a front end. In the middle is the intermediate verification language, which is small, fixed and permission aware. Underneath are two interchangeable back end verifiers, one based on symbolic execution and one on verification condition generation, and both hand their proof obligations to an SMT solver.

An earlier section of these notes covers Why3, which occupies the same position in its own stack: a small language in the middle, several front ends above it, and automatic provers below. The division of labour is the same, and so is the motivation, since writing one careful encoding into a shared middle language is cheaper than writing a verifier per source language. The difference is what the middle language builds in. Viper's assertion language is designed around a heap and around permissions to that heap, so the separation logic reasoning happens inside the intermediate language rather than inside each front end.

The Viper language itself is compact, and the lecturer walked through its four columns once the core concepts were in place. The program part is a sequential imperative language with a deliberately basic type system. There is no primitive support for concurrency, which does not put concurrency out of reach: it is encoded into the sequential core. Control flow is both structured and unstructured, so goto is available and occasionally useful when encoding a source language. The heap, by contrast, is built in, and that is the difference from Why3 and Boogie, which have no heap of their own. The verification part has the usual contract features plus inhale and exhale, the two permission transfer statements discussed below, and permission introspection. The assertion language adds inductive predicates and abstraction functions, both covered here, fractional permissions, which separate read from write access and matter most for concurrency, iterated separating conjunction, which quantifies over permissions for structures with a lot of sharing, and magic wands, for partial data structures. The last two are not developed in this deck, so this section leaves them aside. Last come the mathematical theories: predefined datatypes including sequences, sets, multisets and maps, user-defined datatypes, uninterpreted functions and axioms. The predefined collections are what abstraction functions map into.

Permissions and the separating conjunction

The central move is to associate every heap location with a permission. Permissions are created when a location is allocated by new(f, g). They are held by method executions, not by objects. Read or write access to a location requires holding the permission for it, so an assignment such as x.f := 5 is a proof obligation and not only an instruction. Permissions can be transferred, but never duplicated and never forged: the total amount in the system only changes at allocation.

Definition An access predicate acc(p.f) is the assertion "I hold the permission to the location p.f". Access predicates may not appear under negation, under disjunction, or on the left of an implication. Assertions may mix permissions with value constraints, as in acc(p.f) && p.f > 0. Most assertions in a program must be self-framing, meaning that they include the permissions needed to evaluate their own heap accesses, so a bare requires p.f > 0 is rejected.

Aliasing is then handled by a new connective, the separating conjunction. A * B holds in a state if both A and B hold and the state holds the sum of the permissions required by A and by B. If neither side contains access predicates, A * B and ordinary A && B agree. In Viper there is no separate symbol: && is the separating conjunction.

The consequence that makes the connective useful is this: holding the permission to p.f and the permission to q.f at the same time implies that p and q are different references, because permissions cannot be duplicated. Disjointness is derived from ownership instead of being stated by the programmer. The deck's example is a method swap(a: Ref, b: Ref) with precondition acc(a.f) && acc(b.f). For the call swap(x, x) that precondition is equivalent to false, so the call simply cannot be verified.

With permissions in place, framing becomes a proof rule rather than a convention.

premise: { A } S { B }
conclusion: { A ∗ C } S { B ∗ C }
side condition S does not assign to a local variable that is free in C

The frame C must be self-framing. If the heap locations constrained by C are disjoint from those modified by S, then C survives the statement. If they are not disjoint, the permissions required on the left of the conclusion exceed what any state can hold, the precondition is equivalent to false, and the triple holds trivially. The rule is therefore sound without any case analysis on aliasing.

The typical proof the deck returns to three times is small enough to check by hand. 

method set(p: Ref, v: Int)
  requires acc(p.f)
  ensures acc(p.f) && p.f == v
{ p.f := v }

x := new(f); x.f := 2
y := new(f); y.f := 7
set(x, 5)
assert x.f == 5 && y.f == 7

Note what changed compared with the version at the start. The precondition no longer says p != null; it says acc(p.f), which is stronger and also implies non-nullness. The postcondition gives the permission back, otherwise the caller could never touch x.f again. And nothing at all is said about y, yet y.f == 7 is provable, because the permission to y.f was never handed over.

Predicates for unbounded data structures

The second lecture opens by fixing a running example and using it to show what the machinery so far cannot say. The example is a linked list of integers. A node has two fields, elem and next. A list is a chain of such nodes whose last node is a sentinel: it carries no value, its next is null, and on its own it represents the empty list. The operation under discussion is append, which walks the chain, and on reaching the sentinel allocates a fresh sentinel, stores the new element in the node that was the sentinel a moment ago, and links the two. Otherwise it recurses on the tail.

Two things then go wrong. The first is that access predicates reach only a fixed, statically known set of locations, and append needs the permission to every node it visits. Written out with what the language has so far, its precondition would be acc(this.next) and acc(this.next.next) and acc(this.next.next.next), without end. There is no way to write it. The second is information hiding. Even the getter, whose precondition acc(this.elem) and postcondition acc(this.elem) && res == this.elem do fit on one line, is written entirely in terms of field names, so any client is told exactly how the module lays out its data. And the functional behaviour of append cannot be expressed at all.

User-defined predicates fix this. A predicate has a name, a list of parameters, and a self-framing assertion as its body. Because the body may mention the predicate itself, a single predicate instance can denote a statically unbounded number of permissions. 

predicate node(this: Ref) {
  acc(this.elem) && acc(this.next)
}

predicate list(this: Ref) {
  acc(this.elem) && acc(this.next) &&
  (this.next != null ==> list(this.next))
}

Recursion creates a new difficulty for a static tool: the verifier cannot know how far to unfold a recursive definition. Viper therefore uses an iso-recursive semantics: a predicate instance and its body are different things, and permissions are held either by method executions or by predicate instances, never by both at once. The stepper below follows the demo in which the need for that distinction becomes visible.

Exchanging one for the other is then an explicit step in the program text. An unfold statement trades a predicate instance for its body, and a fold statement trades the body back for the instance. 

method foo(x: Ref)
  requires list(x)
  ensures list(x)
{
  unfold list(x)     // now we hold acc(x.elem), acc(x.next) and list(x.next)
  x.next := null     // permitted
  fold list(x)       // give the body back, obtain the instance again
}

Give append the precondition list(this) and the postcondition list(this). A predicate instance is an assertion like any other, so the caller transfers it to the callee and receives it back. The lecturer's image is a box: you put permissions inside, you hand it to somebody else, they hand it back. And yet verification fails, with the message that the assignment may lack permission, even though the body of list(this) plainly contains acc(this.next).

The reason is not specific to separation logic. Any automatic verifier reasoning about recursive definitions must be built so that it never unrolls one indefinitely. Take a method with precondition list(x) whose body writes y.next := null. A verifier hunting for the missing permission would open list(x), find acc(x.next), which is not what it wants unless x and y are equal, split on the implication, obtain list(x.next) in the non-null case, unroll that, and continue. Nothing stops the search, so the verifier may fail to terminate.

So the instance and its body are made two different assertions on purpose. Mathematics does not do this, because there a predicate simply is its interpretation and there is nothing to move between. Here there is, and under that reading the question "do we hold the permission to y.next?" gets the answer no immediately, with no search.

unfold list(this) exchanges the box for its contents, and the field access now verifies. The postcondition then fails instead, because after the unfold we hold the body and not the instance. fold list(this) puts the contents back and returns the instance.

In append the fold does not succeed at the first attempt. The method has allocated a fresh node n, and the predicate body is recursive, so folding list(this) needs a list(n) instance for the new tail too. Folding list(n) first completes the proof.

fold and unfold exist only for the proof. They have no run-time meaning and a compiler erases them, which makes them ghost code in exactly the sense of the Filliâtre lectures earlier in the school, a connection the lecturer drew explicitly.

fold and unfold are statements, so they can appear only inside a method body. Assertions often need the same effect and have nowhere to put a statement: a postcondition constraining this.elem needs the body of the predicate in order to be self-framing at all. Viper therefore adds an unfolding expression, a temporary unfold that opens the predicate, evaluates one expression and closes it again, with no net effect on the permissions held. That is what makes heap-dependent functions usable in specifications, and it appears in nearly every example in the rest of the lecture.

Predicates carry more than permissions, and this is where the design pays a second time. The body of a predicate is an arbitrary assertion, so it can constrain values as well as permissions. Data structures usually maintain consistency conditions, which may be value constraints such as a reference being non-null or an integer being positive, or structural constraints such as a tree being balanced. Adding a conjunct such as 0 <= this.elem to the body of list turns these representation invariants into part of the predicate. The pattern then becomes economical: a constructor establishes the invariant by folding, and every operation begins with unfold, which assumes the invariant, and ends with fold, which checks it again.

The live version is short. Strengthening the body of list to require 0 <= this.elem at every node that is not the sentinel makes the previously verified append fail, precisely at the fold, because e is an arbitrary integer and nothing establishes that it is non-negative. That is not a false alarm: a negative argument really would break the invariant. Adding requires 0 <= e restores verification. The invariant came for free on top of the fold and unfold discipline the permissions required anyway, and every operation added later is checked against it automatically, because every operation ends with a fold.

Abstract predicates and the client's view

Predicates as introduced still mention concrete field names in their bodies, so handing a predicate to a client hands over the layout of the data structure with it. The remedy, which the lecture presents as a standard device of separation logics rather than a Viper peculiarity, is the abstract predicate: a declaration that gives the predicate a name and a parameter list and stops there, with no body. It says only that such a predicate exists. A client can hold an instance, receive one through a precondition, return one through a postcondition and pass it to another method. What it cannot do is fold or unfold it, because it does not know the body.

Combined with abstract methods, which are signatures and specifications with no code, this gives the familiar arrangement of a module and its interface. The implementation keeps the full bodies, because it needs them in order to reason; the version published to clients keeps only signatures and specifications. A client programming against list(this) then has no idea what a list is. It calls a constructor, which returns a reference packaged with its predicate instance, passes the instance into append and gets it back, and never looks inside the box.

Key idea The same abstract interface is satisfied by a singly linked list, a doubly linked list, an array-based list or a cyclic list. The client cannot distinguish them, which is what information hiding means here, and the closing demo exercises exactly that freedom.

Functions and data abstraction

Predicates solve the permission half of information hiding. Functional behaviour needs one more mechanism. Old-expressions and unfolding-expressions already allow small specifications such as

method head(this: Ref) returns (res: Int)
  requires list(this)
  ensures list(this)
  ensures res == old(unfolding list(this) in this.elem)

but the deck immediately marks the limits: this does not work when the behaviour depends on an unbounded number of fields, for instance when sorting a list, and the specification still mentions the field elem, so implementation details leak out.

This slide turns on a question. Written naively, with requires node(this) and ensures res == this.elem, the specification is not merely weak, it is not well-formed, and it is worth seeing why. The answer is self-framing: to constrain a value you must hold the permission to it, and holding the predicate is not holding its body. Since an assertion has no room for an unfold statement, the repair has to be the unfolding expression. Even repaired, the pattern reaches only as far as a getter.

The standard answer is data abstraction. The concrete data structure is mapped to a mathematical concept, a linked list to a mathematical sequence, a binary search tree to a mathematical set, and the behaviour is specified in terms of the mathematical value. Viper provides heap-dependent functions for the mapping, and they may be recursive, so they reach across unbounded structures. 

function content(this: Ref): Seq[Int]
  requires list(this)
{
  unfolding list(this) in
  (this.next == null
     ? Seq[Int]()
     : Seq(this.elem) ++ content(this.next))
}

The precondition is not decoration. A function must have a precondition that frames its body, that is, provides all the permissions needed to evaluate it. That requirement pays off twice, once here and once in the encoding, where the same precondition is read as the function's read effect. What a function does not need is a postcondition handing the permissions back. Since it cannot have side effects, it cannot lose a permission either, so Viper returns everything to the caller automatically and the annotation is halved.

Three conditions are imposed on such a function: it must be side-effect free, deterministic and terminating. Two of them come for free, because function bodies are expressions rather than statements, and an expression can neither be non-deterministic nor have a side effect. Termination has to be proved, and the obvious measure is unavailable: in the Why3 lectures a variant over a list value gives a well-founded order directly, but a Viper list is reached through a reference, and references have nothing well founded about them, since the heap may contain cycles. What is well founded is the predicate. Every predicate instance has a finite unrolling by construction, so its nesting depth is a legitimate measure, and the demo writes exactly that in a decreases clause, Viper's spelling of Why3's variant. The unfolding around the recursive call is what makes the measure go down.

With the abstraction function in place, the specification of append becomes one line and names no field at all.

method append(this: Ref, e: Int)
  requires list(this)
  ensures  list(this)
  ensures  content(this) == old(content(this)) ++ Seq(e)

Permissions are described by the predicate and values by the function, independently of each other. That separation is characteristic of implicit dynamic frames, the variant of separation logic Viper is built on, where acc(x.f) and x.f == 5 are separate conjuncts. Scaled up, it means talking about many permissions with a predicate and about functional behaviour with functions without entangling the two, which the lecturer named as the main reason Viper does not use textbook separation logic.

This closes the third challenge as far as the deck takes it. Viper offers three abstraction mechanisms and they line up neatly with the three syntactic categories of the language: methods abstract over statements, functions abstract over expressions, and predicates abstract over assertions. Together they allow specifications for unbounded data structures, for code whose implementation is unavailable such as abstract methods, foreign functions and binaries, and for modules that want to hide their internals.

The closing demo: the same list, made cyclic

The second lecture ended with a live refactoring whose only purpose was to test the claim the lecture had been making. The starting point was the file built up during the session: a null-terminated list with its predicate, its content function and a method constructing a singleton list. The target was a different representation altogether, a cyclic list, in which the empty list is a sentinel pointing at itself and a non-empty list is a sentinel followed by the value-carrying nodes, the last of which points back to the sentinel.

The permissions came first, with the functional specifications commented out so that the error messages stayed readable. A predicate that recurses until it reaches null is no use on a structure with no null in it, so the demo introduced the standard device, a list segment predicate. lseg(this, last) describes the nodes from one node up to but not including another. If this == last the segment is empty and contributes nothing; otherwise it holds the first node's two fields and, recursively, lseg(this.next, last). The list is then the permission to the sentinel itself plus one segment that starts after the sentinel and runs back round to it.

predicate lseg(this: Ref, last: Ref) {
  this != last ==>
    acc(this.elem) && acc(this.next) && lseg(this.next, last)
}

predicate list(this: Ref) {
  acc(this.elem) && acc(this.next) && lseg(this.next, this)
}

The constructor then had to be repaired, since the representation had changed: the head is now the dummy, so the element goes into the second node and that node's next points back to the head. The folds changed with it, an empty segment from the head to itself, then a segment from the new node back to the head, then the list predicate. The functional side needed a helper of the same shape, contentSeg(this, last), defined by unfolding the segment: an empty segment gives the empty sequence, otherwise the first element followed by the content of the rest. The content of a list is the content of the segment after the sentinel, which carries no value.

What changed and what did not is the entire point. The predicate body changed, the method body changed, and one predicate and one function were added, both private. The signature of list, the signature of content and the specification of the method are the same characters as before, and the client's assertions verified unchanged once uncommented. No client can tell that the data structure was replaced.

Automation: the permission mask, inhale and exhale

The third part of the deck shows how the logic is turned into work for an SMT solver. The verification condition route encodes the program into guarded commands and applies a weakest-precondition transformer: to verify a statement S, one proves the weakest precondition of S under a background predicate BP, which encodes properties of the programming language. Conditionals, for instance, become nondeterministic choice plus assume.

The heap becomes a global variable holding a polymorphic map, and permissions become a second global map called the mask. 

type Ref                                  // references
const null: Ref
type Field T                              // polymorphic field names
type HeapType = <T>[Ref, Field T]T
type MaskType = <T>[Ref, Field T]bool
var Heap: HeapType
var Mask: MaskType

v := x.f          becomes    assert Mask[x,f];  v := Heap[x,f]
x.f := E          becomes    assert Mask[x,f];  Heap[x,f] := E

Every field access begins with an assertion about the mask, so a verified program is one in which every access was owned. Since permission is by convention never held for locations of the null reference, the same check also rules out null dereferences, at no extra cost. The mask in this simplified presentation is boolean, so permission is all or nothing; the slide marks in the margin that going beyond full permission is a separate case, which is where fractional permissions come in.

Definition inhale A obtains all permissions required by A and assumes all its logical constraints. exhale A asserts all logical constraints of A, checks and removes all permissions required by A, and havocs any location to which all permission is lost. They are the permission-aware analogs of assume and assert.

Both are defined by recursion on the structure of the assertion.

assertioninhaleexhale
Eassume Eassert E
acc(E.f)Mask[E,f] := trueassert Mask[E,f]; Mask[E,f] := false; havoc Heap[E,f]
E ==> Aif (E) { inhale A }if (E) { exhale A }
A && Binhale A; inhale Bexhale A; exhale B

The last row is the separating conjunction at work: the two sides are processed one after the other, so the permissions add up on inhale and are removed as a sum on exhale. The havoc on exhale is what makes framing automatic. Once the last permission to a location is gone, the verifier forgets its value, so nothing can be assumed about it later. In both cases the real encoding also asserts that E is well-defined, which the deck omits.

With these two statements, the proof obligations for method bodies and calls are short. A body inhales the precondition, runs the encoding of the statements, and exhales the postcondition. A call exhales the precondition with the actual arguments substituted, havocs the assigned variables, and inhales the postcondition. Calling a method transfers permissions from caller to callee according to the precondition, returning transfers them back according to the postcondition, and whatever is not transferred is residual and is framed around the call. Predicates reuse the very same mask: fold and unfold are permission transfers between the caller's own permissions and the instance.

x := new(f); x.f := 2 and y := new(f); y.f := 7. Allocation creates permissions, so the current method execution now holds acc(x.f) and acc(y.f), and the mask records both. It also knows the two values.

The call set(x, 5) starts by exhaling the precondition acc(p.f) with p bound to x. The mask entry for x.f is checked and cleared, and because all permission to that location is gone, Heap[x,f] is havocked. The caller has now forgotten that x.f was 2, which is correct: the callee is free to change it.

acc(y.f) was not mentioned in the precondition, so it is residual and stays with the caller, together with the knowledge that y.f == 7. This is the frame. No reasoning about whether x and y alias is needed, because the callee received nothing that would let it write to y.f.

set is verified separately, once. Its body inhales acc(p.f), executes p.f := v, which the mask now permits, and exhales acc(p.f) && p.f == v, which checks both the value constraint and the return of the permission.

Back at the call site, the caller inhales acc(x.f) && x.f == 5. It regains the permission and learns the new value. Note the order: the value is only learned after the havoc, so no stale information survives.

assert x.f == 5 && y.f == 7 succeeds. The left conjunct comes from the postcondition, the right one from the frame. Neither requires looking at the body of set, which is exactly the modularity that was lost at the start of the lecture.

Heap-dependent functions need one more piece. They are encoded as uninterpreted functions with an extra heap parameter, and the body becomes a definitional axiom. That alone is not enough, because every field update changes the global heap variable, so all previously derived facts about function applications refer to the old heap and become useless. Recovering them by looking at the function body would break information hiding and would not work for abstract functions. The fix is a framing axiom generated from the function's precondition, which is read as a declaration of the read effect: if two heaps agree on the locations the function is allowed to read, the function has the same result in both.

∀ x, h1, h2  ::   h1[x, elem] == h2[x, elem] ⇒ get(x, h1) == get(x, h2)

The deck notes that the axiom actually used is more complex, in order to break symmetry and avoid unnecessary quantifier instantiations, and that for predicates in preconditions the axiom must consider all locations contained in the predicate. This is a good illustration of a general point about SMT-based verification: the logic is settled long before the performance is, and the shape of the axioms matters as much as their content.

Front ends: Gobra, Prusti and the cost of annotations

A front end has to bridge three gaps. The state model, where source pointers, arrays, slices and a type system must be expressed in Viper's object-based model. The execution model, where complex statements, higher-order computations and effects such as exceptions and input or output become simple statements and defunctionalized encodings. And the program logic, where concurrency and higher-order features must be built from Viper's universal primitives.

Gobra verifies Go with a separation logic very close to Viper's, targeting functional properties, memory errors, aliasing and data races. The encoding of a pointer swap shows the mechanics: Go's *int parameters become Ref objects with a val field, the source specification requires acc(x) && acc(y) becomes requires acc(x.val) && acc(y.val), parameters are copied into locals because Go allows assignment to parameters, and locals are given their default initial values by an explicit inhale tmp == 0.

The cost is visible in the source program: the developer writes separation logic directly, including the permission annotations, and the overhead is substantial in both the amount and the complexity of the annotations.

Rust's type system already guarantees the absence of memory errors, controls aliasing and prevents data races, so the question is whether verification can build on that instead of asking for it again. Prusti extracts permissions automatically from type information and generates a Viper core proof of memory safety with no user input at all. Users then add functional correctness specifications using a slight extension of Rust expressions, such as #[ensures(*x == old(*y))], with no acc in sight. The overhead for programmers is substantially reduced in both amount and complexity.

The deck makes the comparison concrete by placing a Rust program with Prusti annotations next to the Viper code a developer would otherwise write for the same list operations, where predicates, unfold, fold and permission amounts are all explicit.

The list example on the comparison slide is also where fractional permissions appear. cloneList requires acc(list(this), 1/2) and returns it unchanged, while producing a fresh list(res). A fraction below the full permission grants read access only, which is what a cloning or a length operation needs, and it can be split among several readers because the fractions still add up to at most one. The pure function len asks for acc(list(this), wildcard), an unspecified positive fraction, which is the weakest read request one can make.

The family of front ends is large: Prusti for Rust, Nagini for Python, Gobra for Go, VerCors for Java and OpenCL, SnaKt for Kotlin, and further front ends and prototypes for OCaml, Pancake and Vyper. Between them they cover imperative and object-oriented code, nominal and structural typing, ownership types, multithreading with shared state and with message passing, weak-memory concurrency, input and output, closures and iterators, and digital assets. The properties proved range from memory safety and crash freedom through absence of overflows, termination and functional correctness to race freedom, deadlock freedom, secure information flow and worst-case execution time.

Careful The deck is explicit about the limitations. Some are inherited from the SMT solver: undecidable theories can produce spurious errors, and verification time grows for large methods. Annotation overhead is typically 2 to 5 lines of annotation per line of code. And the trust assumptions are threefold, since one must trust the SMT solver, Viper itself, and the encoding performed by the front end.

A large case study: the SCION router

SCION is a new architecture for inter-domain routing, with both research and commercial deployments. The stated goal is formal end-to-end verification of security and correctness: the protocol for secure packet forwarding, and the code for crash freedom, functional correctness, termination and protocol compliance. The proof is layered. A mathematical model of the entire network is refined to a mathematical model of a border router, that model is connected by refinement and equivalence arguments to a router specification, and the implementation is verified against that specification.

The reported outcome: verification of the SCION router, 4,700 lines of optimized Go, was completed for all four properties, with 16,700 lines of annotations, a ratio of 3.6 lines of specification per line of code, and only three code changes were required. The work identified 14 confirmed issues related to memory safety, functional correctness and protocol compliance, plus 2 performance issues, in code that had already been through extensive code reviews, testing and fuzzing, and it triggered various performance optimizations.

Key idea The summary of this part is that Viper's concepts are expressive enough to encode a wide range of verification problems for different languages, programs and properties. Most front ends reflect Viper's verification logic directly, while some reduce the annotation overhead by using ownership type systems. Annotation overhead and performance on large code bases remain the open challenges.

Research directions

The closing part argues that AI increases rather than decreases the demand for verification. Large amounts of code are now generated by agents, that code contains a significant number of bugs and security vulnerabilities, and code review has become the main bottleneck of software development. At the same time AI has become effective at detecting vulnerabilities. Both trends point the same way.

Three directions follow. First, program logics, which capture the essential correctness arguments of a program: invariants for loops, ranking functions for termination, lock orders for deadlock freedom. AI agents need such logics to phrase proofs for the same reason human developers do, and logics for probabilistic programs, hyperproperties, distributed systems and quantum computing are still open problems. Second, agentic verification, presented as a trade-off rather than a winner. Explicit proof objects may be better training targets and their expressiveness is not limited by an SMT solver, but user interaction exposes the complexity of the underlying logic. Annotated programs cater to the strengths of models that are good at coding, relying primarily on an SMT solver is likely to be faster and cheaper, and a code-centric approach may make developer and AI interaction easier. Third, validation: given an intent in natural language, a specification, an implementation and proofs, the specification is the part nothing checks, so how AI-generated specifications and code are validated remains an open question.
