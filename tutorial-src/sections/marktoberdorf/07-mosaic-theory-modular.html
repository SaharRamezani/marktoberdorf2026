Bit-Precise CHC Solving with Theory-Modular Reasoning

Lectures by Orna Grumberg (Technion). Deck: "Constrained Horn Clauses and their Applications", lectures 2 and 3.

The previous section ended with a clean pipeline: a program and a specification go into an encoder, out comes a set of constrained Horn clauses, and a CHC solver answers SAT (safe) or UNSAT (buggy). One assumption sits quietly inside it: the clauses are formulated modulo one background theory. These two lectures attack that assumption. They present "Bit-Precise CHC Satisfiability Using Theory-Modular Reasoning" by Omer Rappoport, Orna Grumberg and Yakir Vizel (ATVA 2026), and the Mosaic framework built on it. The idea is to stop forcing a single theory on the whole clause set, to cut the set into fragments, to solve each fragment in the theory that suits it, and to keep the fragments consistent through interface constraints.

Machine arithmetic is not integer arithmetic

One reminder from the previous section is enough. A constrained Horn clause has a body of predicate applications plus a constraint, and a head that is either a predicate application or false. The predicates are the unknowns; the constraint is written in a background theory, and that theory fixes the sorts of the variables and the meaning of the operations.

Background theorySort
Integer arithmeticInt
Real arithmeticReal
ArraysArray[I,V]

The theory this lecture cares about joins that list a few slides later: fixed-size bit-vectors, sort BV[w], where w is the width. The reason it is needed is simple. In a real machine an integer variable is a finite binary array, so arithmetic on it wraps around. The deck makes the point with one small program fixed at 4-bit width and run on two different inputs. On the first input the loop overflows and the assertion fails. On the second input no overflow happens and the same assertion holds. The note printed on the slide is the whole motivation for the work: integers behave differently than bit-vectors.

Careful

If you verify a program by giving its variables sort Int, you have verified a different program from the one that runs. The proof can succeed while the compiled code fails, and it can fail on a wrap-around that the real code never performs. Bit-precise verification means the encoding reproduces the finite width exactly, so the answer is about the machine, not about an idealised mathematical program.

Two single-theory options, both of them stuck

Given a program that mixes bit-level operations with ordinary counting arithmetic, there are two obvious ways to produce a bit-precise CHC system, and the deck measures both on the running example with Spacer under a two-hour budget.

Option 1 is to encode everything modulo the theory of fixed-size bit-vectors, so every variable gets sort BV[4], or BV[w] in general. This is precise by construction, since the theory has the wrap-around semantics built in, but bit-vector reasoning ultimately comes down to individual bits and the cost grows quickly with the width. The deck's verdict is one word, "not scalable", with the measurement next to it: Spacer reaches width 9 in two hours.

Option 2 is to encode everything modulo integer arithmetic, so every variable gets sort Int. This is where CHC solvers are strongest, because their invariant generation and interpolation machinery is built for arithmetic. But an integer encoding is only bit precise if it spells out the wrap-around, and doing so puts modulo operations and conversions all over the constraints, which is exactly what arithmetic reasoning handles badly. The verdict is the same word with a worse number: Spacer reaches width 3 in two hours.

Every clause modulo BV[w]. Bit precise with no extra work, and the theory solver understands masks, shifts and xor natively. The price is that width drives the cost, so the whole system becomes hard as soon as w grows. On the deck's example, width 9 in two hours.

Every clause modulo Int, with wrap-around written out so that precision is not lost. Strong arithmetic reasoning is available, but the modulo operations and conversions needed for precision block it. On the deck's example, width 3 in two hours.

Neither theory for the whole system. The clauses that use bit-level operations stay modulo BV, the clauses that only count stay modulo Int, and the two sides are connected by interface constraints. This is what the rest of the section explains.

The key idea and the Mosaic framework

Key idea

Do not commit to one theory. A single CHC system usually contains clauses of two very different kinds: clauses that manipulate bits, where the bit-vector theory is the right tool, and clauses that just count, where integer arithmetic is the right tool. Use both, on different parts of the same system, and connect the parts with an interface constraint.

Mosaic is the framework that turns this idea into a pipeline. Its input is not the program directly: the usual encoder still runs first and produces an ordinary, fully bit-precise set of CHCs modulo BV. Mosaic then adds two stages. A theory-modular encoder rewrites that set into a theory-modular encoding, made of a bit-vector fragment, an integer fragment and the interface constraints between them. A theory-modular CHC solver then decides satisfiability of the pair of fragments, and its answer is read exactly as before: SAT means the program is safe, UNSAT means it is buggy.

Relating values across theories

Before any clause can be moved between fragments, the two theories need a common vocabulary of values. A bit-vector of width 4 and an integer are different objects, so the framework has to say which integer stands for which bit-vector.

Definition

Domain transformer. Every bit-vector variable is associated with an integer counterpart, and an injective map sends each bit-vector value to an integer. Injectivity matters: two different bit-vectors must never collapse onto the same integer, otherwise precision is lost at the very first step. The deck names the two natural choices, unsigned and signed, which differ in how they read the top bit.

Definition

Theory transformer. A map that takes every quantifier-free bit-vector formula to a quantifier-free integer formula, so that the two formulas agree on the restricted bit-vector domain. Informally, writing α for the domain transformer and T for the theory transformer, what is required is

for every assignment σ of bit-vector values:  σ ⊨ φ  ⇔  α(σ) ⊨ T(φ)

Agreement is only demanded on integer assignments that come from bit-vector ones, which is why the encoding later has to add explicit domain restrictions. The transformer in the other direction, from integer formulas to bit-vector formulas, is defined dually.

For the direction from bit-vectors to integers, the paper does not invent a translation. It adopts int-blasting, from Yoni Zohar and co-authors (VMCAI 2022), which turns a QF_BV formula into a QF_IA formula that keeps the exact machine semantics by inserting modulo operations. The single change reported on the slide is that int-blasting is extended to support signed domain transformers as well, which means adjusted domain restrictions and explicit signed to unsigned conversions.

The direction from integers to bit-vectors is the one the authors had to build themselves, and it is where the interesting difficulty appears. The obvious approach is syntactic substitution: replace each integer variable by its bit-vector counterpart and each integer operation by the corresponding bit-vector operation. This is unsound as it stands, because bit-vector arithmetic overflows and integer arithmetic does not. The deck's example shows an integer assignment that satisfies the integer formula, while the matching bit-vector assignment fails to satisfy the translated formula, purely because an intermediate result wrapped around. The fix is to give the arithmetic enough room: sign-extend the variables and the constants by the minimal width that makes overflow impossible, and the translated formula is then satisfied by the matching assignment.

The shape of the overflow problem, on concrete numbers

Take signed 4-bit vectors, whose values run from -8 to 7, and the integer constraint x + y > 8. The integer assignment x = 5, y = 5 satisfies it, since 10 > 8. Substitute naively into bit-vectors of width 4: the bit-vector addition of 5 and 5 wraps to -6, and -6 > 8 is false, so the translated formula rejects an assignment that the original accepted. Widening the addition by one bit before comparing removes the wrap, and the two formulas agree again. This is the deck's phenomenon on numbers of our own choosing; the slide states it with its own example.

The theory-modular encoding in four steps

With the transformers in place, the encoder can rewrite one CHC system modulo BV into a pair of fragments. The deck presents this as four steps, and both lectures walk through the same worked system.

Split the clauses into two groups. Nothing is translated yet, only sorted. The heuristic printed on the slide is: a clause whose function applications are purely arithmetic goes to the integer fragment. Everything else, in particular any clause that uses bit-level operations such as masks, shifts or xor, stays in the bit-vector fragment. In the paper's benchmarks this cuts exactly along the seam of the programs, since they are bit-manipulation routines composed with plain counting loops.

The clauses that stayed behind keep their theory and their constraints untouched. The only change is predicate renaming: each predicate is replaced by its bit-vector copy. After this step a predicate that is used on both sides of the partition exists as two distinct symbols, which is what makes the two fragments separate problems that a solver can attack independently.

Four changes are applied to the clauses that moved. Predicate renaming, as above, but to the integer copies. Variable renaming: each bit-vector variable is replaced by its integer counterpart. Constraint translation: each constraint is passed through the theory transformer, so a QF_BV constraint becomes a QF_IA one. Domain restrictions: each integer variable is confined to the image of the domain transformer, so it can only take values that a w-bit vector can actually represent.

The translated constraints are heavy, because int-blasting protects every operation with a modulo and with uts conversions (uts is the unsigned to signed conversion the translation uses). The deck adds an optimization: eliminate the modulo and uts operations wherever the encoder can already see that overflow is impossible. What is left is the plain arithmetic that the integer solver is good at, which is the whole point of moving these clauses to the integer side.

The two fragments would now be unrelated problems. The last step adds, for every predicate whose two copies are both in use, a constraint tying them together through the domain transformer, so that a fact about the integer copy is a fact about the bit-vector copy and the other way round. These constraints are the only place where the fragments meet, and they are what makes the pair equivalent to the original system.

What counts as a theory-modular solution

Splitting the system changes what a derivation looks like. In the single-theory setting of the previous section, a derivation is a tree built from clauses, and the system is unsatisfiable exactly when some derivation violates the query. Here a derivation may start in one fragment and continue in the other. The deck marks the steps of such a derivation as local when the fragment produces the fact itself and external when the fact arrives from the other fragment across the interface.

A solution is defined to match. A theory-modular solution is a pair of interpretations, one per fragment, that satisfies two conditions: local satisfaction, meaning each interpretation satisfies all the clauses of its own fragment, and interface constraint satisfaction, meaning the two interpretations agree wherever the interface relates them. Neither condition alone is enough. Local satisfaction on its own would let the two fragments believe contradictory things about the same predicate.

Key idea

Correctness of the encoding. Let S be a set of CHCs modulo BV and let S' be a theory-modular encoding of S. The theorem states that S is satisfiable if and only if S' is satisfiable. The deck adds one more remark that is easy to miss and matters a lot in practice: the decidability of CHC satisfiability modulo BV is not compromised by the transformation. Nothing is given away for the speed, and no answer needs to be double checked against the original system.

MosaicSolve, the theory-modular solver

The second half of the work is the solver. MosaicSolve does not solve the fragments itself: it calls an ordinary CHC satisfiability oracle for each theory, one for CHC modulo BV and one for CHC modulo IA, and its job is to coordinate them. The difficulty it has to manage is that neither oracle can see through the interface. When the bit-vector oracle reasons about a shared predicate, part of the truth about that predicate is produced on the integer side, and vice versa. The deck calls this the external semantics of an interface predicate, and MosaicSolve approximates it from both directions while it searches.

State componentWhat it holdsWhat it is for
proof obligationspairs of a predicate p and a formula, asking whether some tuple derivable for p satisfies that formuladrives the search
under-approximation lemmasfacts that certainly do hold of the external semantics of an interface target predicatefind real counterexamples
over-approximation lemmasfacts that bound the same external semantics from aboveblock infeasible counterexamples and detect convergence

The search itself is a small set of moves on that state.

  1. Query. Take an obligation that cannot be resolved with what is known. Call the CHC oracle of the fragment that owns the predicate. If the answer is UNSAT with a refutation whose leaf is an interface predicate, that leaf becomes a new obligation for the other fragment, and it is added to the obligation set.
  2. NegAnswer. If the oracle answers SAT with a solution, the obligation cannot be met with the current knowledge. Remove it from the obligation set and record the solution as a new over-approximation lemma.
  3. PosAnswer. Dually, if the current under-approximations already justify an obligation, discharge it positively and record a new under-approximation lemma.
  4. Sat / Unsat. Stop as soon as the initial obligation is resolved. Resolved negatively means no query violation is derivable, so the system is satisfiable and the program is safe. Resolved positively means a real derivation of a query violation exists, so the system is unsatisfiable and the program is buggy.

The two guarantees are stated together at the end. Soundness: if MosaicSolve returns SAT then the original system is satisfiable, and if it returns UNSAT then the original system is unsatisfiable. Termination: MosaicSolve is guaranteed to terminate provided every single invocation of the underlying CHC satisfiability oracles terminates. That is a conditional guarantee, and honestly so: CHC satisfiability is undecidable in general, so the coordination layer promises only that it adds no new source of divergence of its own.

What the experiments report

The implementation is a prototype built on top of Z3, with Spacer instantiating both CHC satisfiability oracles. The benchmarks are 11 small programs taken from the "Bit Twiddling Hacks" collection by Anderson (Stanford), each composed with simple arithmetic loops, so that every benchmark genuinely mixes bit manipulation with counting. Each program is run at increasing bit-widths under a two-hour timeout, and three configurations are compared.

The results table reports, for each benchmark and configuration, the maximal bit-width reached within the budget and the runtime, with the largest width in bold. The claim the deck makes from it is stated in one line, and it is worth repeating with its qualifier intact: BV+IA achieves the largest bit-width on most benchmarks, often by a substantial margin. Not on all of them, and the summary is about how far the width can be pushed rather than about raw speed at a fixed width.

Careful

This is a prototype evaluated on 11 small programs that were built to have exactly the mixed shape the method targets. That is the right first experiment for the idea, and it is fair evidence that the partition pays off when a program really does contain both kinds of reasoning. It is not yet evidence about large code bases, nor about programs where the seam between bit-level and arithmetic reasoning is less clean.

Conclusion and where the series goes next

The closing slide names the three ingredients in the order the lectures built them. Theory transformations: translations across theories that preserve the represented bit-vector semantics. Theory-modular encoding: the decomposition of one clause set into fragments plus interface constraints. Theory-modular solving: coordinated reasoning across the fragments through per-theory oracles. The reported outcome is substantial scalability improvements on bit-precise verification benchmarks. Two directions are listed as related and future work: abstraction refinement for theory-modular CHC satisfiability, and extending theory-modular reasoning to further background theories, with linear and nonlinear integer arithmetic named as the next pair.

The rest of the third lecture leaves Mosaic behind and opens the first application of CHCs in the series: condition synthesis realizability, from "Condition Synthesis Realizability via Constrained Horn Clauses" by Bat-chen Rothenberg, Orna Grumberg, Yakir Vizel and Eytan Singher (NFM 2023). The problem there is a partial program with holes in its conditional branches, and the question is whether the holes can be filled so that the assertions hold. The algorithm, COSYN, is aimed in particular at proving unrealizability efficiently, which it does by searching for a doomed initial state, one that reaches an error on every run no matter how the conditions are filled in, and that search is again reduced to constrained Horn clauses.
