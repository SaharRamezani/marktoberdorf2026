Scenario-Based Testing of Autonomous Driving Systems

Lecture by Alexander Pretschner (Technical University of Munich, fortiss, bidt). Companion slides: Scenario-based Testing, the second of two decks.

The first deck built up defect-based testing for ordinary software. This one asks what changes when the system under test is a car. Three things change at once: the system is a controller in a closed loop with a physical world, so an input is not something you can fix and replay; the components that interpret the world are learned, so there is no specification to test against; and the input space is enormous while the number of runs you can afford is small. The storyline has two halves: generate good system test cases from a catalogue of scenario types, by turning each type into a search problem over its parameters, and then ask where the catalogue comes from, by deriving parameterized scenarios from recorded drives.

A closed loop, not a program you can replay

The starting picture is the standard control loop. The controller receives the difference between a desired value r(t) and the sensor measurement of the actual value, that is the error e(t), and computes an actuator value u(t) from it. The plant, meaning the physical part, maps u(t) to the actual value y(t) while an environmental disturbance d(t) also acts on it. The sensor observes y(t) and feeds its measurement back. In the deck's air conditioning example, the error is the difference between desired and measured room temperature, and the actuator value is how far the valve for the cooling liquid opens. The failure model behind this view is from Holling and Pretschner, Failure Models for Testing Continuous Controllers (2016).

Because physics is in the loop, the tests run in a simulation environment. The deck orders the X-in-the-loop setups by how much of the real system takes part: model-in-the-loop runs a model of the system, software-in-the-loop the actual software, hardware-in-the-loop adds real parts such as the mechanical steering, and vehicle-in-the-loop puts the whole car in. The point of the ladder is to raise realism step by step.

Testing a system that has no specification

The next problem is the oracle. For components built by machine learning there is, by the method used to build them, no specification: training data plays the role that a requirements document plays elsewhere. The specification has to be reverse engineered, and the deck reverse engineers it from behaviour in traffic scenarios: no crash, and follow the traffic rules including the informal ones. Everything that follows makes those two informal sentences precise enough for a machine to search for counterexamples.

Why there are no regression tests for closed-loop systems

This is the deck's most striking claim, and it is worth taking slowly. In ordinary software a regression test is a recorded input plus an expected output. You replay it after every change, and if the output moves you know something broke. The replay works because the input is independent of the program: the program cannot influence what it is fed.

In a closed loop that independence disappears. Suppose the test asks whether the ego vehicle e keeps a sufficient distance to the surrounding cars while it changes lane. Version e1 performs the lane change and violates the distance to car c1, so the test fails and the system is corrected. Version e2 is run on the same recorded scenario and does not even change lane there. The test now passes, but for the wrong reason: it no longer exercises the behaviour it was written for. The recorded trajectories of the other cars were reactions to what e1 did, so replaying them against e2 produces a situation that is consistent only by accident.

Careful

One concrete test case can be good for one system and bad for another, so re-use of concrete scenarios is essentially random. That is the conclusion of Hauer, Pretschner and Holzmüller, Re-Using Concrete Test Scenarios Generally Is a Bad Idea (IEEE IV 2020). Test cases therefore have to be generated again for every new version of a subsystem.

What counts as a good test case here

A test is an input plus an expected output plus the infrastructure conditions needed to run it, and the expected output is the part that needs a specification. The criterion from the first lecture stays: a good test case reveals potential faulty behaviour with good cost effectiveness. Translated with the notion of a safe operating envelope, which the deck aligns to Koopman's Challenges in Autonomous Vehicle Testing and Validation (2016), a good test scenario is one in which a correct system approaches the limits of the envelope and a faulty system violates them. A scenario in which every plausible system stays comfortably inside teaches nothing, and neither does one in which every system crashes.

Why not sample at random? Testing usually partitions the input domain and samples from each block, and depending on how failing inputs are distributed, random testing does better, worse or the same. The value of partitioning lies entirely in choosing the blocks in a risk-based manner, from a defect hypothesis together with harm and likelihood. Scenario types are those blocks. They are chosen not because a defect is suspected in each of them, but because they occur frequently in traffic, which is a risk argument; the extreme instances inside a block, which the search will hunt for, are limit tests and therefore defect-based. Keeping the blocks explicit also serves the traceability that regulation demands.

Scenario types, operational design domains and logical scenarios

The deck gives the small pictures of traffic situations a formal reading. Env is the environment, a function from time to the (x, y) positions of each of the n non-player characters, meaning the other vehicles and the people around the car. Bhv is the ego vehicle's own behaviour over time. A functionality such as lane following is defined only for some environments; that subset is the operational design domain, and it gives rise to a desired target behaviour.

Env : ℝ → (ℝ × ℝ)n    Bhv : ℝ → ℝ × ℝ    ODD ⊆ Env    Trg ⊆ Bhv
Definition

A logical scenario, also called a specification scenario, is the specification of a function ODD → Trg, including the ranges of all possible parameters in the ODD. Scenario-based testing then means, first, to partition Env into several ODDs, and second, to partition the ODD of a given driving function and to search inside each block for the limit values that produce a crash or come close to one. The terminology follows Bagschik, Szenarien für Entwicklung, Absicherung und Test von automatisierten Fahrzeugen (2017).

The search formulation

Once a scenario type is written down with parameter ranges, a concrete test case is a point in a box of numbers. The running example is a lane change on a three lane road, a simplified ten dimensional space of test cases. Two things are true of that space: not every point in it is a test case of the desired form, because a random parameter vector may produce a run in which nobody changes lane, and not every point of the desired form is a good test case, because most of them are harmless.

Both observations are handled by writing test generation as an optimization problem, in which good simply means optimal. For the lane change the deck states the objectives as a conjunction: a lane change of e behind c, a simultaneous lane change of c, a lane change of c behind e, and on top of these the search for an envelope violation. The first group makes sure the run really is an instance of the intended scenario type; the last one makes it a limit test. The contribution claimed here is the methodology together with a set of fitness function templates, from Hauer, Pretschner and Holzmüller, Fitness Functions for Testing Automated and Autonomous Driving Systems (SAFECOMP 2019).

The deck shows both outcomes on one scenario. In the unsafe run the ego car is responsible for the collision because it did not brake fast enough, and the allowed braking distance is violated by 3.49 m. In the safe run it needed 0.37 m less braking distance than allowed. Both results are one signed number on the same scale, and that number is what makes a search possible at all.

Take one logical scenario from the catalogue, for instance the lane change on a three lane road. Its parameter ranges define the search space, a box of about ten dimensions here.

A point in that box is a concrete scenario: initial positions, initial speeds, accelerations and the times at which the other cars start their manoeuvres. Nothing about the ego trajectory is fixed.

Run the system under test in the loop with that world, at whatever level of realism the setup offers. The ego trajectory comes out of the system; it is not stored in the test case.

Evaluate the objectives on the resulting signals. One part asks whether the run really is an instance of the scenario type, for example whether both cars changed lane in the intended order. The other measures how far the run is from leaving the safe operating envelope, as a signed margin.

The optimizer keeps the better candidates and derives new parameter vectors from them. Because the margin is a number and not a yes or no answer, the search can see which candidate came closer and move that way.

Stop at a violation or when the budget runs out. A violation reveals a problem in the car. No violation after a serious search is also useful, since the tests were aimed at potential defects.

The optimizer, and what heuristic search does not promise

The stepper says the optimizer keeps the better candidates and derives new ones from them, which leaves open what does the deriving. In the lecture it is ordinary heuristic search, and three families were named. Hill climbing is the simplest: hold one candidate, look at the values next to it, move to a neighbour that scores slightly better, and repeat until nothing nearby improves. A genetic algorithm keeps a population rather than a single point. Every candidate is executed, meaning the scenario is simulated and its robustness or its actual distance to the other car is measured, the better ones are selected, modified and re-run, and the process repeats for a number of generations fixed by the budget rather than by any stopping criterion. Simulated annealing sits between the two, occasionally accepting a worse candidate so that the search can climb out of a hollow it has fallen into.

What matters here is not the mechanics of the three, which are standard, but the price. None of them guarantees anything. Hill climbing returns a local optimum at best; the other two return whatever the budget allowed them to reach. There is no statement of the form: after this many simulations, no envelope violation exists in this scenario type. This was put squarely on the debit side of testing, and it compounds an existing debt. Testing was already incomplete because it samples the input space, and now the sampling itself is steered by a procedure that promises nothing about what it did not visit. There is a practical ceiling too: the dimensionality of the search space has to be cut down to what university hardware can run, while an automotive company can afford larger problems.

Key idea

A test case is good if it provokes a failure, and it is also good if it merely comes close to one. The near miss is not a wasted run. The safe outcome reported earlier, 0.37 m of braking distance left over, found no fault, but it did establish that the system was operating with almost nothing in reserve under the hardest conditions the search could construct. That is a statement about potential defects, which is what risk-based testing is after, rather than a statement about defects already present.

Fitness function templates

Turning the essence of a scenario type into an objective function is the part the deck calls non-trivial, so it offers templates. The foundation is one sentence, that system behaviour must not exceed a safety threshold, and the templates cover the shapes of constraint that scenario descriptions keep reusing.

Testing the safe operating envelope. The requirement is that the ego must not leave it, and the search goal is the negation: find parameters that make the ego leave it. This template carries the pass or fail verdict.

Qualitative goals of the form: a value at a time has to be within a certain range. Template 2a says the ego car should be in between the other cars, template 2b that another car should be in front of the ego car. These describe the situation that must arise for the run to count as an instance of the scenario type, not a failure.

Timing constraints, for example that both cars should change onto the middle lane simultaneously. Without one, the optimizer would satisfy the location constraints in some order that has nothing to do with the intended traffic situation.

Several templates apply to one scenario, so their values must be combined. A single-objective optimizer folds them into one number; a multi-objective optimizer keeps them apart, as the vector of the four goals of the lane change example.

The recipe generalizes. For intersections the goal becomes a left turn of the ego before another car, combined with a search for an envelope violation in the longitudinal and the lateral direction, following Kolb, Hauer and Pretschner (ITSC 2021). Two pitfalls are named: there is at least one search problem per scenario type, so the cost depends strongly on how finely the catalogue is cut, and one separate search problem per safety criterion, since searching for a longitudinal and a lateral violation at once is called explicitly not useful.

Revisiting re-use: three systems, three worst cases

The claim that re-use does not work is backed by an experiment on a real trajectory planner, an approach developed at Volvo Cars and described by Nilsson, Lane Change Maneuvers for Automated Vehicles (2017).

  1. Predict the positions of the other cars.
  2. Determine the safety corridor, that is the safe operating envelope, using safeDistEstimation = max{ε, τ · v}, so a fixed floor ε together with a term that grows with speed.
  3. Compute an optimal trajectory inside that corridor by minimising a weighted cost.

Three variants were tested, each time by searching for a collision with vehicle c1. System A is the baseline. System B is A with a larger required safety distance in the planner. System C is B with a reduced proportional gain of the PID controller, a change meant to make the control smoother. The search found a safety distance violation for A, because the planner did not keep enough distance. On B it found none, so the system was assumed correct. On C it found a violation again, for a completely different reason: the tracking is now too slow. A change made for comfort reintroduced a safety problem one layer below the one that had been fixed.

Each system produced its own worst case scenario, including the parameters of the other cars, and these three concrete scenarios were then run against all three systems. The numbers are signed margins, and a negative value means the safety distance was violated.

Read the rows. Scenario A, the worst case found for the faulty baseline, is devastating there and still harmful on C, but on B it leaves a comfortable margin. Scenario C leaves more than 20 units of margin on A and B, so as a test for those systems it is close to worthless, even though A is known to be faulty. Worst case scenarios are system specific.

Regenerating everything for every commit is too expensive for continuous integration, so the deck offers a way out based on a simple intuition: the best test for the new version will differ from the best test for the old one, but probably not by much. The best test case of the previous version therefore becomes the initial seed of the heuristic search instead of a random seed, with a reported reduction of roughly 70% in effort (Kolb and Pretschner, submitted 2024). Note what this preserves: the old test case is re-used as a starting point for a search, never as a verdict.

Signal temporal logic as the specification language

Fitness function templates run into limits once requirements get richer. Comparing timed events requires stacking several templates, only specific time points can be evaluated rather than a signal as a whole, comfort and efficiency are hard to express, and actual traffic laws are hard to encode. The deck's example of a rule that resists them is the German regulation for stop signs: a driver must stop and give way; must not stop up to 10 metres in front of the sign if that would conceal it; and, if there is no stop line, must stop where the view of the other road is unobstructed.

Signal temporal logic (STL) is introduced as a language that can state such rules. It is a logic over time-series data with the usual operators and, or and not, plus operators that talk about time: eventually (F, written ◇), always (G, written □) and until (U), with implication derived as usual.

φ ::= ⊤  |  μ ≥ 0  |  ¬φ  |  φ1 ∧ φ2  |  φ1 U[a,b] φ2
φ1 ∨ φ2 = ¬(¬φ1 ∧ ¬φ2)    ◇[a,b] φ = ⊤ U[a,b] φ    □[a,b] φ = ¬◇[a,b] ¬φ    φ1 ⇒ φ2 = ¬φ1 ∨ φ2

The core of the semantics is the predicate case: a signal s at time t satisfies μ ≥ 0 when μ applied to the value of the signal at that time is greater than zero, so non-positive values indicate a violation. The formula ◇[a,b] φ holds at t when φ holds at some time in the interval [t+a, t+b], and □[a,b] φ holds at t when φ holds throughout it. The window slides with t, which the deck shows by evaluating one formula at two times on the same signal: ◇[1,3](x > 2.5) is false at t = 0 and true at t = 3. Until is the primitive the other two come from: φ1 U[a,b] φ2 holds at t when there is a time t' in [t+a, t+b] at which φ2 holds, and φ1 holds at every time from t up to t'.

Nesting is where the expressiveness comes from. For a temperature that must rise above 50 degrees within the next 10 seconds and then stay above 50 for at least 5 seconds, the deck writes ◇[0,10](□[0,5](T(t) > 50)). The same pattern, an eventually wrapped around an always, is what the stop sign needs.

f1 = (signAhead.type == stop) ⇒ ◇[0,2](□[0,3](speed == 0) ∧ stoplineAhead)
f2 = (signAhead.type == stop ∧ signAhead.distance ≤ 10 ∧ concealedByEgo) ⇒ speed > 0
f3 = (signAhead.type == stop ∧ ¬stoplineAhead.exists) ⇒ ◇[0,2](□[0,3](speed == 0) ∧ intersectionAhead)
ffinal = □(f1 ∧ f2 ∧ f3)

Each legal sentence becomes one implication, and the whole rule is the always of their conjunction, so it must hold at every moment of the drive. The three second window inside f1 and f3 reflects the recommendation to stand still for three seconds, and f2 reads: if a stop sign is closer than 10 metres and the ego would conceal it, the ego must be moving. A second example encodes the yellow light rule, that a car whose remaining braking distance is too short should cross the intersection, parameterized by the reaction time tr and the deceleration a.

Quantitative robustness, the bridge to search

So far STL only says whether a signal violates a formula. An optimizer needs more: it has to compare two runs and know which came closer to the boundary. That is what the robustness value provides. A formula evaluated on a signal returns a real number whose sign is the verdict and whose magnitude is the margin, for instance how close the run came to the speed limit. Of two candidates with robustness R1 > R2, it is R2 that gets kept and mutated to find more critical tests.

If you are supposed to drive 60 kilometres per hour and you drive 61, that is not that bad. It is worse if you are driving 100 in a 30 zone. We somehow want to distinguish between the different severities of violations, and this is where robustness comes into play.

Alexander Pretschner, motivating the quantitative semantics

That is the whole argument for leaving the boolean world behind. A yes or no verdict puts both of those drivers in the same bucket, labelled violated, and discards exactly the information a search needs in order to know which way to move. The quantitative semantics keeps it. Instead of asking whether a formula holds on a trace, it asks to what extent the formula holds, and answers with a real number: the sign still carries the classical verdict, so nothing is lost, and the magnitude supplies the gradient.

Key idea

Robustness is defined by recursion over the formula, and each connective becomes an arithmetic operation. The predicate contributes the raw signed quantity, negation flips the sign, conjunction takes the minimum, disjunction the maximum, always the minimum over the time window and eventually the maximum over it. This is what turns a specification into a fitness function.

ρ(s, t, μ ≥ 0) = μ(s(t))     ρ(s, t, ¬φ) = −ρ(s, t, φ)
ρ(s, t, φ1 ∧ φ2) = min(ρ(s, t, φ1), ρ(s, t, φ2))     ρ(s, t, φ1 ∨ φ2) = max(ρ(s, t, φ1), ρ(s, t, φ2))
ρ(s, t, ◇[a,b] φ) = maxt' ∈ [t+a, t+b] ρ(s, t', φ)     ρ(s, t, □[a,b] φ) = mint' ∈ [t+a, t+b] ρ(s, t', φ)
ρ(s, t, φ1 ⇒ φ2) = max(−ρ(s, t, φ1), ρ(s, t, φ2))

Two remarks make this less mysterious than it looks. The first is that the base case is pure convention. Nothing in the mathematics forces μ ≥ 0 to be the satisfied side; the sign of the underlying function could have been read the other way round, and the lecture is explicit that this is a stipulation and nothing more. Once it is fixed, every other line is forced. Negation must flip the sign, because a robustness value is a signed real and negating a formula negates how well it is met. The second remark is that the minima and maxima above are the finite-trace reading of an infimum and a supremum. The general definition takes inf and sup over the time window, which matters if you treat time as dense; for the finite, sampled traces a simulation actually produces, the two coincide and you may read every rule as a plain minimum or maximum over the sample points.

Reading the rules, and one word of caution on until

A conjunction is only as robust as its weakest part, which is why min is right: a run that satisfies one clause by a wide margin and another by a hair is close to failing. An always over a window is a conjunction over all its time points, so it is a minimum too, and an eventually is a disjunction over the window, so it is a maximum. Implication follows from its definition as a disjunction with a negated left side. For until, the robustness takes the best time point at which φ2 becomes robustly true, limited by how robustly φ1 held before it. The printed rule on the slide repeats φ2 in the inner minimum, which does not match the other operators, so read that inner term as the robustness of φ1.

The definition has an obvious limitation, and he raised it as soon as he had finished deriving it: the number it returns is anchored at a single moment in time. Whatever the formula, the recursion eventually bottoms out in one worst sample, and everything that happened around that sample is discarded. He made the point with two traces drawn against the same reference line, where the requirement is that the signal must not fall below it. The first dips once, sharply, and touches minus one. The second sits below the line for a long stretch, and its worst point is also minus one. By any engineering standard those two runs are not equally bad, but the robustness value cannot separate them: both score minus one.

That phenomenon is called pointwise masking, and it is the clearest of the three weaknesses the deck names, since always is a minimum and a minimum forgets duration. The other two are the loss of information once signals leave the range of interest, and input signals masking output signals. The fixes are alternative definitions: generalized mean robustness (Mehdipour, Vasile and Belta, IEEE Transactions on Automatic Control, 2025), and duration robustness with duration-severity robustness, which combine the severity and the length of a violation (Finkeldei, Wolf, Weghorn, Pretschner and Althoff, ITSC 2025).

The summary is balanced. STL gives a formal way to specify spatio-temporal relations between continuous signals, and robustness turns those formulas into fitness functions. But there is not one notion of robustness, there are many, and the choice encodes a judgement: is violating a rule once as bad as violating it over a long period? Which measure to pick is therefore context specific. It cannot be settled up front and there is no universally correct answer, only measures that are more or less adequate to the situation being tested, so the choice has to be made and defended per requirement. The same machinery also serves to evaluate large amounts of recorded driving data and to state motion planning goals such as □(◇(reach a gas station)).

Completeness, and completeness of what

Two things are now settled: tests must be regenerated per version, and given a scenario type we know how to derive good instances of it, by translating the essence of the type into an optimization problem and searching for envelope violations. The open question is whether the list of scenario types is complete.

The deck refuses to treat that as one question and splits it into six: completeness of the scenario types with respect to reality; of the tests with respect to one scenario type; of the scenario types with respect to recorded data, marked as a purely statistical argument, following Hauer, Schmidt, Holzmüller and Pretschner, Did We Test All Scenarios for Automated and Autonomous Driving Systems? (ITSC 2019); of clustered data with respect to expert-defined scenario types; of the scenario types with respect to granularity, since a coarse catalogue is complete more easily and says less; and of the data with respect to reality.

Key idea

Only some of these are answerable. A statistical statement about recorded drives is a statement about the sample, not about the world: it can say how likely it is that the next drive contains a scenario type not seen before, but it cannot certify that reality holds no surprises. The last item, completeness of the data with respect to reality, has no formal answer at all.

This is where recorded drives earn their place. They are useless as concrete regression tests, as the first half of the deck argued, but they are good for building the catalogue: clustering transforms recorded drives into scenario types, and the resulting clusters are compared with the hand-crafted scenario types written by experts. A cluster with no counterpart in the catalogue is a situation the experts did not think of, and a catalogue entry with no cluster behind it is either rare or wrongly imagined. The meaning of a cluster matters as much as the count: it is usable as a scenario type only if a human can say which traffic situation it stands for, which is also what regulation requires.

Why drones are harder than cars

Everything up to this point assumed that a catalogue of scenario types exists and that the only open question is whether it is complete. For highway driving that assumption is defensible. Domain experts have agreed on a set of roughly fifty scenario types considered the relevant ones, plus a few special situations, and everyone involved has an intuitive picture of what a cut-in or a lane change is. The catalogue gives the input space a structure the search can exploit, because each type arrives with its own parameters and its own idea of what makes an instance interesting.

For an unmanned aerial vehicle none of that exists. Regulation is thinner, expert agreement is absent, and the honest answer to the question of what the relevant scenario types are for a drone is that nobody knows. There is empty space, and there may be a tree. The parameterization therefore has to be built one level lower, out of geometry. You generate a set of obstacles distributed in space, decide for each whether it is static, a tree, a flag pole or a building, or dynamic, another drone or a bird, and decide how many of each there are. Which of those combinations is critical is not known in advance, which is exactly why it is handed to the search. The safety property survives the move even though the catalogue does not: you may not know what minimum separation a regulator would demand of a drone, but hitting an obstacle is unambiguously something you would deem problematic, so there is still an envelope to aim at.

The system under test is an autopilot in the plain sense: you give it a target coordinate and it flies there with obstacle avoidance, going around whatever it detects. The results reported for PX4 are not flattering, with hundreds of severe situations found by these methods. Two observations from the drone work generalize beyond drones. The first is about combination. A drone has a small number of well-defined failure modes, and injecting them one at a time already exposes problems; combining the geometric scenario types with those failure modes pairwise multiplies the number of situations in which the object detection module is caught out. The second is about what counts as a finding. The most instructive outcome shown was not a crash. The drone was supposed to hold an altitude and pass between obstacles, and instead it dove down through a gap and climbed back up on the other side. Nothing was hit, so a crash-only oracle would have recorded a pass, yet the path is plainly questionable. That is the same argument as the safe operating envelope, one level up: the interesting verdict is usually about margin and intent, not about impact.

Generating attacks instead of accidents

The last example points the same generation machinery at security rather than safety, and it is worth reading in terms of what the attacker controls and which assumption breaks. The driving function is lane keeping, and its inputs are the lane marking and the steering wheel angle, both read off the vehicle bus. At least in the vehicle generation used here, the signals on that bus are neither encrypted nor signed, for the usual reasons in embedded systems, so anything on the bus can be modified. That is the assumption that breaks, and it is an assumption about the bus, not a defect in the driving function.

The warm-up is crude. Inject a wrong steering wheel angle and the car is steered off course, first in software-in-the-loop and then on a real car. The objection to that experiment came immediately, and the lecture raised it before the room could: an intrusion detection system that watches the physical process spots something that blatant at once. A steering wheel that appears to jump ninety degrees to the right is not a subtle event.

So the follow-up experiment put an intrusion detection system into the setup and asked the search for an injection the detector would not flag, by shaping the trace of the injected signal rather than by increasing its size. What makes that possible is a property of the system being attacked rather than a weakness in any particular detector. A lane keeping function is never still. Because a car never travels perfectly straight, the function issues continuous small corrections, a little to the left, a little to the right, and the detector has to accept that traffic as normal. Small malicious corrections are therefore hard to tell from ordinary ones. The attack the search settled on is to pretend the steering wheel was not moved at all: the reported angle stays constant while the wheel actually moves, so the function overcorrects and the car begins to oscillate. The point stressed in the deck is that this was found by a machine and not by a human.

Two caveats were attached on the spot. A person in the car eventually notices, because the car starts moving in a slow snake and a driver realises something is wrong even though the detector never fires, so the attack buys time rather than invisibility. And evaluating intrusion detection systems of this kind was described as a nightmare, because there is no agreed benchmark to evaluate them against. The strongest available claim is that this detector did not catch this generated attack, which says something about one pairing rather than measuring detector quality in general. That is the same epistemic position as the rest of the lecture: the method yields sharp, specific evidence, and declines to promise more than it has.

Discussion and conclusions

The closing list is partly a summary and partly a set of open problems. Virtual testing is mandatory for these systems. Scenarios define spatial and temporal constraints, encoded either directly in fitness function templates or as STL formulas whose robustness is the fitness, so the quality of a test is expressed as the optimization goal itself. There is in general no re-use and no regression testing, so tests are regenerated, which is expensive, and the effort can be cut by clever seeding. Completeness of the scenario types stays open, and two topics were left out entirely: the gap between simulation and reality, and scalability.

One warning belongs to the search itself. Heuristic search gives no global optimum, and the difference is not academic: testing the PX4 autopilot for drones with different combinations of optimizers produced outcomes as different as crash and no crash for the same system. One algorithm cannot be trusted, and there is no best combination to fall back on either. The tool is StellaUAV, from Schmidt and Pretschner (ISSRE 2022, pages 37-48).
