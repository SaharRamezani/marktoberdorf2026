Architectures for AI Systems: Prompting, Retrieval and Agents

John C. Mitchell, Stanford University. Deck: Evaluation and Security of AI-based Systems, day 2.

A model on its own answers one question at a time. A deployed system wraps the model in machinery: a fixed system prompt, a retrieval step, a set of tools, a planner, a loop. This session walks up that ladder of architectures, from plain prompting to retrieval augmented generation to agentic systems, and asks two questions at every rung. What can be measured at each point in the pipeline, and what does the new machinery hand to an attacker? The session ends with the classical way of writing down a threat model, which is the setup for prompt injection.

Prompt-based systems

The simplest architecture is a conversational read and respond loop . The application holds a conversation history. When the user types something, the application appends that text to the history, sends the whole history to the model, receives a response, and appends the response as well. In front of the history sits a system prompt written by the application developer. Its job is to define the scope of the conversation and to state the restrictions, the so called guardrails, that turn a general model into a chatbot, a tutor or a therapist assistant.

Two things matter here. First, the system prompt and the user text end up in the same place: they are concatenated into one sequence of tokens, and the model has no separate channel marking one as authoritative and the other as untrusted. Second, the only place the developer can intervene is the text itself, since there is no code path to constrain and no schema to validate.

The deck then shows three prompting patterns that improve accuracy without touching the weights. Chain of thought prompting gives the model an example question with a worked step by step answer, and only then asks the question of interest, so the model continues in the same style . Self consistency samples several chains for the same question and takes the answer that appears most often, on the assumption that a correct answer can be reached by several routes while errors scatter . Both are illustrated with figures from Wang et al. (2022). Subquestion reasoning, also called least to most prompting, breaks the problem into simpler subquestions and solves them in order, feeding earlier answers into later ones, following Zhou et al. (2022) .

The trust picture for prompting is short . Untrusted user input is passed to a model. Jailbreaking is the attempt to subvert restrictions that the application added in its system prompt. Model output is returned to the user, which can leak information and compromise privacy. Alignment properties such as freedom from bias and cultural sensitivity are hard to guarantee, because nothing in the architecture enforces them.

Retrieval augmented generation

Retrieval augmented generation, RAG, adds one component and two steps . The component is a grounding corpus, a document store that the developer controls. The steps are: retrieve passages relevant to the user query, either by vector search over embedded documents or by mapping the prompt to a query and running a traditional search; augment the prompt with those passages, together with instructions that the answer must be consistent with them; and generate the response. The model may additionally be finetuned on prompts in this shape so it uses the supplied passages rather than its own memory.

The motivation is that the corpus can hold what the training set does not: internal documents, current prices, last week's incident reports. The cost is a new failure surface. Retrieval can return nothing relevant, so the model answers from its parameters and the augmentation is decoration. It can return passages that match on the surface but not in meaning, a common effect of embedding search. It can miss a document that does exist, because query and document use different vocabulary. The corpus itself can be stale or wrong, in which case a perfectly grounded answer is still false. And because the corpus may contain proprietary material, a retrieval bug becomes a disclosure bug.

Because the pipeline exposes intermediate objects, it can be evaluated at more than one point. The RAG triad checks the three pairings among input, data store and output . Context relevance asks whether the retrieved context is relevant to the query, which tests the retriever alone. Groundedness asks whether the response is supported by that context, which tests generation alone. Answer relevance asks whether the answer addresses the query, catching responses faithful to a passage but beside the point. The three fail independently, and knowing which edge failed tells the engineer which component to fix.

Definition

An LLM response is grounded in a knowledge corpus if every claim in the response can be attributed to some document in the corpus . The deck follows the attribution measurement work of Rashkin et al. (2023) in Measuring attribution in natural language generation models, Computational Linguistics 49(4).

Groundedness so defined is a claim level property, so measuring it needs a claim level procedure. The corroboration workflow on turns a response into a report that scores each sentence and lists the documents that support it.

A sentence extractor splits the model response into individual sentences, so that each factual claim can be judged on its own instead of the paragraph being accepted or rejected as a whole.

Each sentence is rewritten to stand alone. Pronouns and references such as "it" or "the second one" are resolved, because a checker that sees only one sentence cannot otherwise tell what is being claimed.

A verification check decides which sentences require verification at all. Sentences that state no external fact, for example a restatement of the question or a transition, are passed over.

For every remaining sentence, grounding snippets are pulled from the corpus and a natural language inference model decides whether the snippets entail the sentence.

The output is one line per sentence: the sentence, a score, and the citations that support it. A reader can see which parts of an answer are attributed and which are not.

The trust perspective for RAG is the prompting one plus the corpus . Input checking may be inadequate, and if the input check is itself an AI component then it has exactly the same weaknesses as the system it protects. Data and model outputs both reach the user, and the risk is higher than in plain prompting because the database may hold proprietary information. Against that, the deck makes a constructive point: the RAG triad and the tools growing around it provide testing and assurance, and a structured architecture supports structured engineering practice. More components means more interfaces, and interfaces are where measurement is possible.

Agentic systems: goal, plan, act

An agentic system replaces the single forward pass with a loop . The agent is given a goal, produces a plan, and acts by calling tools. Each tool result comes back into the context and the agent decides what to do next, revising the plan when a step fails, until it declares that the goal is met. The deck's running example is a web research task : "Chart the market cap (in USD) of the top five U.S. banks". It is built on LangGraph state used as memory, a Tavily web search tool for the research step, a Python tool for the charting step, planning done by a planner, reflection performed by the executor and planner, and coordination between them.

  1. Receive the goal, in the example a chart of a quantity that the model does not know exactly.
  2. Plan: decide whether facts are missing or whether clean numeric data is already in hand.
  3. Act: call the search tool for values, or the Python tool to plot values that are already available.
  4. Observe the tool result and append it to the working state, which is the agent memory.
  5. Reflect: judge whether the step moved the task forward, and revise the plan if it did not.
  6. Stop when the deliverable exists, signalled in the example by the prefix FINAL ANSWER.

Two arrangements of the same task are compared. The single agent version uses one model, in the deck an o1 model, with a system prompt that lists both tools, states rules for when each applies, insists that exact numbers must come from search rather than estimation, and finally asks the agent to write a four part self assessment covering summary, strengths, weaknesses and recommendations . The multi agent version splits the work . A shared system prompt tells each agent that it is collaborating with others, that partial progress is acceptable because a colleague with different tools will continue, and that the prefix FINAL ANSWER is the signal for the team to stop. The research agent may only do research and is bound to the search tool. The chart generator may only produce charts and is bound to a Python interpreter tool.

Splitting the roles does not by itself fix coordination. Adding an orchestrator that oversees the researcher and the chart generator produced better observed behaviour and cleaner traces . A concrete failure mode remained: the researcher sometimes hands over without the numeric values that plotting requires. The stated goals are to improve the orchestrator and researcher interaction and to collect failure mode statistics rather than anecdotes. The deck notes that in this line of work, an early collaboration with Snowflake, the component called the executor is more commonly called the orchestrator .

Control topology is the design choice that decides who speaks when . Round robin consults agents in a fixed order set when the system is created, giving a cyclical deterministic network. A central orchestrator knows all the other agents and picks at each step which one acts, giving a hub and spoke non deterministic network. A central orchestrator with external data structures, for example Magentic-One (Fourney et al., 2024), adds an external task ledger loop to keep the system on task. The slide credits these definitions to work by Shmatikov and co-authors, Multi-Agent Systems Execute Arbitrary Malicious Code, whose title already indicates why topology is a security question as well as a performance one.

Components: system prompt, conversation history, model. Flows: user text in, generated text out, both appended to one history.

What can be evaluated: only the input and output pair, since there is nothing in between. Main exposure: untrusted user text sits next to the guardrails, and the output goes straight back to the user .

Components: the above plus a retriever and a grounding corpus. Flows: query to retriever, passages into the prompt, response out.

What can be evaluated: three edges instead of one, so a failure can be assigned to the retriever or to the generator. Main exposure: the corpus enters the blast radius, and it may hold proprietary data .

Components: one model with a tool set, a plan and a working memory. Flows: a loop of tool calls and observations rather than one pass.

What can be evaluated: the whole trajectory, step by step. Simpler to design and maintain, more consistent on narrow well defined tasks, but a single point of failure and limited scalability .

Components: several agents with different tools and prompts, plus a topology that decides who acts next.

What can be evaluated: the same trajectory measures, plus the handovers between agents, which is where the observed failure sat. Scalable and adaptable, tolerant of one agent failing, at the price of coordination cost and communication protocols .

Evaluating agents: the GPA framework

Evaluating a final answer is not enough for an agent, because an agent can reach a right answer through a wrong route that will not repeat, or fail late for a reason introduced early. The framework in the deck attaches measures to the three phases of the loop and calls the result the agent's GPA, for goal, plan and act .

PhaseMeasureQuestion it answers
GoalGoal fulfilment, with answer relevance as a sub-measureDid the run achieve what the user asked for, and does the reply address the request?
Across the runLogical consistencyDo the steps follow from one another without contradiction?
Across the runExecution efficiencyWere there redundant, repeated or wasted steps?
PlanPlan quality, with tool selection as a sub-measureWas the plan appropriate, and were the right tools chosen for its steps?
ActPlan adherence, with tool calling as a sub-measureDid the agent follow its own plan, and were the calls formed correctly?

The reported results are about coverage and about agreement with people . On the authors' test split of the TRAIL/GAIA dataset the framework captures all 281 agent internal errors. LLM judges scoring these dimensions agree with human judgments on 94 percent of those cases, 264 out of 281, against a baseline TRAIL LLM judge at 55 percent, 154 out of 281. On Snowflake Intelligence the agreement is 82 percent on a three point scale and 97 percent on a two point scale. Judges also locate where the error happened, agreeing with human annotations on 85 percent of cases, 240 out of 281, against 49 percent for the baseline. The gap between the three point and two point scales is a reminder that a judge is far better at deciding whether something is wrong than at grading how wrong it is.

The security perspective for agentic systems is the widest of the three . Untrusted user input can be passed on to any application the agent can reach, and data poisoning becomes possible. Among agent actions, one agent can be tricked into corrupting another. The tools themselves, databases and web search among them, make serious breaches possible. And the agent's output returns to the user, so data breaches and information leakage remain in scope.

Prompt optimization and vibe coding

Prompt optimization treats the prompt as the thing to be improved while the model weights stay fixed . What is optimized is the text that the developer controls: the wording of the instructions, the choice and ordering of worked examples, and the way a task is broken into steps. How it is measured is what makes it an optimization at all. There has to be a scoring function, typically a metric over a development set of tasks with known good outcomes, or a judge model producing scores of the kind described above. The loop then proposes candidate prompts, scores them, and keeps what improves the score. Two consequences follow. The result can only be as good as the metric, so a weak or gameable score produces a prompt tuned to the score rather than the task. And the same procedure applies twice over, since the deck notes that prompt optimization is applicable both to the system of interest and to the agents that evaluate it . The optimization slides in this deck are credited to a talk by Lakshya Agrawal, on joint work with a large group of co-authors, and the deck points to a Snowflake engineering write-up on the CoCoEvolve system . The figures on those slides carry no recoverable text, so no detail is reconstructed here.

Vibe coding is the same agent loop applied to software construction, and the deck walks through one session end to end . The developer describes the application to be built and answers the clarifying questions the coding agent asks. The agent proposes a plan, then writes the application and explains how to run it. In this case that meant installing Xcode to build the application and install it on an iPhone, and the agent wrote the instructions for using Xcode as well. The first version had real defects: a button that did nothing and library pictures that were rendered too large. The developer described those defects in plain language, the agent repaired them, and the application worked. The interesting part is where the human sits in that loop. The developer supplies the goal and the acceptance test, and the agent supplies plan and code. Nothing in the loop checks the code except the person running it.

Writing down a threat model

Before naming any attack, the deck sets out the standard recipe for security analysis . It has three parts. First, a system of interest. Second, the desirable properties of that system, usually its intended purpose or function, and often scaled back to the most essential user protections, because defending everything defends nothing. Third, the interface and capabilities of the attacker, which is what the term threat model means. The analysis is then the question of whether an attacker with those capabilities can make the desirable properties fail.

The classical attacker models are all instances of the recipe, differing only in the third part . Honest users interact with the system through the intended interface and get the intended output. A network attacker may intercept and alter traffic but cannot break cryptography. A web attacker sets up a malicious site that the victim visits but has no control over the network. An operating system attacker controls malicious files and applications. The properties at risk are the traditional three, confidentiality, integrity and availability, with the caveat stated on the slide that these are not an orthogonal decomposition and are not necessarily comprehensive .

Direct and indirect prompt injection

Apply the recipe to the architectures above. In every one of them, text that the system did not write ends up in the same context window as the instructions the developer did write, and the model treats the whole window as one sequence. That is the trust assumption the attacks break. The two attack families differ in the attacker's interface, exactly as the network and web attackers differ.

Definition

Direct prompt injection. The attacker is the party talking to the system. The attacker writes instructions into the ordinary user input channel, aiming them at the model rather than at the application. The assumption that breaks is that the developer's system prompt outranks the user turn. Jailbreaking is the case where the objective is to remove restrictions that the application added .

Indirect prompt injection. The attacker never talks to the system at all. The attacker controls content that the system will later read on its own initiative, through a retrieval step or a tool call: a public page, a document that lands in the grounding corpus, a file, an API response, a message from another agent. The assumption that breaks is that retrieved passages and tool results are data rather than instructions. The victim is whoever's session pulls that content in.

The difference matters for who can be attacked and when. In direct injection the attacker and the victim are the same account, so what is at stake is what that account was allowed to obtain: the system prompt, restricted behaviour, whatever the application would not have given willingly. In indirect injection the attacker plants text once and waits, and the harm lands in some other user's session with that user's permissions. This is the same step from web attacker to network attacker in the classical models: a change in interface, not in cleverness.

Careful

These notes describe attacks at the level of interfaces and trust assumptions, which is what a threat model needs. They do not contain payloads or step by step procedures. The point to carry forward is structural: an attacker's reach equals the union of the permissions of every tool the agent may call, not the permissions of the text they managed to plant.

That last point explains why the same weakness grows more serious as the architecture grows. With prompting alone, a successful injection changes one conversation. With RAG, the corpus is inside the reachable set, and the corpus may hold proprietary information . With agents, tools such as databases and web search are inside it as well, one agent can be used to corrupt another, and the output still returns to a user . Each architecture in this session bought a capability by adding a component, and each added component also widened the interface available to an attacker. The next session takes this from definitions to consequences, starting with control flow hijacking.

Why does an input filter built from a model not close the injection problem?

Because the filter is a prompt-based system with the same architecture as the system it protects, so it inherits the same weakness . The filter reads untrusted text and decides what to do with it using instructions written in that same text channel, which is precisely the assumption injection breaks. A filter raises the cost of an attack and is worth having, but it is not a trust boundary in the sense the classical models use the term, because it is not enforced by anything outside the model.
