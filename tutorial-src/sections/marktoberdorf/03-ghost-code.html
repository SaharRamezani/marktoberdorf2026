Programs to the Rescue of Logic: Definitions, Lemma Functions and Ghost Code

Jean-Christophe Filliâtre, CNRS. Deck: The Why and How of Deductive Program Verification, lecture 3.

The first two lectures used logic as a tool for reasoning about programs. This lecture goes in the other direction and uses programs as a tool for building logic. Its three parts build on each other. The first asks how a new symbol such as factorial gets into the logic at all, and why the easy route, declaring it and adding axioms, is the dangerous one. The second introduces lemma functions, where a proof by induction is written as a recursive program. The third introduces ghost code, which exists only for the proof and is erased before execution.

Where logical symbols come from

Specifications and pure code both need logical symbols: constants, functions and predicates. The previous lectures already used 0, + and >, the sum operator over a range, and the helpers odd, half and div. Sometimes the symbol is already known to the prover: SMT solvers include integer arithmetic as one of their built in theories, so on the Why3 side the symbol is only declared and mapped onto the corresponding SMT symbol. No axiom and no definition are needed. 

function (+) int int : int
function (-) int int : int
function (*) int int : int

Even this cheapest route needs care, and division is the standard example. SMT solvers know about division, so div and mod can be declared and mapped onto the solver's own operations. But which division is it: Euclidean, truncated, floored, or something else again? These conventions disagree on negative operands. The advice on the slide is practical: read the SMT documentation, run some tests, and document the choice on the Why3 side. The deck points to the note "Division and Modulus for Computer Scientists" by Dan Leijen.

Careful

The logic of SMT solvers is total, and so is the logic of Why3: every function is defined everywhere on its argument type, so div 1 0 is a valid term of type int. Hence goal G0: div 1 0 = div 1 0 is provable, because equality is reflexive, while goal G1: div 1 0 = div 2 0 is not, because nothing is known about either term. The term exists but carries no information. Other designs are possible, such as a partial logic, or a total logic that fixes x/0 = 0 by definition.

The second route is a definition. When the symbol is just a shortcut, define it and be done:

function half (n: int) : int =
  div n 2

predicate odd (n: int) =
  mod n 2 = 1

This is translated directly into a similar definition in the SMT input. The comment beside these two lines on the slide is a reminder about trust: you have to read the definition, understand it, and accept it. A definition can still say something other than what you meant. What it cannot do is make the logical context contradictory.

Axiomatization and the danger zone

The third route is used when the symbol is neither predefined nor easily definable: declare it and describe it with axioms. For factorial this looks natural. 

function fact (n: int) : int
axiom Fact0: fact 0 = 1
axiom Factn: forall n. n > 0 -> fact n = n * fact (n-1)

The symbol is axiomatized only on nonnegative integers, so nothing is known about fact (-1) or fact (-2): they are legal terms with no properties, exactly like div 1 0 above. On the SMT side the declaration becomes a declare-fun, each axiom becomes an assert, and the goal becomes an assertion of its negation followed by check-sat. 

(declare-fun fact (Int) Int)
;; "Fact0"
(assert (= (fact 0) 1))
;; "Factn"
(assert (forall ((n Int))
  (=> (< 0 n)
      (= (fact n) (* n (fact (- n 1)))))))
;; Goal "G"
(assert (not (= (fact 3) 6)))
(check-sat)

Now change one character: write n >= 0 instead of n > 0 in the second axiom. The result is that goal G: fact 3 = 5 is proved. The two axioms now contradict each other at zero: the recursive one applies at n = 0 and forces fact 0 = 0 * fact (-1) = 0, while the base one says fact 0 = 1. Once the context is contradictory everything is provable, including every other goal in the file. The proof session goes green and means nothing.

SMT solvers are good at finding inconsistencies, which here is not a virtue: they find the contradiction and use it to close any goal you give them. Checking whether a set of axioms is consistent is undecidable in general, so there is no button that answers the question for you.

Key idea

Axioms are not the only way to introduce assumptions. Declaring a program function with val, that is with a contract and no body, is equivalent to an axiom, because the weakest precondition calculus adds the postcondition to the logical context as a usable fact at every call site. The deck's example is bertrand, with requires { n > 0 }, ensures { prime result } and ensures { n < result < 2*n }, marked on the slide as wrong: Bertrand's postulate needs n > 1, since for n = 1 there is no prime strictly between 1 and 2. The contract promises something false, and the prover will believe it.

The deck lists three answers, in increasing order of strength. Proofread the axioms carefully. Try to derive false from them, a practice called a smoke detector. Best of all, replace the axioms with a definition.

The symbol already exists in an SMT theory, so Why3 declares it and maps it onto the solver's symbol. No axiom, no definition, no risk of inconsistency from your side. You still have to check that the solver's semantics is the one you meant, which is the division story.

The symbol is a plain abbreviation, such as half n = div n 2. It is translated to a definition in the SMT input. It cannot introduce a contradiction, because it only names an existing term. It can still fail to express what you intended, so it must be read and accepted.

The symbol is declared and constrained by axioms. This is the most flexible route and the only dangerous one: a single wrong guard makes the whole context inconsistent, and consistency checking is undecidable. Use proofreading and a smoke detector if you must use it at all.

Write the symbol as a terminating pure program with let rec function. Why3 checks termination with a variant and purity with its effect system, and derives a guarded definition axiom for the solver. This is the route the rest of the lecture builds on.

A definition is better, and the definition can be a program

Defining fact is clearly preferable, but a recursive definition has its own trap: it is only safe if it terminates. The deck makes the point with one line, function f (n: int) : int = 1 + f n. Read as an axiom this says ∀n. f n = 1 + f n, from which 0 = 1 follows. An unrestricted recursive definition is just an axiom in nicer clothing.

The solution is the idea that gives the lecture its subtitle. Everything needed to check termination already exists on the program side: loop and recursion variants, and a verification condition generator that checks them. So define the function as a program, and let Why3 promote it to a logical symbol once the checks pass. 

let rec function fact (n: int) : int
  requires { n >= 0 }
  variant  { n }
= if n = 0 then 1 else n * fact (n-1)

The keyword function is what makes this both a program and a logical symbol. As a program function it produces a verification condition like any other, including the obligation that n decreases and stays nonnegative at the recursive call. On the SMT side the result is a single definition axiom, guarded by the precondition. 

(declare-fun fact (Int) Int)
;; "fact'def"
(assert (forall ((n Int))
  (=> (<= 0 n)
      (ite (= n 0)
           (= (fact n) 1)
           (= (fact n) (* n (fact (- n 1))))))))

The equation only fires for nonnegative arguments, exactly the domain on which termination was established, so the earlier inconsistency cannot arise. Two conditions must hold for a program to be accepted as a logical symbol: it must terminate, and it must be pure, meaning no mutation of a global variable, no exception raised, and so on. Why3 checks both.

The same recipe scales further. The sum operator from the earlier lectures is defined this way, with a variant that is an expression rather than an argument, and a function as one of its parameters. 

let rec function sum (f: int -> int) (a b: int) : int
  variant { b - a }
= if b <= a then 0 else sum f a (b - 1) + f (b - 1)

Lemma functions: induction written as recursion

Suppose we now want the simple property that n! is at least 1 for every nonnegative n, stated as lemma fact_pos: forall n. n >= 0 -> fact n >= 1. A solver can unfold fact a bounded number of times, so it can settle a closed instance such as fact 3 ≥ 1, but the statement for all n needs induction, and SMT solvers do not perform induction.

The trick of this lecture is to write a program whose verification condition is exactly the induction you want. Such a program is called a lemma function. 

let rec lemma fact_pos (n: int) : unit
  requires { n >= 0 }
  ensures  { fact n >= 1 }
  variant  { n }
= if n > 0 then fact_pos (n-1)

Read it as a program and it does nothing at all: the return type is unit, no value is computed, and the body only calls itself with a smaller argument. Read it as a proof and it is an induction on n. The verification condition it generates is the following.

∀n. n ≥ 0 ⇒ [ (n > 0 ⇒ (n-1 < n ∧ 0 ≤ n) ∧ n-1 ≥ 0 ∧ (fact (n-1) ≥ 1 ⇒ fact n ≥ 1)) ∧ (¬(n > 0) ⇒ fact n ≥ 1) ]

The whole condition is under the hypothesis n ≥ 0, which is the precondition of the function. This is what it means for the lemma to be stated only for nonnegative arguments.

In the branch where n > 0, the first obligation is n-1 < n and 0 ≤ n: the variant strictly decreases and is bounded below. This is the termination check, and it is exactly what makes the induction well founded. Without it, a function could call itself forever and prove anything.

The next obligation is n-1 ≥ 0: the recursive call must satisfy the precondition of fact_pos. This is the side condition that the induction hypothesis is only available where the statement applies.

After the call, the postcondition of the callee is added to the context as fact (n-1) ≥ 1, and from it the caller must establish its own postcondition fact n ≥ 1. That implication is the inductive step, and the prover discharges it from the definition axiom, since fact n = n * fact (n-1) with n > 0.

The other branch, ¬(n > 0), is n = 0 given the precondition, and the goal there is fact 0 ≥ 1, which follows from the definition. Base case and inductive step together, produced by the ordinary weakest precondition machinery.

In general, a definition let lemma f v : unit requires P ensures Q = e generates three things: a verification condition for f, a ghost function f, and the axiom ∀v. P ⇒ Q added to the logical context.

On the SMT side the lemma appears as an assertion that looks like any other axiom, (assert (forall ((n Int)) (=> (<= 0 n) (<= 1 (fact n))))). The difference from the first part is not the formula but its origin: this one was derived rather than assumed. A goal such as fact 987 > 0 is then immediate, with no unfolding of the definition 987 times.

Because a lemma function is also a ghost function, it can be called in the middle of a program. Writing fact_pos 42; puts fact 42 ≥ 1 into the logical context from there on. This hands the prover one instance exactly where it is needed, instead of leaving it to instantiate a quantifier on its own.

Nothing forces the body to be recursive. A loop works just as well, and then the induction is carried by the loop invariant instead of by the recursion. 

let lemma fact_pos_loop (n: int) : unit
  requires { n >= 0 }
  ensures  { fact n >= 1 }
= for i = 1 to n do invariant { fact (i - 1) >= 1 } () done

Only the contract matters to the outside world. The body can be anything, provided it is observationally pure and terminating. This is the lecture's second takeaway: a proof can be a program, and not even necessarily a pure one.

The exercise attached to this part

Exercise 5 in the deck uses Fibonacci numbers, defined by F0 = 0, F1 = 1 and Fn = Fn-2 + Fn-1 for n ≥ 2. The five tasks are: define the numbers with let rec function; show that ∀n. Fn ≥ 0 with a recursive lemma function; show the same property with a for loop; verify a function that computes Fn using an array; and verify a function that computes Fn using two variables. The array and two variable versions come with the code already given, so the work is in the specification.

Ghost code

Definition

Ghost code is data and code added to a program in order to make the specification or the proof simpler. It is not going to be executed.

The running example returns the smallest Fibonacci number greater than n. The code is an ordinary two variable loop, but the specification needs the index of that Fibonacci number, and the index does not exist in the code.

The body keeps two variables, a and b, and advances them with a, b <- b, a+b while b <= n, then returns b. The postcondition has to be existential, because the index is not a program value: ensures { exists i. i >= 0 /\ fib i <= n < fib (i+1) = r }.

The loop needs an invariant, and for the same reason it also has to be existential: invariant { exists i. i >= 0 /\ a = fib i <= n /\ b = fib (i+1) }. It is correct, but the quantifier has to be instantiated again at every use, and the witness is never written down anywhere.

Introduce let ghost ref i = 0 in before the loop and add i <- i+1 to the body. That assignment is ghost code. Now the index is an actual variable, and the invariant loses its quantifier: invariant { i >= 0 /\ a = fib i <= n /\ b = fib (i+1) }. The deck calls this the better loop invariant.

Go one step further and return the index as a ghost output: the signature becomes (r: int, ghost i: int) and the postcondition becomes ensures { i >= 0 /\ fib i <= n < fib (i+1) = r }, with no existential at all. A client writes let f, i = first_fib 1000 in, where i is ghost and may only be used in ghost positions. At run time it does not exist.

Ghost data is also used to model data structures. A hash table can carry the real implementation and a logical model side by side, tied together by an invariant. 

type hash_table = {
  buckets: array (list (key, value));   (* implementation *)
  ghost m: key -> list value;           (* model *)
}
invariant { forall k v. ... }           (* gluing invariant *)

Specifications and client proofs then speak about m, the mathematical map, while the code manipulates buckets. The gluing invariant connects the two, and it is the only place where the representation has to be reasoned about.

The same idea handles machine arithmetic. A 32 bit integer is an abstract record holding a ghost mathematical integer, with an invariant fixing the range, and operations declared with preconditions that rule out overflow. 

type int32 = abstract {
  ghost value: int;
}
invariant { -0x8000_0000 <= value <= 0x7fff_ffff }

val (+) (a: int32) (b: int32) : int32
  requires { -0x8000_0000 <= a.value + b.value <= 0x7fff_ffff }
  ensures  { result.value = a.value + b.value }

Because the type is abstract, no one can build a value of it directly, so the invariant cannot be broken from outside. The payoff is that SMT solvers only ever handle mathematical integers, while absence of overflow is enforced by the preconditions.

The rules of the game

The single sentence that governs ghost code is this: the code is verified with its ghost code, but executed without it. Three consequences follow. Ghost code may read regular data but cannot modify it. Regular code does not see ghost data. Ghost code cannot modify the control flow of regular code. Together these are the principle of non interference.

The termination requirement is easy to overlook, so the deck gives a one line counterexample. 

let f x =
  ...
  ghost while true do () done;   (* would change the control flow *)
  ...                            (* everything below is now verified *)

A non terminating ghost loop makes everything after it unreachable from the verifier's point of view, so the remaining obligations hold vacuously. At run time the ghost loop is erased and the code simply continues, unverified. This is why termination of ghost code is a soundness condition and not a matter of taste.

Why3 checks non interference rather than trusting the programmer. For every program expression it tracks possible non termination, exceptions that may be raised, and variables that may be read and modified, with memory aliases known statically. The theory behind these checks is described in "The Spirit of Ghost Code" by Jean-Christophe Filliâtre, Léon Gondelman and Andrei Paskevich, FMSD 2016.

Takeaways

The first takeaway is that axioms are dangerous. There is no mechanical way to chase inconsistencies, because the question is undecidable, and a solver that finds a contradiction will use it rather than report it. A definition is always preferable.

The second is that a proof can be a program, and not even necessarily a pure one. A terminating recursive function with the right contract is an induction, and so is a terminating loop with the right invariant. In both cases the verification condition generator turns the program into the logical statement you wanted, and the prover checks it.

Seen together, the three parts are one idea applied three times. The program side already has contracts, variants, an effect system and a verification condition generator. Rather than building separate machinery for the logic, reuse it: to define a symbol safely, to prove a lemma by induction, and to carry the extra information a proof needs without paying for it at run time.
