Weakest Preconditions: From Programs to Verification Conditions

Jean-Christophe Filliâtre, CNRS. Second lecture of "The Why and How of Deductive Program Verification", subtitled "from programs to provers".

The previous session demonstrated a verification tool from the outside. This lecture opens the box. Filliâtre defines a small imperative language, fixes what correctness means for it using Hoare triples, and then presents the mechanical procedure that turns a program together with its specification into logical formulas a prover can attack. That procedure is Dijkstra’s weakest precondition calculus. The lecture builds it rule by rule, adds loop invariants, runtime safety, function contracts and termination, and applies each addition to one running example: Egyptian multiplication. If you follow that example to the end, you have followed the whole path from source code to verification condition.

A small language where everything is an expression

Nothing can be proved about a language that has not been defined, so the lecture starts by defining one that is small enough to fit on two slides. The first layer is pure terms : integer constants, the Boolean constants true and false, immutable variables (written v), mutable variables (written x), and unary and binary operations. The operations are the arithmetic ones (+, -, ×), the comparisons (=, ≠, <, >, ≤, ≥) and the Boolean connectives (∧, ∨, ¬). There are exactly two data types here, mathematical integers and Booleans.

Two properties of pure terms carry the whole design. First, a well-typed term always evaluates without error, which is why division is deliberately missing at this stage: division can fail, and failure is postponed. Second, evaluating a term never changes the memory. Together these mean that a pure term can live on both sides of the fence, in the program and in the logic, with the same reading in both. That is what makes it possible later to write a specification that mentions program variables directly.

The second layer is program expressions , which may allocate and modify memory.

ExpressionReading
skipdo nothing
ta pure term, used as an expression
x ← tassignment to a mutable variable
e ; esequence, a binary operator on expressions
let v = e in ebind an immutable variable, local to the second expression
let ref x = e in eallocate a mutable variable, local to the second expression
if t then e else econditional, with a pure term as the guard
while t do e doneloop, with a pure term as the guard

Mutable variables are not first-class values: a reference cannot be stored in another variable or passed around as data. Well-typed expressions still cannot fail, but unlike terms they can diverge, because of the loop. Notice also that the guard of a conditional and the right-hand side of an assignment are terms rather than arbitrary expressions. That looks restrictive, and it is not, because syntactic sugar recovers the general forms .

x ← e is let v = e in x ← v
if e then e1 else e2 is let v = e in if v then e1 else e2
if e1 then e2 is if e1 then e2 else skip
e1 && e2 is if e1 then e2 else false
e1 || e2 is if e1 then true else e2

The last two lines are worth reading twice. Short-circuit conjunction and disjunction are not primitives with a special evaluation order bolted on: they are conditionals, and they inherit the right behaviour automatically. This works only because the conditional is an expression that returns a value.

The language makes no distinction between expressions and statements. There are only expressions, and that is nicer and simpler. Many programming languages still separate the two for historical reasons, but if you are designing a new language, especially one meant for verification, it is easier to have expressions only.

Jean-Christophe Filliâtre, on the design of the language

Before any verification happens, the language is statically typed in a completely standard way . Three types suffice: int, bool and unit, the last one for expressions that return no meaningful value. So skip and every assignment have type unit; in a sequence the left expression must have type unit and the type of the whole sequence is the type of the right expression; a loop has type unit. This ordering matters: typing comes first, and a program that does not type check never reaches the prover.

The running example is Egyptian multiplication, also known as Russian peasant multiplication . It computes a product using only additions, halving, and a parity test. It is the same algorithm as fast exponentiation, with multiplication replaced by addition and squaring replaced by doubling.

let ref p = a in
let ref q = b in
let ref r = 0 in
while q > 0 do
    if odd q then r ← r + p ;
    p ← p + p ;
    q ← half q
done ;
r

The informal specification is short: at the beginning we require b ≥ 0, and at the end we ensure that the returned value equals a × b. The rest of the lecture is about making that sentence formal and then proving it mechanically.

Hoare triples and partial correctness

The statement to be proved is written as a triple .

Definition Hoare triple {P} e {Q}, where P is the precondition, e a program expression and Q the postcondition: if we execute e in a state that satisfies P, then the computation either diverges or terminates in a state that satisfies Q. This is partial correctness: nothing at all is claimed about termination.

Three valid triples make the definition concrete . The first is the obvious one: {x = 1} x ← x + 2 {x = 3}. The second, {∃v. x = 4v} x + 42 {∃w. result = 2w}, shows the convention for the value of an expression: the reserved name result stands in the postcondition for the value the expression produced. A multiple of four plus 42 is indeed even. The third is the interesting one: {true} while true do skip done {false}. Starting from any state whatsoever, that program diverges, so by the definition the triple holds, and it holds for every postcondition, including false.

Careful A non-terminating program satisfies every specification under partial correctness. This is not a defect in the definition; it is the price of separating two independent questions. Termination is proved later, with variants, and only the two together give total correctness.

For the running example the goal is therefore the triple {b ≥ 0} Egyptian multiplication {result = a × b}.

From deduction rules to weakest preconditions

How does one establish that a triple is valid? Hoare’s 1969 paper answers with deduction rules, one per construct . The rule for the conditional, for example, says that if the two triples for the branches hold under the guard and its negation, then the triple for the conditional holds.

premises:   {P ∧ t} e1 {Q}    and    {P ∧ ¬t} e2 {Q}
conclusion:   {P} if t then e1 else e2 {Q}

As a proof system this is fine. As a basis for a tool it is awkward. The rules are read from the conclusion upwards, and at many program points they require an intermediate assertion that nothing in the rule tells you how to choose. The rule for a sequence, for instance, needs a formula describing the state in the middle, and that formula has to come from somewhere. Mechanising this means guessing, and guessing is what we want to avoid.

The practical answer came a few years later, from Edsger Dijkstra in 1975 .

Key idea Weakest precondition. Given an expression e and a postcondition Q, compute the weakest precondition P such that {P} e {Q} holds. It is written WP(e, Q). This is a predicate transformer: a function that takes a formula and returns a formula. Nothing has to be guessed, because the intermediate assertions are computed.

The intuition is easiest to see on an assignment. If you want x to be even after x ← 3 × x × y, then what you need before is that 3 × x × y is even. In general, to obtain a postcondition that talks about x, you need the same formula with the assigned term put in the place of x. Here are all the rules of the calculus .

RuleWhat it does
WP(skip, Q) = QNothing happens, so nothing changes.
WP(t, Q) = Q[result ↦ t]A pure term produces a value. Replace the reserved name result by that term.
WP(x ← t, Q) = Q[x ↦ t]Assignment is substitution: every occurrence of x in the postcondition becomes t.
WP(e1 ; e2, Q) = WP(e1, WP(e2, Q))Compute the inner call first. WP(e2, Q) is the assertion that must hold in the middle of the sequence, and it becomes the postcondition of the first expression.
WP(let v = e1 in e2, Q) = WP(e1, WP(e2, Q)[v ↦ result])Like a sequence, with a rename. The middle assertion may mention v, whose value is the value produced by e1, so v is renamed to result before the formula is used as the postcondition of e1.
WP(let ref x = e1 in e2, Q) = WP(e1, WP(e2, Q)[x ↦ result])Identical. For the calculus there is no difference between introducing an immutable and a mutable variable; the difference shows up only in the assignment rule and in typing.
WP(if t then e1 else e2, Q) = (t ⇒ WP(e1, Q)) ∧ (¬t ⇒ WP(e2, Q))Both branches must be covered, each under its own hypothesis about the guard.

Every rule reduces the problem to smaller expressions, so the computation terminates and is completely mechanical. The direction is the point: the calculus starts at the postcondition and moves towards the front of the program.

Swimming up the waterfall: the loop body

The lecture applies the rules to the three lines that make up the body of the running example . Write Q[p, q, r] for an arbitrary postcondition about the three mutable variables, so that Q[p + p, half q, r] means the same formula with p + p in the slot for p and half q in the slot for q. The computation starts at the bottom, under the last line, and works upwards.

We are given the postcondition of the body, Q[p, q, r]. Nothing else is known yet.

The last line is an assignment, so apply WP(x ← t, Q) = Q[x ↦ t]. Every occurrence of q becomes half q; p and r are untouched by this assignment and stay as they are. Result: Q[p, half q, r].

The same rule again, this time substituting p + p for p in the formula we just obtained. Result: Q[p + p, half q, r]. This formula is now the postcondition of the conditional on the first line.

The conditional has no else, so by the sugar rule the missing branch is skip. Since WP(skip, Q) = Q, the precondition of that branch is unchanged: Q[p + p, half q, r].

The other branch is the assignment r ← r + p. Substituting r + p for r gives Q[p + p, half q, r + p].

The conditional rule joins the two results, each guarded by the test: ( odd q ⇒ Q[p + p, half q, r + p]) ∧ (¬ odd q ⇒ Q[p + p, half q, r]). This is the weakest precondition of the whole body. No intermediate assertion was invented at any point: every formula was produced by a substitution.

Loops: the one place the user has to help

Every construct so far had a rule that computes. The loop does not, and this is where the user enters the picture. One can define the weakest precondition of a loop by asserting that a suitable invariant exists, but an existential quantifier over properties is not something a first-order prover can handle. The practical version asks the user to write the invariant down as an annotation .

WP(while t invariant J do e done, Q) =
J ∧
∀ x1 ... xk . (J ∧ t ⇒ WP(e, J)) ∧ (J ∧ ¬t ⇒ Q)

The formula packages three separate proof obligations.

ObligationFormulaMeaning
EstablishmentJThe invariant holds when the loop is first reached.
PreservationJ ∧ t ⇒ WP(e, J)Starting from any state that satisfies the invariant and the guard, one iteration of the body restores the invariant.
ExitJ ∧ ¬t ⇒ QWhen the guard is false, the invariant alone is strong enough to give the postcondition.

The universal quantifier over x1 ... xk, which ranges over exactly the references modified in the body, is the subtle part. We cannot know the values of those references after an unknown number of iterations, so preservation and exit have to be proved for arbitrary values of them. The consequence is a practical one: the invariant has to carry every piece of information about the modified variables that the rest of the proof needs, because outside the invariant nothing is known about them. Variables the loop does not modify are not quantified, so facts about them, such as the precondition b ≥ 0 in the running example, remain available as free hypotheses .

Finding an invariant is hard in general: it amounts to constructing a proof of the postcondition by induction. In a tool such as Why3 the invariant is either written by the user or produced by another method, for instance abstract interpretation.

With the annotation in place, the whole verification condition for Egyptian multiplication can be assembled .

We start from result = a × b, placed after the entire program.

The last expression of the program is the pure term r. By WP(t, Q) = Q[result ↦ t], the assertion just before it is r = a × b. This is what must hold when the loop exits.

The user supplies an invariant J[p, q, r]. Preservation needs WP(body, J), and we computed exactly that in the previous stepper, with J in place of Q: ( odd q ⇒ J[p + p, half q, r + p]) ∧ (¬ odd q ⇒ J[p + p, half q, r]).

Apply the loop rule, quantifying over the three modified references:

J[p, q, r] ∧
∀ p q r . J[p, q, r] ⇒
  (q > 0 ⇒ ( odd q ⇒ J[p + p, half q, r + p]) ∧ (¬ odd q ⇒ J[p + p, half q, r])) ∧
  (q ≤ 0 ⇒ r = a × b)

The three let ref bindings initialise p, q and r with a, b and 0. Their rule substitutes those terms for the variables, and only the first line changes: the first conjunct becomes J[a, b, 0]. The quantified part is untouched, because p, q and r are bound there by the universal quantifier.

By the soundness corollary, proving the triple means proving that the precondition implies the weakest precondition:

b ≥ 0 ⇒ ( J[a, b, 0] ∧ ∀ p q r . J[p, q, r] ⇒ ... )

Note where b ≥ 0 sits: outside the quantifier, so it is available when proving establishment. There is no need to repeat it inside the loop invariant.

Exercise 2 from the lecture: find a suitable invariant J[p, q, r]

One invariant that works is q ≥ 0 ∧ r + p × q = a × b. Establishment: with p = a, q = b, r = 0 it reduces to b ≥ 0 ∧ a × b = a × b, and b ≥ 0 is exactly the free hypothesis coming from the precondition. Preservation: when q is even, r + 2p × (q/2) = r + p × q; when q is odd, (r + p) + 2p × ((q - 1)/2) = r + p × q. Exit: q ≥ 0 together with q ≤ 0 forces q = 0, so r = r + p × 0 = a × b. The conjunct q ≥ 0 is needed precisely because the exit obligation knows nothing else about q.

What justifies the whole construction is a soundness theorem : for any e and any Q, the triple {WP(e, Q)} e {Q} is valid. It is proved by induction on the structure of the program with respect to a reasonable semantics, for example an operational one. The corollary is the working recipe: to show that {P} e {Q} holds, it suffices to prove the single formula P ⇒ WP(e, Q). That is what Why3 does.

Runtime safety

So far a program could diverge but never fail. Real programs fail: arithmetic operations overflow or divide by zero, memory accesses hit null pointers or run past the end of a buffer, and assertions written by the programmer can be violated. The definition of the triple is therefore strengthened : if we execute e in a state satisfying P, then there will be no runtime error, and the computation either diverges or terminates normally in a state satisfying Q. Divergence is still allowed under partial correctness; failure is not.

The first new construct is the assertion, assert R, which fails if R does not hold . Its rule looks trivial and hides a practical trick.

WP(assert R, Q) = R ∧ Q = R ∧ (R ⇒ Q)

The two right-hand sides are logically equivalent, and yet the second is the one tools use. The reason appears when the conjunction is split into separate proof obligations: the first one asks you to prove R, and in the second one R arrives as a hypothesis in the context, so the fact you just asserted can be used to discharge everything that comes after it in the program. That is usually the whole point of writing the assertion.

Partially defined operations get the same treatment . Adding Euclidean division and array access to the language gives two more rules.

WP(t1 div t2, Q) = t2 ≠ 0 ∧ Q[result ↦ (t1 div t2)]
WP(a[t], Q) = 0 ≤ t < |a| ∧ Q[result ↦ a[t]]

Each rule has the same shape: a safety condition, then the ordinary substitution. Notice that the division on the left of each rule is the program operation, which can fail, while the one inside the substituted term is the logical function, which is total. The same symbol appears on both sides of the fence with two different meanings.

Functions and contracts

A program is not one big expression, so the language gains functions . There are two forms: let f (v1: τ1) ... : τ C = e defines a function with a body, and val f (v1: τ1) ... : τ C declares an abstract one with no implementation at all. Both carry a contract C made of three kinds of clause: requires P for the precondition, ensures Q for the postcondition, and writes x1 ... xk listing the global references the function may modify. For a defined function the tool can infer the writes clause; for a declared one the user must state it.

val ref r : int   (* a global reference *)

let incr_r (v: int) : int
  requires { v > 0 }
  writes   { r }
  ensures  { result = old r /\ r = old r + v }
= let u = r in
  r <- u + v;
  u

The postcondition needs to relate the state at the end of the function to the state at the beginning, which is what the old notation provides: old r denotes the value of r in the pre-state. Verifying the definition means discharging one formula : quantify over the global references and the parameters, assume the precondition, and prove the weakest precondition of the body against the postcondition, with the old references replaced by the current ones since we are standing in the pre-state.

VC(incr_r) = ∀ r v . v > 0 ⇒ ( r = ro ∧ r + v = ro + v )[ro ↦ r]
which reduces to   ∀ r v . v > 0 ⇒ r = r ∧ r + v = r + v

At a call site the contract is used in the other direction . The rule for f t1 ... tn is a conjunction of two parts. The first is the precondition of f with the formal parameters replaced by the actual arguments: the caller must establish it. The second says that the postcondition of f, similarly instantiated, implies the postcondition we are trying to prove after the call. That second part is under a universal quantifier over result and over the references the function may modify, because after the call their values are unknown except for what the postcondition says, and fresh variables are used to remember the pre-state values so that old keeps its meaning. The substitutions look heavy, and their job is simply to avoid variable capture.

The result is that verification is modular: each function is verified once, on its own .

Filliâtre draws the analogy with static typing explicitly. A compiler checks the declared types against the body when it compiles a function, and afterwards assumes those types at every call. A verifier does the same with the contract, one level up. The body is checked once against the contract, and each caller then works against the contract alone, never against the body.

This also gives a cleaner account of unsafe operations than the special rules of the previous section . Division and array access need not be built into the language at all: they can be declared as program functions whose contracts state the safety condition and relate the result to the corresponding logical function.

val (/) (x: int) (y: int) : int
  requires { y <> 0 }
  ensures  { result = div x y }

val ([]) (a: array 'a) (i: int) : 'a
  requires { 0 <= i < size a }
  ensures  { result = a[i] }

Applying the function-call rule to these declarations produces exactly the weakest preconditions given earlier for the built-in versions. This is how Why3 actually handles unsafe operations: they live in the library, not in the calculus.

Termination, variants and total correctness

Everything so far is partial correctness. The remaining question is whether the program terminates for every initial state satisfying the precondition . Two things suffice: every loop makes a finite number of iterations, and recursive calls cannot go on indefinitely. Partial correctness plus termination is called total correctness.

Definition A variant is a value attached to a loop or a recursive function which is required to decrease at each iteration or each call, with respect to a well-founded order, that is, an order with no infinite decreasing chain . For signed integers a practical choice is i ≺ j defined as i < j ∧ 0 ≤ j.

Note where the non-negativity sits in that order: it constrains the larger value j, not the smaller one. That is convenient in practice, because it allows the variant to become negative in the very last state, after the final iteration, without breaking anything.

The loop rule gains one clause . With a variant s, preservation becomes J ∧ t ⇒ WP(e, J ∧ s ≺ w)[w ↦ s], where w is a fresh variable holding the value of the variant at the start of the iteration. So each iteration must both restore the invariant and strictly decrease the variant.

Exercise 3 from the lecture: find a suitable variant for Egyptian multiplication

The variant is q. Inside the loop the guard gives q > 0, so half q < q, and the order requires only that the larger value be non-negative, which the guard already provides. The invariant conjunct q ≥ 0 is what the postcondition proof needs; the guard is what the variant needs.

Recursive functions get a variant clause in their contract. At each recursive call inside the body, the call rule gains one extra conjunct next to the precondition: the variant evaluated at the call site must be smaller, in the well-founded order, than the variant evaluated at the entry of the function. Mutually recursive functions each need their own variant term, and all of them must use a common well-founded order .

The example is McCarthy’s 91 function .

let rec f91 (n: int) : int
  ensures { result = if n <= 100 then 91 else n - 10 }
  variant { 101 - n }
= if n <= 100 then
    f91 (f91 (n + 11))
  else
    n - 10

The inner call is easy: its argument is n + 11, so the variant drops from 101 - n to 90 - n. The outer call is the interesting one, because its argument is the value returned by the inner call, and syntactically nothing is known about that value. What saves the proof is the postcondition of the inner call, which says the returned value is 91 when n + 11 ≤ 100 and n + 1 otherwise; in both cases it is strictly greater than n, so the variant strictly decreases. Since the decrease of the variant is generated as part of the verification condition, the postcondition of the inner call is available in the context exactly where it is needed. Specification and termination are not independent: here one is proved with the help of the other.

What to remember

The calculus turns a program and its specification into verification conditions completely mechanically . Everything is computed by substitution, working backwards from the postcondition, with two exceptions: loop invariants and variants, which the user provides. That division of labour is the practical shape of deductive verification. The prover never has to guess an intermediate assertion, and the human only has to supply the inductive content of the proof.

The second point is that termination matters as much as partial correctness . A specification that says nothing about a diverging program is satisfied by a program that simply loops forever, so partial correctness alone is not a meaningful specification. The two together are.

Not covered for lack of time: exceptions

The deck continues with exceptions, treated as additional destinations of a computation next to divergence, failure and normal termination. Each exception E gets its own postcondition QE, declared in the contract with a raises clause, and the calculus simply carries a second postcondition through every rule: WP(raise E, Q, QE) = QE, while a sequence propagates the exceptional postcondition unchanged and try e1 with E → e2 passes the weakest precondition of the handler in as the exceptional postcondition of the protected expression. Exceptions carrying data reuse the machinery of let. The typical specification given is binary search, whose contract requires a sorted array, ensures that the returned index holds the value, and states under raises that if Not_found is raised then the value occurs nowhere in the array.
