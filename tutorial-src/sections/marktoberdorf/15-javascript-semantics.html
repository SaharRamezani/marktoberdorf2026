Mechanized Specifications for Real Languages: JavaScript and ESMeta

Sukyoung Ryu (KAIST), from the deck Mechanized Specifications Adopted by Real-World PLs, 17 August 2026.

Almost everything we build in formal methods sits on top of a semantics for some programming language. Whether an analysis is sound, whether an optimisation preserves behaviour, whether a verifier can be believed: all of it depends on having got the semantics of the real language right. This lecture is about what happens when the real language is JavaScript, whose semantics is genuinely difficult and whose standard is republished every year. The answer the lecturer's group arrived at is unusual and worth understanding in detail: stop writing the tool by hand, and generate it from the standard document itself.

Where this sits in the series

This is the first of four lectures on mechanized specifications for languages that industry actually uses. The plan on the outline slide is: JavaScript and ESMeta first, then WebAssembly and SpecTec, then P4 and P4-SpecTec, and finally other programming languages together with non-PL software . The through line is the same in each case. Take a standards document written for human implementers, turn it into something a machine can execute and analyse, and then persuade the people who own the document that this is worth having.

She opened with a point about research taste, borrowed from a talk Thomas Reps gave at the PLMW workshop at PLDI 2026 . There are two honest ways to choose a problem. One is problem-driven and technique-agnostic: you want to solve something real and you will use whatever works. The other is technique-driven and problem-agnostic: you have a favourite method and you look for places to apply it. Her own group started firmly in the second camp, because they liked static analysis, and the JavaScript work gradually pushed them into the first. The advice she drew out of it was practical: think about impact, build artifacts, build tools, engage with industry, and reach out. The adoption story later in this section is what that advice looks like when it works.

One line of JavaScript that should not surprise you, but does

Before any of the machinery, it helps to feel why this language is hard. Consider a function that compares its argument with the negation of that argument .

function f(x) { return x == !x; }

// Always false?  No.
f([])  ->  [] == ![]
       ->  [] == false
       ->  +[] == +false
       ->  0 == 0
       ->  true

The reason is that the two operators in the expression convert their operands through different types. The logical negation operator applies ToBoolean to its operand. Every object is truthy in JavaScript, including an empty array, so ToBoolean of [] is true and ![] is therefore false. We are now asking whether [] is loosely equal to false.

Loose equality does not stop there. Its rules say that when one side is a Boolean, that side is replaced by its numeric value, so false becomes 0. That leaves an object compared with a number, and the rule for that case converts the object to a primitive: the empty array becomes the empty string, and the empty string converts to 0. So both sides arrive at 0, and the comparison is true. A value and its own negation are equal, because ! travels through Boolean and == travels through Number, and the two roads meet at zero.

Careful This is not a curiosity bolted on to an otherwise tidy language. ECMA-262 devotes an entire chapter to implicit conversions. The reason is historical and deliberate: JavaScript was designed for the web, where getting stuck is worse than being wrong. Rather than raise an exception, the language coerces its way onward. Every one of those coercions is a rule someone has to model correctly before any analysis built on the language can be called sound.

Does f return true for everything, then?

No, and the contrast is instructive. Take f(0). ToBoolean of 0 is false, so !0 is true, which loose equality converts to the number 1. We end at 0 == 1, which is false. The same rule chain that makes f([]) true makes f(0) false. Following the chain is the only way to know which you get, and following the chain is exactly what a hand-written analyser has to reproduce for every operator in the language.

What the standard actually contains

ECMA-262, the ECMAScript language specification, is maintained by TC39, the technical committee that owns the language. It defines both halves of what a semantics needs . The syntax appears as grammar productions: the deck uses the production for ArrayLiteral as its running illustration. The semantics appears as numbered evaluation algorithms attached to those productions: for the same example, the evaluation algorithm for the third alternative of ArrayLiteral. The algorithms are written in English, but in a very particular English.

Two facts about the document set the problem. It is large: ECMAScript 2021, the twelfth edition, runs to 879 pages . And since 2015 it has been on an annual release cadence with an open development process, so it changes continuously and ships a new edition every year. The lecturer keeps a full printout in her office and described reading it line by line, the way one studies for an exam.

The hand-written era, and what it cost

The conventional approach is that a person reads the standard and writes an analyser. Three long-running JavaScript analysers did exactly this: SAFE at KAIST, TAJS at Aarhus University, and WALA at IBM T.J. Watson . The deck's picture of the situation is blunt: ECMA-262 goes in, an analyzer developer reads it, defines the formal semantics by hand, and hand-writes an abstract JavaScript static analyser out the other end, with both the definition and the implementation carrying the word "manual" on the arrow . The same picture holds for the formal semantics line of work that the deck lists alongside it, including KJS, JSIL and JSCert.

The second picture is the damaging one. Laid against the timeline of ECMAScript editions from ES1 in 1997 to ES12 in 2021, each of those tools appears at the version it was built for and then falls behind . ES6 in 2015 brought classes and modules, ES7 brought destructuring patterns, ES8 brought new object manipulation, and every one of those releases meant reading the diff and patching the analyser by hand. As the lecturer put it, this is labour-intensive and error-prone work, and after late 2014 the annual cadence turned it from a burden into a treadmill.

The group's own decade in that era produced a chain of extensions rather than a single tool. They had to model the DOM, because a JavaScript program that never touches the browser is not a realistic program. They modelled host APIs described in WebIDL, because JavaScript programs interoperate with code written in other languages. They worked on abstracting minified or bundled code whose source is not available, by leveraging dynamic analysis to obtain results and abstracting from those. And when purely static analysis did not scale, they combined forces with the WALA group at IBM: WALA was fast but unsound, SAFE was sound but slow, and the joint work traded one property against the other deliberately . Some of that was driven by wanting to optimise real applications, including programs written at Samsung Electronics. Ten years of it were later written up as a survey of JavaScript analysis, and the journey itself became a Communications of the ACM article on JavaScript language design and implementation in tandem .

In the beginning we were two teachers, but we soon became good friends, because we were struggling with the same weird, crazy language.

The question that changed the approach

The breakthrough came from a change of question rather than from a new technique. Jihyeok Park argued that maintaining an analyser by hand was the wrong thing to be spending the effort on, and that a different approach was needed . His question was: can we generate static analyzers automatically, straight from the book ? This was before large language models were a practical option, so the answer had to come from the structure of the document itself.

The observation that made it possible is on the next slide, and it is the whole idea in one sentence: the specification is written in very simple English prose . The evaluation algorithms are not free-form natural language. They are numbered steps built out of a small, stylised set of phrase forms that recur across the whole document, because the editors of a standard write in a house style on purpose . If the set of phrase forms is small and closed, then a compiler from those phrases into an executable language is not only possible, it is small.

Key idea Treat a prose specification as a program. The English is the source language; the machine-readable semantics is the target. What stands between them is a compiler, and because the English is stylised the compiler is a table of phrase patterns rather than an exercise in natural language understanding.

The target language is IRES, an intermediate representation for ECMAScript designed to say the things ECMA-262 says . It has functions that can be ordinary or syntax-directed, instructions for reference update, object allocation, call, branch and return, and values that include addresses, primitive values such as booleans, integers and strings, and JavaScript abstract syntax trees as first-class values. That last point matters: because IRES treats JavaScript ASTs as values, a syntax-directed function in the metalanguage corresponds directly to an evaluation algorithm attached to a grammar production in the standard.

Definition A mechanized specification here means a machine-readable, executable rendering of the standard: a parser generated from its grammar productions and a set of IRES functions generated from its evaluation algorithms. Together those functions are a JavaScript interpreter, and that interpreter is itself just a program, which is what makes everything downstream possible. The umbrella framework holding the tools built on it is called ESMeta.

From book to interpreter

The extraction toolchain is JISET, the JavaScript IR-based Semantics Extraction Toolchain, by Jihyeok Park, Jihee Park, Seungmin An and Sukyoung Ryu, published at ASE 2020 . Its architecture has two lanes running in parallel from the same document: one for syntax, one for semantics .

The standard is published as HTML as well as PDF, and the HTML carries structural annotations that mark grammar productions and algorithm steps. Those annotations are what make parsing the document tractable rather than a heuristic mess. The group took the HTML and parsed it.

A BNF production extractor pulls the grammar out of the syntax sections. ECMAScript's grammar is not context free in the convenient sense, so the productions are turned into a parsing expression grammar with lookahead, which is what the standard's own side conditions amount to.

A parser generator turns that grammar into an actual JavaScript parser. No one writes this parser; it is a function of the edition you fed in, so a new edition gives a new parser for free.

In the other lane, the abstract algorithms are collected: the numbered English steps attached to productions and to the built-in library functions.

An algorithm compiler matches each step against a pattern and emits IRES. This is where the small-and-stylised observation pays off: the paper reports 118 compile rules, and the deck notes 126 as of today. That is the entire English-to-IR translation table for a document of several hundred pages.

About 96 percent of the algorithms compile automatically . The remainder is genuinely awkward prose. The lecturer singled out one chapter that reads less like English than like a translation of C++ code, a description its own author cheerfully accepted. Rather than spend effort on the residue for every edition, they picked the latest edition and filled in the missing parts by hand.

Test262 is the official ECMAScript conformance test suite. Of it, 18,556 tests are applicable. The generated parser passes all 18,556 parsing tests, and the generated interpreter passes all 18,556 evaluation tests . That is the evidence that the extracted specification is not merely plausible but correct in the sense the committee itself uses.

What you can build once the interpreter is generated

Extraction is only the first of three steps in the overall approach: mechanized specification extraction, then a validity check on the extracted specification, then derivation of static analysers . The second and third steps are where the payoff is, and they are only available because the specification is now a program.

JEST, by Jihyeok Park, Seungmin An, Dongjun Youn, Gyeongwon Kim and Sukyoung Ryu (ICSE 2021), does N+1-version differential testing of JavaScript engines . Classical differential testing compares implementations against each other. Here the extracted specification acts as an extra participant, so when engines disagree you can tell which of them is wrong, and when they all agree but the specification says otherwise you have found a specification bug. Programs are synthesised from the syntax and semantics of the specification, mutated under coverage guidance, and then turned into conformance tests by injecting assertions in seven kinds: exceptions, aborts, variable values, object values, object property descriptors, property keys, and internal methods and slots . From ES11 it synthesised 1,700 conformance tests and found 44 bugs in engines and 27 in the specification .

JSTAR, by Jihyeok Park, Seungmin An, Wonho Shin, Yusung Sim and Sukyoung Ryu (ASE 2021), turns the tables and analyses the specification itself . Because the extracted algorithms are IRES functions, you can run a type analysis over them and look for the kinds of mistake any untyped program has: unknown variables, duplicated variables, wrong arity, failed assertions, operands of the wrong type, and unchecked abrupt completions. The illustrative bug is a numeric comparison applied to a value that can be a boolean, which is why Math.round(true) and Math.round(false) had to be pinned down as 1 and 0 . Run across 864 versions of ECMA-262 spanning three years, JSTAR reported 157 candidate bugs of which 93 were true bugs, a precision of 59.2 percent once condition-based refinement is switched on, and 14 of those bugs were still present in ES12 at the time .

JSAVER, by Jihyeok Park, Seungmin An and Sukyoung Ryu (FSE 2022), closes the loop by deriving the static analyser . The trick is a change of level. The usual, compiler-based route writes a hand-made compiler from JavaScript to some IR and then analyses the IR. JSAVER instead takes the generated interpreter, which is itself an IR program, and runs an abstract interpretation of that interpreter on the program of interest. The analyser you get is derived, not written, so it conforms to whichever edition you extracted. On the 18,556 applicable Test262 tests it analysed the programs with 99.0 percent precision at 590 milliseconds on average .

JEST_fs, by Jihyeok Park, Dongjun Yoon, Kanguk Lee and Sukyoung Ryu (PLDI 2023), sharpens the conformance testing with feature-sensitive coverage . Plain coverage of the specification's algorithms treats every execution of a step alike; feature sensitivity distinguishes the language feature under which a step was reached, which exposes gaps that undirected coverage reports as already covered. The line of work continued into a journal version and a tool demonstration at FSE 2025 .

How the work got adopted

A formalisation that the standards body ignores is a paper. This one is in the committee's own infrastructure, and the lecturer raised the question of how that happened herself, because another well regarded group had done comparable work, had published it, had presented it to TC39, and had not been taken up. The question put to her was, in effect, how did you convince them, given the community's reputation for being hard to convince. The recording garbles the name of the group involved, so it is not reproduced here.

The recording does not preserve the spoken answer: the question is the last thing on the tape. What the deck does preserve is the sequence of events, and the sequence is itself the argument .

Read in order, the tools arrive first and the meetings come after. By the time the group sat down with the editors they were not proposing that the committee learn a formalism; they were reporting concrete defects in the document the editors were responsible for, and defects in the engines that implement it. The eventual integration is the part that matters: ESMeta runs in the continuous integration of ECMA-262 and Test262, so it checks each proposed change to the standard as that change is made, rather than checking a snapshot after the fact. Ecma International went on to publish a note about the arrangement between the KAIST group and TC39 , and the current specification is served in exactly the annotated HTML form the extractor consumes .

The same pattern shows up one level down, with implementers rather than editors. After JEST reported 16 engine bugs in GraalJS, one of which crashed the engine outright when the prefix increment operator was applied to undefined, so that developers could not even catch the exception, the response was not scepticism about the method .

Right now, we are running Test262 and the V8 and Nashorn unit test suites in our CI for every change. It might make sense to add your suite as well.

Key idea The adoption argument was never "our semantics is more rigorous than your prose". It was "here are bugs in your document and your implementations, found automatically, and the finder can be wired into your build". Rigour was the means. Defects that someone was already obliged to care about were the currency.

Where this goes next

The JavaScript work is the hard case, because ECMA-262 was never written with mechanisation in mind and the extraction has to cope with prose that grew organically over twenty-five years. The lecturer's verdict on the next language in the series was short: they met WebAssembly, and its specification is really nice. That is tomorrow's topic, together with SpecTec, the specification framework built for it . The interesting question to carry across is what changes when the standards document is designed from the start to be a formal artifact rather than reverse-engineered into one, and whether the same adoption strategy is still needed when the committee is already sympathetic.
