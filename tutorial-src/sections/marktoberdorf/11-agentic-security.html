Security for Agentic Systems: Attacks and Vulnerabilities

John C. Mitchell (Stanford University), from the deck Evaluation and Security of AI-Based Systems, day 3.

The previous section defined direct and indirect prompt injection. This one follows what happens when the same weakness is placed inside a system that plans, delegates and executes code. The argument runs along a ladder: a chatbot can be talked into breaking its own rules, a single agent with tools can be fed instructions through the tools, and a multi-agent system can have its control flow rewritten by content it merely read. At each rung the attacker gains more, and the defences that worked one rung down stop being sufficient.

How to state a security question properly

Before describing any attack, the lecture insists on a habit that is easy to skip. A security claim only means something once three things are written down . First, the system of interest. Second, the desirable property, which is usually the intended function of the system, though in practice it is often scaled back to the most essential protection the user needs. Third, the interface and capabilities of the attacker, which is what people mean by a threat model. Only then can you ask the actual question: can an attacker with that interface make the desirable property fail?

Key idea Every attack below is stated as a triple: who the victim is, what interface the attacker has, and what the attacker is trying to make the system do. If you cannot fill in all three, you do not yet have a threat model, you have a worry.

Rung one: the chatbot and the SQL analogy

The simplest case is a chatbot with a system prompt. The system prompt defines the scope of the conversation and acts as the guardrail. The loop is short: user input is appended to the conversation history, the history goes to the model, and the response comes back . Here the victim is the system, the attacker interface is the ordinary user input box, and the goal is to obtain responses the system prompt forbids .

Three properties make this work . Trusted input, meaning the system prompt, and untrusted input, meaning whatever the user typed, are concatenated and handed to the model as one text. The model has been fine-tuned to follow instructions, so it follows the instructions it finds, wherever they came from. And the user's text can therefore modify or override the system prompt. This was recognised early, and filtering input and output gives partial mitigation, but only partial.

The lecture spends real time on the comparison with SQL injection, because the comparison is instructive in both directions . A login page that builds its query by pasting the submitted username into a string has exactly the same shape: a trusted query template, an untrusted value, and one flat string handed to an interpreter that cannot tell which part it is supposed to trust. An attacker who supplies a value containing query syntax rather than a name changes the meaning of the statement rather than its data, and the server executes the result.

What matters is the fix and why it does not carry over. SQL injection is solved by parameterized queries . The application sends the query template and the argument values through separate channels, so the database engine never has to guess where the template stops and the data begins. The structure of SQL is what makes this possible: there is a grammar, so there is a boundary to enforce.

Careful There is no parameterized natural language. A prompt has no grammar that separates instruction from data, so there is no equivalent of binding a parameter. This is the reason prompt injection has no clean fix while SQL injection does, and it is the single most important point to carry into the rest of this section.

Rung two: one agent, and the tools it trusts

Now give the model tools. The lecture's example is an email and calendar manager . The user states a goal such as reading their email and scheduling meetings where needed. A planner turns that into a plan, including the criteria for deciding when a meeting is required. An orchestrator carries the plan out: it asks the email client to read messages, decides whether meetings are needed, then updates the calendar and sends invitations. This is the agent plus tools pattern.

The attack does not touch the user's input at all . The attacker simply sends the user an email whose body is addressed to the machine rather than to the person, asking that certain instructions be passed back to the calling agent. The email client reads it and returns the text to the orchestrator as tool output. The orchestrator, or the planner it consults, treats that text as part of its working context and may act on it. The victim is the system and its user, the attacker interface is simply the ability to send an email, and the goal is an action harmful to the user, such as sending data somewhere it should not go.

The structural point is that tool output arrives from a trusted component of the system, the email client, but its content came from outside. The channel is trusted and the payload is not, and nothing in the pipeline records the difference.

How common is this in the wild? The lecture cites an empirical study that analysed 1.2 billion URLs across 24.8 million hosts and validated 15,300 instances of injected instructions on 11,700 pages . Two findings stand out. A small number of reused templates account for most of what was found, which suggests copying rather than invention. And roughly 70 percent of the instructions sit in parts of the page a person never sees, such as headers, comments and metadata, with many of the remainder hidden by rendering tricks. The text is written for machines, not for readers.

Rung three: agents that read each other

Multi-agent systems add a specialised web surfer, a code runner and others, coordinated by an orchestrator, often through a framework . They plan, delegate, adapt and replan. The lecture draws out the consequence that matters : agents now reason about each other's output rather than about the environment directly, and they extend implicit trust to the other agents in the system. That creates a threat vector that does not exist in a single-agent design, since one agent's output can mislead another agent that reads it.

The walkthrough is worth following, because the attack is unusually mundane . It is described here at the level of what each component believes and does, which is what makes it instructive.

The user asks the agent to visit a page and report what it finds. In a realistic setting the user does not name the page at all: an ordinary query leads to a search, which leads to a site the attacker happens to control.

The orchestrator forms a plan to visit the site and assigns the step to the web surfer. Nothing unusual has happened yet.

The site does not serve the page. It serves something that looks like an access control error, together with text presented as a helpful suggestion for how to obtain access. The web surfer retrieves it and returns it to the orchestrator, exactly as it would return any other page content.

This is the hinge. The orchestrator's whole purpose is to adapt when a step fails, so it consults the plan and rewrites it in line with the error it was handed. The attacker is now editing the plan, using the system's own recovery logic to do it.

The revised plan instructs the code runner to fetch the resource the false error pointed at, and then to run it. The system was designed to be able to do both of these things, and it does them, in the user's execution context.

The lecture then asks which agent capabilities the attack actually depends on . There are three: the agent must be able to retrieve information from resources other people control, it must update its plans in response to unexpected errors or findings, and it must be able to write and run code to act on what it discovers. The uncomfortable observation is that all three are reasonable capabilities for an agentic system, and arguably the point of building one. Preventing this class of attack is therefore not going to be easy.

Definition Confused deputy: a component that holds legitimate authority is persuaded by a less privileged party to exercise that authority on its behalf. The term comes from a 1988 paper, and it describes this situation exactly . The web surfer reads an untrusted site and reports to the orchestrator; the orchestrator receives that report from a trusted component of its own system and acts with the user's authority.

Two failures that look alike and are not

The lecture is careful to separate control flow hijacking from indirect prompt injection, because they arrive through the same door . In indirect prompt injection, a malicious prompt instructs the victim model to do something. In control flow hijacking, malicious content reprograms the agent, which then reaches any tool or resource that agent can reach. The difference is scope: the first subverts a response, the second subverts a plan, and a plan commands the whole toolset.

Victim: the system. Attacker interface: the ordinary user input box. Goal: responses the system prompt forbids.

Trusted and untrusted text are concatenated before the model sees them. Input and output filtering helps, and it is genuinely partial.

Victim: the system and its user. Attacker interface: any content the system's tools might fetch, such as an email or a web page. Goal: actions harmful to the user, such as data exfiltration.

The attacker never interacts with the agent. Most instructions found in the wild are hidden from human readers.

Victim: the system and its user. Attacker interface: a site or file the agentic system visits. Goal: behaviour the design forbids, up to running code in the user's execution context.

The content is not aimed at the model's answer but at the orchestrator's plan. The recovery logic that makes the agent robust is the mechanism that is abused.

The fourth item on the lecture's outline: agents behaving exceptionally when they meet conditions nobody anticipated . The deck lists it alongside monitoring and mitigation, asking whether agentic judges can detect the error and whether conventional or AI-based repairs exist. It is posed as an open question rather than answered.

How far the problem generalises

A single demonstration proves little, so the lecture reports how widely the effect holds . It is not confined to one multi-agent framework, so it is not simply a poor implementation. It is not confined to one model size or one developer, so it is not an artefact of a single training recipe, and the models inside these agents are mostly safety aligned. It is not confined to one orchestration method, one input modality, one phrasing of the user's query, or one flavour of fake error, with fake Python and web server errors working as well as a generic access denied message.

Two further results deserve emphasis. The attack carries across modalities, including screenshots of errors, without needing carefully crafted adversarial images . And, stated plainly on the same slide, more capable models were found to be more vulnerable than less capable ones, which inverts the comfortable assumption that capability and safety improve together.

On consequences, the lecture reports a tested data exfiltration goal against a framework with a built-in memory module: build a profile of the user from what the memory holds and forward it to the attacker . The lesson drawn is that sandboxing and ephemeral execution environments are not sufficient protection when those environments contain sensitive user data. At the top of the severity scale the deck places complete adversarial control of the user's device or container, and full data exfiltration .

Where this leaves the defender

The honest summary is that this session is about attacks and vulnerabilities, and the lecture keeps the defensive material deliberately modest. Filtering input and output helps against direct injection and is explicitly described as partial. Monitoring and mitigation appear as questions rather than as solutions: whether an agentic judge can reliably detect that something has gone wrong, and whether repairs, conventional or AI-based, can be applied once it has .

What the material does support is a way of thinking. The three capabilities that make the attack possible are the same three that make the agent useful, so the design question is not how to remove them but how to bound them: which resources an agent may reach, which actions need a human decision before they happen, and whether the system records where a piece of text came from before acting on it. None of that is a solved problem, and the lecture does not pretend otherwise.

Key idea The ladder from chatbot to multi-agent system is a ladder of authority, not of cleverness. The attacks get more serious not because they become more sophisticated, but because each rung hands the same trick a larger set of things it can do.

Why is provenance so hard to keep once text enters a model?

A conventional system can label data at its boundary and carry the label along, because the data stays in identifiable pieces. Text handed to a language model is flattened into one sequence, and the model's output is new text conditioned on all of it. There is no reliable way to recover, from the output alone, which parts of the input drove which parts of the answer. That is why the boundary has to be enforced around the model, by limiting what its output is allowed to trigger, rather than inside it.
