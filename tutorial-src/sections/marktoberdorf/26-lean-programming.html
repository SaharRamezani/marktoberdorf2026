Programming and Proving in Lean

Lecture by Leonardo de Moura, the second of his four on Lean, written from his deck Programming and Proving in Lean. No recording of this session was available, so everything below is drawn from the slides and cited to them, and nothing is claimed about what was said in the room. The deck is unusually code-heavy, which is the point of it, so the code is reproduced here rather than paraphrased.

The recap slide sets out a plan in four steps: inductive types, where Nat, List and Or all come from; structures and type classes, meaning how Lean organises interfaces; Lean as a programming language, meaning monads, IO and performance; and building a language, meaning expressions, an evaluator and an optimiser . That is really two halves fastened together: an ordinary functional programming course, and then a small optimiser proved correct in the same file, in the same language, with no export step in between. Everything the reader has met so far in this tutorial keeps those two activities apart; Lean does not.

Data and patterns, quickly

Section 25 covered inductive declarations, definition by cases and structural recursion, so the opening slides here are a recapitulation. The line worth carrying forward is the deck's own summary: an inductive type is freely generated by its constructors, meaning those are all the values and they are distinct, and the same three ingredients return on every slide, constructors, pattern matching and structural recursion . Bool is not a primitive bolted on beside the type theory; the two-constructor declaration is the actual definition in the core library.

What is new here is how much pattern matching is allowed to do. Patterns nest, literals are patterns, overlapping cases are resolved first-match-wins, and n + 2 is a legitimate pattern meaning two successors .

def fib : Nat → Nat
  | 0     => 0
  | 1     => 1
  | n + 2 => fib (n + 1) + fib n

#eval fib 10
-- 55
example : fib 7 = 13 := rfl

def describe : List Nat → String
  | []          => "empty"
  | [x]         => s!"one element: {x}"
  | x :: _ :: _ => s!"starts with {x}"

#eval describe [5, 7, 2]
-- "starts with 5"

Two things in that block recur for the rest of the lecture. #eval runs the function and prints the answer, so a definition can be tried the moment it is written. And example : fib 7 = 13 := rfl is a proof whose whole justification is the word rfl: both sides compute to the same value. A test and a theorem sit two lines apart and cost about the same to write, which is the lecture's thesis in miniature. The slide also repeats section 25's point that match is not primitive: Lean compiles it to recursors .

Every function terminates, and what to do when it does not

The reason totality is not negotiable is stated bluntly: a nonterminating loop : False would prove anything, so a language whose types are also propositions cannot admit one . Structural recursion, where the recursive call is on a subterm, is checked automatically, and len, add and fib are all structural. The deck's phrasing is that termination checking has been running behind every def so far, invisibly.

Two slides then handle the cases where it does not run invisibly. The first is a recursion that does not descend into a subterm but does decrease.

def gcd' (a b : Nat) : Nat :=
  if h : a = 0 then b
  else gcd' (b % a) a
termination_by a
decreasing_by exact Nat.mod_lt _ (Nat.pos_of_ne_zero h)

#guard gcd' 12 20 = 4

termination_by names the measure and decreasing_by proves it decreases, though the deck notes Lean often finds both by itself and that this is a case where it needs the hint. A reader who came through sections 1 to 4 will recognise Why3's variant clause under another name, split into its two halves: the term, and the obligation that the term goes down. Section 25 drew that comparison; what is new is the split being visible in the syntax. Note also if h : a = 0, the dependent if: the else branch is handed a proof h that a is not zero, and decreasing_by uses exactly that proof.

The second escape hatch is for functions where nobody knows whether they terminate.

partial def collatzSteps (n : Nat) : Nat :=
  if n ≤ 1 then 0
  else if n % 2 == 0 then 1 + collatzSteps (n / 2)
  else 1 + collatzSteps (3 * n + 1)

#eval collatzSteps 27
-- 111

partial def opts out of termination checking, and the price is precise: you can run it, but you cannot unfold it in proofs, which is what keeps the logic sound . The definition becomes an opaque constant to the prover. The deck lists two middle grounds between full checking and full opacity, an explicit fuel parameter and partial_fixpoint, the latter giving partial correctness reasoning about possibly nonterminating functions.

Structures, type classes, and laws

A structure is an inductive type with one constructor and named fields . Two conveniences come with it. { q with x := q.x + 1 } builds an updated copy, with no mutation and, the deck promises for a later lecture, often no copy either. And declarations live in namespaces, so dot notation finds them from the type: p.normSq means Point.normSq p, as xs.map f and e.eval σ will later.

Type classes arrive through a problem statement rather than a definition. + has to work for Nat, Int, Float, BitVec 32 and matrices, with different code for each, so somebody has to pick; and separately, one wants to write functions that work for any type that has + . The answer to both is one mechanism: interfaces whose implementations are found by the elaborator.

class Add (α : Type u) where
  add : α → α → α

instance : Add Point where
  add p q := { x := p.x + q.x, y := p.y + q.y }

def a : Point := { x := 1, y := 2 }

#eval a + a
-- { x := 2, y := 4 }

def sum3 [Add α] (a b c : α) : α := a + b + c

#eval sum3 2.0 1.0 3.0
-- 6.000000

The class is a structure and an instance is a value of it, registered for instance search; [Add α] is an implicit argument that search fills in, which is why sum3 works at every type with a +. Instances also require instances, and that is where the mechanism starts paying: given Add α the deck defines Add (Pair α), and search chains them, finding Add (Pair Point) from the Add Point written by hand . Mathlib runs on this: over 1,500 classes and over 20,000 instances.

Slide 15 lists the classes one meets daily, and doubles as an explanation of notation seen earlier: OfNat makes the literal 2 mean OfNat.ofNat 2 at whatever type is wanted, BEq and DecidableEq are the equality tests #guard uses, Repr and ToString are what #eval prints through, and GetElem is the class behind the xs[i] and xs[i]? notation, which matters in a moment. Writing those by hand would be tedious, so deriving Repr, BEq, DecidableEq generates them .

The last slide of this run is the one that separates Lean's classes from an ordinary language's interfaces: a class may carry a law as a field, and the law is a proof obligation on every instance.

class Semigroup (α : Type) where
  op : α → α → α
  assoc : ∀ a b c, op (op a b) c = op a (op b c)

instance : Semigroup Nat where
  op := (· + ·)
  assoc := Nat.add_assoc

-- Generic code using the proof field
open Semigroup in
example [Semigroup α] (a b c : α) : op a (op b c) = op (op a b) c :=
  (assoc a b c).symm

Instance search is now doing something no interface resolution in a conventional language does: it delivers a proof along with the operation, and generic code gets the law for free. The deck says this is how Mathlib's algebraic hierarchy works, and how the grind tactic finds its theory solvers.

Effects with types

The programming half of the lecture ends with monads, and it introduces them by writing bad code first. The task is to fetch the first and third elements of a list, both of which can fail, using the xs[i]? lookup that returns an Option.

Return the first and third elements of a list as a pair, or nothing if either is missing. The type says it: def firstThird (xs : List α) : Option (α × α). The lookup xs[0]? comes from the GetElem class of slide 15 and has type Option α.

Case on the first lookup, and inside the some branch case on the second. The slide's own title for it is the pyramid of doom .

def firstThird (xs : List α) : Option (α × α) :=
  match xs[0]? with
  | none => none
  | some a =>
    match xs[2]? with
    | none => none
    | some c => some (a, c)

Every step can fail, and every step repeats the same plumbing: match, handle none by returning none, continue with the value. Two lookups already means two copies. The observation on the slide is that this shape, sequence computations and propagate failure, is a monad, and that Option, IO, StateM and parsers all have it.

The class has two operations, and the Option instance is the plumbing lifted out of version 1 verbatim.

class Monad (m : Type u → Type v) where
  pure : α → m α
  bind : m α → (α → m β) → m β

instance : Monad Option where
  pure := some
  bind x f :=
    match x with
    | none   => none
    | some a => f a

x >>= f is notation for bind x f, and pure wraps a value. The none check now lives in one place, so firstThird never mentions failure at all .

def firstThird (xs : List α) : Option (α × α) :=
  xs[0]? >>= fun a =>
  xs[2]? >>= fun c =>
  pure (a, c)

The lambdas are noise, so do hides them. let x ← e sequences, and failure short-circuits automatically.

def firstThird (xs : List α) : Option (α × α) := do
  let a ← xs[0]?
  let c ← xs[2]?
  return (a, c)

#eval firstThird [10, 20, 30, 40]
-- some (10, 30)
#eval firstThird [10]
-- none

Nothing about version 3 mentions Option in its body. do works for any monad, with the Monad instance supplying the plumbing, which is why the next two slides can reuse the identical notation for mutable state and for real input and output without changing a keyword.

The reuse is the payoff. StateM S α is defined as S → α × S, so a stateful computation is a pure function from the initial state to the result paired with the final state; pure a leaves the state alone, bind feeds the result and the updated state onward, and get and set become one-liners . Then the same do, with a different effect underneath:

def double : StateM Nat Unit := do
  let s ← get
  set (s + s)

example : StateM Nat Unit = (Nat → Unit × Nat) := rfl

#eval double.run 21
-- ((), 42)

That example proved by rfl is making a point rather than checking anything: the state monad really is the function type, definitionally, and running a stateful program really is function application. IO then gets the same treatment, effects visible in the type and sequenced by the same do. A Lean program is a main : IO Unit built by lake, and the compiler, language server and build system are themselves Lean programs .

This is a real departure from sections 1 to 5. Why3 and Viper give you mutable state as a language primitive and reason about it with weakest preconditions or with separation logic assertions about a heap. Lean has no state to reason about: state is a value threaded by a function, and the notation that makes it look imperative is a macro over bind.

Building a language

The second half of the deck is announced by a divider slide: syntax trees, an evaluator, an optimiser, and then we prove things . The object language is arithmetic with literals, variables, + and *, and the slide's comment is that inductive types are made for syntax trees.

inductive Expr where
  | const (n : Int)
  | var   (x : String)
  | add   (a b : Expr)
  | mul   (a b : Expr)
  deriving Repr, BEq

def State := String → Int

def State.init : State := fun _ => 0

def State.get (σ : State) (x : String) : Int := σ x

def State.set (σ : State) (x : String) (v : Int) : State :=
  fun y => if y = x then v else σ y

A program state is a total map from variable names to values: .get reads and .set updates by shadowing. The reason given for the total map is proof engineering rather than modelling, namely that it leaves no error cases to thread through the proofs , a saving anyone who has carried a partiality side condition through a Why3 verification will recognise. The slide also separates this State from StateM's get and set: this one is the value a stateful program manipulates, the S in StateM State α.

The evaluator is then ten lines, and the deck calls it a definitional interpreter: the semantics of the language, as a program.

def Expr.eval (σ : State) : Expr → Int
  | .const n => n
  | .var x   => σ.get x
  | .add a b => a.eval σ + b.eval σ
  | .mul a b => a.eval σ * b.eval σ

#eval (Expr.add (.var "x") (.const 3)).eval (State.init.set "x" 10)
-- 13

Writing terms as Expr.add (.var "x") (.const 3) gets old, so the next slide adds concrete syntax with five macro rules that reuse Lean's own parser, plus two more that give the State API a notation of its own: σ⟦x⟧ expands to σ.get "x" and σ⟦x := v⟧ to σ.set "x" v . The payoff is a line that reads like the language it is about:

syntax "[Expr|" term "]" : term

macro_rules
  | `([Expr| $n:num])   => `(Expr.const $n)
  | `([Expr| $x:ident]) => `(Expr.var $(Lean.quote x.getId.toString))
  | `([Expr| ($e)])     => `([Expr| $e])
  | `([Expr| $a + $b])  => `(Expr.add [Expr| $a] [Expr| $b])
  | `([Expr| $a * $b])  => `(Expr.mul [Expr| $a] [Expr| $b])

#eval [Expr| x + 3 * y].eval (State.init⟦x := 2⟧⟦y := 4⟧)
-- 14

The optimiser is constant folding, structured as one smart constructor per operation: recurse first, then fix up. mkAdd drops a zero on either side, mkMul drops a one and absorbs a zero, and Expr.optimize is the obvious traversal that calls them . Then come the tests.

def mkAdd : Expr → Expr → Expr
  | .const 0, b => b
  | a, .const 0 => a
  | a, b => .add a b

def Expr.optimize : Expr → Expr
  | .const n => .const n
  | .var x   => .var x
  | .add a b => mkAdd a.optimize b.optimize
  | .mul a b => mkMul a.optimize b.optimize

#guard [Expr| 0 + x].optimize == [Expr| x]
#guard [Expr| 1 * (x + 0)].optimize == [Expr| x]
#guard [Expr| 0 * (x + y)].optimize == [Expr| 0]
#guard [Expr| x + 2 * 3].optimize == [Expr| x + 2 * 3]

#guard evaluates at compile time, so the file does not build if a test fails. The verdict on it is the hinge of the lecture: tests catch bugs early and cheaply, but optimize has infinitely many inputs, and for every input we need a theorem . The next divider is titled, exactly, From Tests to Theorems.

From tests to theorems

Proofs about programs start where the programs did, with the constructors. induction xs gives one goal each, and the cons goal gets the induction hypothesis ih for the tail; the slide sets it beside the case analysis of the previous lecture, saying induction is cases plus hypotheses for the recursive arguments .

theorem len_append (xs ys : List α) :
    len (xs ++ ys) = len xs + len ys := by
  induction xs with
  | nil => simp [len]
  | cons x xs ih => simp [len, ih]; lia

theorem rev_rev (xs : List α) : rev (rev xs) = xs := by
  induction xs with
  | nil => rfl
  | cons x xs ih => simp [rev, rev_append, ih]

Two tactics carry most of the weight. simp [len] unfolds by the defining equations and rewrites; lia decides linear integer arithmetic and finishes the leftover goal. The instruction is to use lia freely and not prove a + 1 ≤ b + 1 by hand, and its companion calc writes chains of equalities and inequalities the way one would on paper . The other lesson is structural: rev_rev needs rev_append, which needs the library's lemmas about ++. A development is a lemma chain .

Applied to the optimiser, that means one lemma per helper function, each saying that the smart constructor means what the plain constructor means.

theorem mkAdd_eval (a b : Expr) (σ : State) :
    (mkAdd a b).eval σ = a.eval σ + b.eval σ := by
  unfold mkAdd
  split <;> simp [Expr.eval]

theorem mkMul_eval (a b : Expr) (σ : State) :
    (mkMul a b).eval σ = a.eval σ * b.eval σ := by
  unfold mkMul
  split <;> simp [Expr.eval]

split performs the case analysis of the match inside mkAdd, and <;> applies the following tactic to every goal it produced, collapsing three near-identical bullet lines into one. The deck's design rule for such lemmas is that good simp lemmas rewrite toward a normal form, which here is plain arithmetic on evaluations. With those two in place, the main theorem is one simp per case:

theorem optimize_correct (e : Expr) (σ : State)
    : e.optimize.eval σ = e.eval σ := by
  induction e with
  | const n => rfl
  | var x   => rfl
  | add a b iha ihb => simp [Expr.optimize, mkAdd_eval, Expr.eval, iha, ihb]
  | mul a b iha ihb => simp [Expr.optimize, mkMul_eval, Expr.eval, iha, ihb]

Without the helper lemmas, the slide notes, each branch would need a nested case analysis, and it invites the reader to try. Its closing line is the one to keep: the lesson is about structuring definitions and lemmas, not about tactic tricks, and this habit is most of proof engineering .

The ladder of automation

The same theorem is then proved three more times, each shorter. The first improvement changes what the induction follows. induction e follows the type; fun_induction Expr.optimize follows the definition, giving one case per defining equation, with the match already split and an induction hypothesis for each recursive call . The slogan is that proofs about a function should follow the function.

theorem optimize_correct₂ (e : Expr) (σ : State) :
    e.optimize.eval σ = e.eval σ := by
  fun_induction Expr.optimize <;>
    simp_all [Expr.eval, mkAdd_eval, mkMul_eval]

theorem optimize_correct₃ (e : Expr) (σ : State) :
    e.optimize.eval σ = e.eval σ := by
  fun_induction Expr.optimize <;> grind [Expr.eval, mkAdd.eq_def, mkMul.eq_def]

Two coda slides guard against reading the ladder as a promise that automation removes thought. Proving that optimising twice changes nothing needs case analysis on what the smart constructors returned, and the fix is to hand grind the full match equation with mkAdd.eq_def . The last example proves a plain recursive sum equal to its tail-recursive version; the recursive call changes the accumulator, so the lemma must generalise it, with induction n generalizing acc . No tactic finds that for you: it is a choice about the statement, made before any tactic runs.

What to take away

The summary slide compresses the lecture into four lines: inductive types plus pattern matching plus structural recursion make up the whole language, including its logic; type classes organise interfaces and instance search composes them; monads and do give effects with types, in Option, StateM and IO; and proof engineering means helper lemmas, fun_induction and generalising the invariant . The exercise file walks the same path, ending with the optimiser: implement it, prove it correct, and then, marked harder, prove it idempotent .

One orientation is worth stating plainly. In Why3 and in Viper the program, the specification and the proof live in three places, joined by a verification condition generator and discharged by an external solver. Here they are all definitions in one file, and #eval, #guard and theorem optimize_correct differ only in which keyword starts the line. What that buys is the ladder above; what it costs is that the automation is a tactic you invoke rather than a solver behind a door, which is why the next lecture opens up simp, grind and bv_decide.
