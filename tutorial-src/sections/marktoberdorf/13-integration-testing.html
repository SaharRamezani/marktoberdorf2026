Integration Testing: Design Faults in Disguise

Alexander Pretschner, TUM, fortiss and bidt. From the deck "(Integration Testing and) Scenario-Based Tests for Cyber-Physical Systems: Autonomous Driving Systems", joint work with Michael Wolf, Florian Hauer, Nicola Kolb, Tabea Schmidt and Thomas Hutzelmann.

Every unit has passed its own tests. The system is assembled, and it fails. What exactly was the integration test supposed to look for? This lecture answers that question by building a small formal model of what composition promises, deriving four obligations that any composition has to discharge, and reading the four obligations as four classes of fault. The conclusion is uncomfortable: most integration faults are not coding errors. They are design faults or infrastructure faults, and they exist because the specifications the units were tested against left something out.

What is being tested, and at which level

The lecture sets its scope in four lines: this is about testing rather than formal verification, about integration and system level rather than component level, about continuous and hybrid behaviour rather than purely discrete behaviour, and about situations where there is no specification to test against, which the deck calls testing the untestable.

Definition A test case is an input, an expected output, and a set of environment conditions. Testing means applying the input to the system under test and comparing the actual output to the expected one. A good test case detects a potential defect with good cost effectiveness, which is to say it reduces risk per unit of effort spent.

Testing can never show the absence of defects. What it buys in exchange is that it scales, that it applies to entire systems including their hardware rather than to single components, and that depending on the test level it runs under more realistic circumstances with fewer strong assumptions. That last point matters here, because software does not run on an abstraction. It runs on libraries, a virtual machine, middleware, an operating system and hardware, connected to further systems, sensors and actuators, and many of those parts arrive without source code, so no analysis of your own code can settle what they will do.

The standard test levels are unit, integration, system and acceptance. The deck maps them onto what is actually being checked: technical software functions get unit tests, subsystem tests and horizontal software integration tests, and since their behaviour is mostly discrete, classical unit testing frameworks are adequate. User functions get software-in-the-loop tests, because their behaviour is continuous and needs co-simulation, for example with FMUs. Systemic properties get software-in-the-loop or hardware-in-the-loop tests.

Integration rests on shared knowledge about the world

The starting picture is a single system with an input and an output, surrounded by two rings: explicit knowledge about the world, written down in interface descriptions, APIs and data models, and implicit knowledge about the world, the assumptions nobody wrote down. Now split that system into subsystems. The two rings do not shrink, but the number of places where the knowledge has to be shared multiplies, because every internal boundary is a boundary across which assumptions must agree.

From there the challenge has three shapes. Different stakeholders can hold different understandings of the same interface. An understanding can be wrong. Or it can be incomplete, in two grades: sometimes realistically foreseeable, as with certain system properties, and sometimes not, as with externalities, feature interactions and emergent properties. The word "unit" is not fixed either: it can mean a class, a task, a microservice or an electronic control unit, and the development process, who runs the test (the developer or the system integrator) and the class of system all change what integration means in practice.

The standards do not agree either

Two entries in ISO/IEC/IEEE 24765:2017(E) pull in different directions. "Integration test" is defined as the "progressive linking and testing of programs or modules in order to ensure their proper functioning in the complete system". "Integration testing" is defined as "testing in which software components, hardware components, or both are combined and tested to evaluate the interaction among them". ASPICE does not define the term at all; its process SWE.5 asks that components be verified against the detailed design, that the software elements be integrated, and that the integrated elements comply with the software architecture including the interfaces between them, and SYS.4 says the analogous thing at system level.

Practitioners are no more consistent. The deck collects what engineers actually say, and the statements contradict each other: "integration tests test if we have had the same understanding", "unit tests have no state, integration tests do", "unit tests are technical, integration tests test user functionality", "regression tests can only be used for units", "we can't really distinguish between integration and (sub)system tests". The rest of the lecture replaces this list with a definition that can be applied to a concrete failure and give a definite answer.

Development as a chain of refinements

Idealised, development is a chain. Requirements become functional system requirements, those become subsystem specifications, those become component architectures, those become software implementations, and those become deployments.

R ⇝ F1 + … + Fk ⇝ S1 + … + Sℓ ⇝ J1 + … + Jm ⇝ I1 + … + In ⇝ D1 + … + Do

The "+" in that chain is not one operator. Depending on the level it means function composition, logical conjunction, function calls or message protocols. Two properties of the chain drive everything that follows. First, the description at each level is necessarily partial. Second, each next level removes some of that partiality and, in doing so, adds assumptions about the context in which the described artefact will sit. Those added assumptions are the implicit world knowledge. And, as the deck notes plainly, the world is not a waterfall: the chain is a way of talking about the dependencies, not a claim about the schedule.

If the chain were linear and correct by construction, integration testing would be unnecessary: transitivity would give us that the deployed system satisfies the requirements. It is not, so we have to check, and checking the deployed system against the requirements directly is far too difficult. The right branch of the V breaks the check up. Unit tests establish that a deployment satisfies its component architecture; integration testing then picks a subset of components and their corresponding specifications and checks that subset against them. The levels at which such a subset can be picked are unit, horizontal software integration, vertical software and hardware integration, software-in-the-loop and hardware-in-the-loop, plus horizontal hardware integration.

Why two correct units can still fail together

Here is the question in its sharpest form. If I1 satisfies its specification J1 and I2 satisfies J2, how can the composition of I1 and I2 fail to satisfy the composition of J1 and J2? The lecture's answer is that we never actually showed the two premises.

Testing samples the input space, it does not prove anything about all of it. Beyond that, a test implicitly encodes extra assumptions Ai that come from the deployment context it was run in, and the specification itself makes implicit assumptions W about the runtime environment, while the real environment is W_real. So what a unit test establishes is not the clean implication at all, but something weaker, at three levels at once:

[ Ii + Ai + W_real ] ⊨ [ Ji + W ]

Formal verification improves on this by proving instead of sampling, and by forcing the assumptions to be written down. That is a real gain, but it is not a cure: the stated assumptions may still be wrong or partial, because specifications are abstractions.

What do these assumptions look like? The deck separates them into assumptions between components and assumptions that cut across components and live in the infrastructure.

Key idea In testing, these assumptions are almost always implicit, and for a structural reason: each harness constructs its own unit's environment, so the Ai hold automatically and nobody ever has a reason to write them down. In a proof the Ai must be stated to get the proof through, which at least makes them visible. Hyrum's law says the rest: what matters in the end is the observable behaviour, not the contract.

Four obligations, four fault classes

Once the weak form of the unit result is written out, the question of what composition needs becomes answerable. For the composed claim to hold, four things must be true.

  1. (i) The deployment context establishes the assumptions: [D] ⇒ [A1] and [A2].
  2. (ii) The platform satisfies its own description: [W_real] ⇒ [W].
  3. (iii) Each implementation satisfies its own specification under its assumptions: [I1 + A1] ⊨ [J1] and [I2 + A2] ⊨ [J2].
  4. (iv) The composition operator is compositional: [X + Y] = [X] and [Y].

Definition These four obligations are the four fault classes. An integration fault is the breach of at least one of them.

The split between design and infrastructure is not arbitrary. An integration fault cannot be canonically attributed to one component, and a fault attributable to no component has exactly two possible homes: the relation between the units, which the design step fixed, or the layer beneath them. Read against the V model, this is why high-level design faults show up as integration faults. Each subsystem specification may be correctly derived from its function, and yet their product fails to capture the conjunction of the functions, because the specifications were too liberal or their design decisions contradict each other.

The tabs below give the detail for each class.

Assumptions not established. Two sub-cases. In the first, the assumptions are contradictory in themselves: unit 1 was verified under "the payload is JSON", unit 2 under "the payload is XML". No architecture can establish both, so the failure is deterministic and is caught on the first end-to-end run. In the second, the assumptions are jointly satisfiable, nothing forbids them, and yet they are incompatible in practice: I2 emits values with property P2, I1 was verified under input assumption P1, and P2 does not imply P1. A single input from P2 outside P1 is enough, so the system can survive for months, until the first apostrophe in a surname or the first 29 February. The fault was there on day one; only the witness was missing. Other instances of P: units of measurement (ground software in pound-force seconds, navigation in newton-seconds, both modules correct), frequency, byte order, timing, assumptions about call history. Test question: if the platform keeps exactly to W, does the fault go away? If no, it is class (a). Attribution: none, because there are three equally admissible repair sites, namely loosen I1, tighten I2, or insert an adapter.

The platform does not satisfy the assumption. The design step was correct under W, but W describes reality wrongly: communication is asynchronous where synchronous was assumed, latency exceeds the stated bound, the channel is lossy, clocks drift, messages are duplicated or reordered. There are two repairs, and one of them is a reclassification. Either fix the platform by configuration or replacement, or correct W to the truth, at which point the same fault reappears as a now visible design fault and is handled as class (a). Test question: does the fault vanish if the platform satisfies W exactly? If yes, it is class (b). Attribution: none, because it sits beneath all units, in no component at all. Example: W says FIFO per channel, and the deployed middleware uses multipath routing and delivers out of order.

The unit fails its own specification. This is not an integration fault at all, even though it surfaces during integration. It is either an ordinary bug, or an over-idealised specification that no implementation on this machine can satisfy: the specification computes in the real numbers where the machine has IEEE-754 floating point, or it assumes unbounded memory. It surfaces at integration because the offending input is one the unit test never generated, and only the partner component or the platform's timing makes it reachable. Attribution here is settled: exactly one component violates its own specification in the given W_real, the artefacts single it out, and nothing else has to move. That is the dividing line.

The composition operator is not compositional. The meaning of the composed system is not the conjunction of the meanings of the parts. This is a fault in the frame itself rather than in any artefact within it, so attribution is not merely undecided, it is impossible. The repairs are correspondingly heavy: a different formalism, or a different resource architecture. This is also the one obligation a test cannot reach at all; only a proof can.

Worked example: the customer billed twice

The lecture works one example in full, and it is worth following line by line, because everything in it is individually correct.

Component I1 offers an operation charge(order). Its implicit assumption A is that each order-ID reaches it at most once. This is a perfectly reasonable thing to assume, and it is not written anywhere.

The unit test calls charge once. A is trivially satisfied inside the harness, so no test ever fails, and nobody ever has a reason to write A down. I1 passes.

Component I2 calls I1 over a channel that retries on timeout, so delivery is at-least-once rather than exactly-once. That is the part W did not say. The middleware behaves exactly as described; the description was simply too abstract.

A retry delivers the same order-ID twice, A is violated, and the charge is applied twice. Both components satisfy their specifications. No unit test could have caught this, because no unit test constructs the environment that breaks A.

The architecture attached a component that requires exactly-once delivery to a channel that does not provide it. Note where this leaves attribution: the repair can be a deduplication key in the protocol, or making I1 idempotent, or inserting an adapter. All three are legitimate. That is an architectural decision, not a bug fix.

Is the billed-twice example class (a) or class (b)?

It depends on what W claimed, and the lecture's own reclassification rule settles it. Apply the test question: if the platform delivered exactly once, as W described, would the fault go away? Yes, so as stated it is class (b), an infrastructure fault. Now correct W to the truth, so that W states at-least-once delivery. The platform now satisfies its description, obligation (ii) holds, and the same failure reappears as a breach of obligation (i): the design attached a component needing exactly-once to a channel that does not provide it. It has become a class (a) design fault. That is exactly what the deck means when it says one of the two repairs for class (b) is a reclassification.

What makes an integration fault an integration fault

With the classes in place, the lecture can state the criterion that the practitioner quotations were groping for.

Definition A fault is an integration fault if it cannot be attributed to any single component: each part meets its own specification, and the specifications do not determine where to intervene. A unit fault, by contrast, is attributable: exactly one component's implementation violates its own specification, the artefacts themselves single it out, and the diagnosis is finished when they do.

Careful This does not say the repair has to touch several components. It usually can be done in any one of them. If two specifications are silent about the wire format and the implementations disagree, either side can be changed and no specification needs to move. That is precisely the point: because the specifications leave the choice open, choosing is a design decision and not a diagnosis.

The criterion also resolves the disagreement between the two ISO entries: they are not competing definitions, they name two different targets. The first, about proper functioning in the complete system, is testing for design faults, that is, for conflicting assumptions where every part meets its own specification and the composition still fails. The second, about the interaction among combined components, is testing for communication and infrastructure faults, where the connection itself, the middleware, the bus or the timing, does not behave as the design assumed. So JSON against XML, or metres per second against kilometres per hour, is a design fault and not a communication fault.

What a test buys and what a proof buys

The four obligations also make it possible to say precisely what each verification method can reach.

Test

  • Samples the input space and extrapolates, so it misses the offending input until something makes it reachable.
  • Scales to whole systems and to the real platform. It is the only method that observes W_real at all.
  • Needs an oracle only for the cases it actually runs, so the specification can stay informal.
  • The assumptions A live in the harness, unstated.
  • Cannot pass vacuously: a contradictory setup runs no cases.

Proof

  • Quantifies over the entire input range, with no extrapolation.
  • Scales in the input space but not in system size: cost grows with component complexity, and whole-system proofs stay rare.
  • Requires the specification, W and A to be stated precisely. This is often the real work, and often the real obstacle.
  • Forces part of the assumptions into the open, but only the part inside the model. Scheduler, clock, network, floating point and memory usually sit outside it.
  • Can pass vacuously.

Matched against the obligations: a proof is the strong instrument for (iii) across all inputs and the only instrument for (iv). A test is the only access to (ii), because (ii) is a claim about hardware that nobody can prove from a model of the code. A proof settles (i) if the assumptions are written down somewhere, and (iv) does not concern tests at all. Whatever the method, the abstraction hiding behind the assumptions may still miss faults.

No specification for the composition, so use negative specifications

A test is an input, an expected output and a set of infrastructure conditions, so a test requires a specification. For integrated components the obvious question is: against which one? There may well be specifications for named subsystems, but there is usually none for the composition of an arbitrary set of units, and it is not even clear what constitutes a subsystem. What remains is explorative matching of interfaces.

The lecture's first idea for filling the gap is to use potential faults as an implicit specification: instead of stating what the composition should do, state what must not be the case. If integration faults exist at all, the subsystem specifications are abstractions and therefore necessarily incomplete, and the aspects they left out can be catalogued.

Each cell is a family of negative specifications, and the lecture pins two of them to known failures. The Mars Climate Orbiter is the "unit of measurement" cell: the ground software worked in pound-force seconds, the navigation software in newton-seconds, and both modules were correct. Flaky tests are the "worst-case execution time against timeout" cell.

The catalogue also explains why the unit and integration boundary refuses to stay put. Because a fault is usually located in one unit, we could in principle reveal these integration faults with unit tests, if only we had sufficiently precise unit specifications. For that reason alone the boundary is blurred. For some failures there is genuinely no unique unit to blame, and the reason is the same throughout: unit specifications are partial, and refinements of them may be inconsistent with each other.

What integration testing cannot reach

Not every system failure is a unit fault or an integration fault, and the lecture fences off three cases this machinery does not cover. First, systemic or emergent properties do not follow from the conjunction of the subsystem specifications at all. Performance is one. Security is another, since a system is only as strong as its weakest link and confidentiality is not compositional. So is a functional property such as the minimum distance a drone must keep from its neighbours or from obstacles, illustrated with the SwarmLab drone swarm simulator of Soria, Schiano and Floreano (IROS 2020).

Second, the answer can depend on where you draw the system boundary. The parameters of an adaptive cruise control planner, its speed, acceleration and time distance, can be optimised perfectly well at unit level. But if the system is taken to be a string of vehicles rather than one vehicle, traffic string stability becomes a property of that system, and it may simply not have been considered. The lecture calls this a design fault, not an integration fault, and notes that it can be addressed by optimising against a system-level simulation of the cars in front (Hauer, Stern and Pretschner, ITSC 2019).

Third, feature interaction, illustrated with telephony. If T1 forwards to T2 and T2 forwards to T3, is a call to T1 forwarded to T3? If T1 is set to "do not disturb" and forwards to T2, which is not, is a call to T1 forwarded to T2? None of these has an answer in the individual feature specifications. This too is a design fault rather than an integration fault, and the underlying problem is the same: incomplete requirements for the overall system.

Bottom line

Integration problems arise for three reasons: a design fault that is only understood after implementation, a deployment problem where the hardware does not meet the assumptions of the software, or a deployment problem where the communication does not meet those assumptions. In all three, the assumptions that cause the trouble are implicit and not recorded in any specification.

Testing is risk-based and therefore defect-based, so integration testing has to target the specific faults that integration can produce: design faults and infrastructure faults. The underlying problem is not really a testing problem at all; it is a problem about specifications, abstractions and assumptions. Asked whether testing is the right remedy for that, the lecture answers no, and adds that it is the only realistic one. The practical consequence: use the fault classes to derive and to assess integration test suites, and use large language models to generate tests and to draft the missing subsystem specifications.

Key idea The five-line summary the deck opens and closes with. Integration rests on a shared understanding of the world: explicit contracts such as APIs and data models, plus implicit assumptions about timing, units, ranges and ordering. Integration faults surface only under composition, when every part meets its own specification and the system still fails. In principle the unit and integration boundary is artificial, since sufficiently complete specifications would catch these faults earlier, and the real gap is the missing specification. The first remedy is to test against negative specifications, cataloguing the faults composition can produce. The second is to surface the implicit background knowledge, where generative AI can help fill in the unwritten assumptions.
