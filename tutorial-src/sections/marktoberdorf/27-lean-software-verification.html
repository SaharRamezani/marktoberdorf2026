Software Verification in Lean

Leonardo de Moura, from the deck Software Verification in Lean, 49 pages. No recording of this lecture survives, so the deck is the only source and every claim below is cited to a page of it. Its own recap slide places it last in his series, after the foundations, the programming and proving, and the automation lectures.

Four lectures of this school wrote programs and then handed them to a tool that already knew Hoare logic. This one builds the tool. The deck takes a small imperative language, declares it inside Lean as ordinary data, gives it an operational semantics as an inductive relation, defines the Hoare triple over that semantics as a plain definition, proves the rules of Hoare logic as ordinary theorems, writes a verification condition generator as an ordinary Lean function, and then proves that function sound. Nothing in the chain is primitive, and nothing is taken on faith except the semantics itself and the kernel that checks everything above it. That is where the two halves of this tutorial join: sections 1 to 4 used a program logic from the outside through Why3, section 5 used one through Viper, and here the same machinery is visible from the inside, with a derivation for every rule. The deck then repeats the exercise with a shallow embedding, and closes on what it costs to make any of it scale.

Verification frameworks as Lean libraries

The opening quarter of the deck is a survey, and it is there to establish that the small development which follows is a scale model of something real. The framing comes from the course abstract, quoted on the slide: Lean's extensibility enables the construction of entire domain specific verification frameworks, including custom specification languages, proof strategies and automation pipelines, all within Lean itself, with no need for external tools or trusted code generators . The last clause is the one this lecture cashes out.

Five systems are named. SampCert is an open source Lean library of verified differential privacy primitives, deployed in AWS Clean Rooms, whose correctness arguments need Fourier analysis, number theory and topology out of Mathlib, and whose verified implementation replaced an earlier one and runs twice as fast . Waimea is a CompCert style verified compiler for AWS Trainium, around 500,000 lines of Lean, aimed at a target whose instruction set specification changes several times a week rather than a fixed one like x86; the Lean model doubles as a simulator shared by hardware and verification engineers . Kraken is a formal model of x64 for verifying sequential machine code, started at Google by Jonathan Protzenko, whose own lectures are sections 19 and 20 of these notes, together with Andres Erbsen . Veil verifies distributed protocols, offering push button verification through cvc5 and Z3 on decidable fragments with interactive Lean proofs when automation falls short, and its VC generator is proved sound against the semantics of its specification language . Strata is an extensible platform for formalizing language syntax and semantics, organised around composable dialects in the manner of MLIR, with a pipeline from Python, Java or JavaScript through Laurel and Strata Core to VC generation and SMT .

Key idea Every one of those systems has the same four part architecture . Embed the object language (Rust, a protocol language, an instruction set) in Lean. Give it a semantics, either a function or an inductive relation. Compute verification conditions. Discharge them with simp, grind, bv_decide or interactive proof. The rest of this lecture is those four steps carried out in full on a language small enough to fit on four slides.

The language, as data

The first step is a deep embedding: programs are values of an inductive type, not Lean code . Two declarations do the whole job. An assertion is a predicate on states, and a statement is one of five shapes.

def Assertion : Type := State → Prop

inductive Stmt where
  | skip
  | assign  (x : String) (e : Expr)
  | seq     (s₁ s₂ : Stmt)
  | ite     (c : BExpr) (s₁ s₂ : Stmt)
  | whileDo (c : BExpr) (inv : Assertion) (body : Stmt)

State with its get and set interface, and the expression evaluator, are carried over unchanged from the earlier programming lecture; BExpr adds boolean tests, and only Stmt is new. One field deserves attention immediately. The whileDo constructor carries an inv field of type Assertion, which is an invariant annotation: input for the verifier, and something the semantics is going to ignore entirely. Building the annotation into the syntax rather than into a separate table is what later lets the verification condition generator be a total function on Stmt.

Writing programs as raw constructor applications would be unbearable, so the deck spends a slide on notation . Statements are not terms, so they get their own grammar through declare_syntax_cat impStmt, with impStmt* meaning a sequence of them, and a single bridge back into the term language.

declare_syntax_cat impStmt

syntax ident " := " term "; " : impStmt
syntax "while" " (" term ")" " invariant" " (" term ")" ppLine " {" impStmt* "}" : impStmt
syntax "[Imp|" impStmt* "]" : term

macro_rules
  | `([Imp| ]) => `(Stmt.skip)
  | `([Imp| while ($c) invariant ($I) { $bs* }]) => `(Stmt.whileDo [BExpr| $c] $I [Imp| $bs*])
  | `([Imp| $s $ss*]) => `(Stmt.seq [Imp| $s] [Imp| $ss*])

The payoff is that a program can be written the way a programmer writes one, and after elaboration the quotation is gone: factorial is a value of type Stmt built from seq, assign and whileDo like any other piece of data . The same machinery runs in reverse, so unexpanders print states and programs back in this syntax and proof goals stay readable while stepping.

def factorial : Stmt := [Imp|
  n := 10;
  r := 1;
  while (0 < n) {
    r := r * n;
    n := n - 1;
  }
]

The semantics, and an interpreter that agrees with it

Meaning is given by a big step relation with one constructor per rule . BigStep σ s σ' reads: executing s from state σ terminates in σ'. Because derivations are finite trees, the relation captures exactly the terminating runs, which is why the triple built on it will be a partial correctness judgment. Note that inv appears in the two while constructors as a bystander: it is threaded through and never inspected, so the annotation has no semantic content at all.

inductive BigStep : State → Stmt → State → Prop where
  | skip :
      BigStep σ .skip σ
  | assign :
      BigStep σ (.assign x e) (σ.set x (e.eval σ))
  | seq (h₁ : BigStep σ s₁ σ') (h₂ : BigStep σ' s₂ σ'') :
      BigStep σ (.seq s₁ s₂) σ''
  | ifTrue (hc : c.eval σ = true) (h : BigStep σ s₁ σ') :
      BigStep σ (.ite c s₁ s₂) σ'
  | ifFalse (hc : c.eval σ = false) (h : BigStep σ s₂ σ') :
      BigStep σ (.ite c s₁ s₂) σ'
  | whileTrue (hc : c.eval σ = true) (hbody : BigStep σ body σ')
      (hrest : BigStep σ' (.whileDo c inv body) σ'') :
      BigStep σ (.whileDo c inv body) σ''
  | whileFalse (hc : c.eval σ = false) :
      BigStep σ (.whileDo c inv body) σ

A relation cannot be run, so the deck adds a fuel bounded interpreter, Stmt.run, and with it #eval factorial.runGet "r" answers some 3628800 and two #guard lines pin that down as a test . The interesting part is the next slide, which makes the tests more than tests . Four results are stated: Stmt.run_mono, that more fuel never changes an answer; Stmt.run_sound, that whatever the interpreter computes the semantics derives; Stmt.run_complete, that whatever the semantics derives some amount of fuel computes; and BigStep.deterministic. Together run and BigStep describe the same language, so every #guard on the previous slide is a theorem about the semantics rather than a spot check of an unrelated evaluator. Fuel monotonicity is the workhorse lemma.

The triple is a definition, not a logic

With a semantics in hand the specification language is one line .

def Triple (P : Assertion) (s : Stmt) (Q : Assertion) : Prop :=
  ∀ σ σ', P σ → BigStep σ s σ' → Q σ'

def Stmt.wlp (s : Stmt) (Q : Assertion) : Assertion :=
  fun σ => Triple (· = σ) s Q

theorem wlp_iff (s : Stmt) (Q : Assertion) (σ : State)
    : s.wlp Q σ ↔ ∀ σ', BigStep σ s σ' → Q σ' := by
  unfold Stmt.wlp Triple; simp; constructor
  · intro h σ'; exact h σ σ' rfl
  · intro h σ' σ'' he hb; subst σ'; apply h σ'' hb

Definition Triple P s Q is partial correctness spelled out: if P holds initially and s terminates, then Q holds finally. Divergence is invisible to it because a diverging run has no σ' and therefore no BigStep derivation to quantify over. s.wlp Q is the safe region of s, the set of states from which every terminating run establishes Q, which is Dijkstra's weakest liberal precondition.

This is the same judgment section 2 introduced as {P} e {Q}, defined there in prose and taken as a primitive of the tool. Here it is a Lean definition sitting on top of BigStep, which changes what the rules of Hoare logic are. The deck states the consequence flatly: this is not a new logic, Triple is a definition, and the rules of Hoare logic will be ordinary theorems about it.

The rules are theorems

Three rules come first, and their proofs are four lines each . The method is always the same: unfold Triple, then invert the derivation with cases. Because the statement in the goal has a fixed shape, only the matching BigStep constructors can apply, and the case analysis collapses to one or two branches.

theorem Triple.skip (Q : Assertion) : Triple Q .skip Q := by
  intro σ σ' h hstep
  cases hstep
  exact h

theorem Triple.assign (Q : Assertion) (x : String) (e : Expr) :
    Triple (fun σ => Q (σ.set x (e.eval σ))) (.assign x e) Q := by
  intro σ σ' h hstep
  cases hstep
  exact h

theorem Triple.consequence (h : Triple P s Q)
    (hpre : ∀ σ, P' σ → P σ) (hpost : ∀ σ, Q σ → Q' σ) :
    Triple P' s Q' := by
  intro σ σ' hP' hstep
  exact hpost _ (h _ _ (hpre _ hP') hstep)

Triple (fun σ => Q (σ.set x (e.eval σ))) (.assign x e) Q. Read it aloud: to have Q afterwards, require Q of the state already updated. It is Hoare's assignment axiom, with substitution into the assertion replaced by an update of the state, because assertions here are functions on states rather than syntax.

Triple is a definition, so the goal is literally ∀ σ σ', Q (σ.set x (e.eval σ)) → BigStep σ (.assign x e) σ' → Q σ'. There is no proof system to appeal to; there is a universally quantified statement to prove.

Now h : Q (σ.set x (e.eval σ)) and hstep : BigStep σ (.assign x e) σ' are hypotheses, and the goal is Q σ'. Nothing yet connects σ' to σ.

This is the step that does the work. The statement is fixed to .assign x e, so of the eight constructors of BigStep only assign can have produced this derivation, and its conclusion is BigStep σ (.assign x e) (σ.set x (e.eval σ)). Matching forces σ' to be σ.set x (e.eval σ), and the goal becomes Q (σ.set x (e.eval σ)).

Goal and hypothesis are now the same term. Four tactic lines, and the assignment axiom is proved.

The rule was not postulated and it is not built into anything. It is a consequence of exactly one constructor of the semantics. Change how assign evaluates, say by making it read the old value of x somewhere, and this proof stops working at the cases step, immediately and loudly. That link between the rule and the meaning of the language is what a verifier with a built-in weakest precondition calculus cannot offer from inside itself.

The next slide raises a point about tactics that shapes the whole design . Triple.assign's precondition has a fixed shape, the postcondition pushed through the update, so an arbitrary precondition written by a user does not unify with it and apply Triple.assign simply fails. The fix is a primed variant that fuses the rule with consequence, so that its proof term is the combination and its statement applies to any pre and postcondition, leaving an ordinary implication as the remaining goal. The deck turns this into a design rule: theorems meant for apply must be stated for arbitrary goals.

theorem Triple.assign' (P Q : Assertion) (x : String) (e : Expr) :
    (∀ σ, P σ → Q (σ.set x (e.eval σ))) →
    Triple P (.assign x e) Q :=
  fun h => Triple.consequence (Triple.assign Q x e) h (fun _ h => h)

Sequencing has a problem of its own . The textbook rule needs an intermediate assertion R shared by two premises, and applying it invents a metavariable for R whose filling is left to unification and elaboration order. Section 2 met the same difficulty from the other side and called it the reason weakest preconditions exist at all: the sequence rule needs a formula describing the state in the middle, and it has to come from somewhere. The deck's answer is Triple.seq', whose postcondition for the first statement is definitionally s₂.wlp Q, so it produces one goal and no metavariables, and intermediate states arrive later as intro bound variables rather than as holes.

theorem Triple.seq (h₁ : Triple P s₁ R) (h₂ : Triple R s₂ Q) :
    Triple P (.seq s₁ s₂) Q := by
  intro σ σ' hP hstep
  cases hstep with
  | seq hs₁ hs₂ => exact h₂ _ _ (h₁ _ _ hP hs₁) hs₂

theorem Triple.seq' :
    Triple P s₁ (fun σ => Triple (· = σ) s₂ Q) →
    Triple P (.seq s₁ s₂) Q := by
  intro h₁ σ₁ σ₃ hp hb
  cases hb
  next σ₂ h₂ h₃ => exact h₁ σ₁ σ₂ hp h₂ σ₂ σ₃ rfl h₃

The while rule is the only one whose proof needs a real idea : the statement has to be generalized before inducting on the derivation, which is why the code delegates to an auxiliary lemma. Its primed form is the important one, because it takes the invariant from the annotation stored in the syntax instead of from a metavariable, and its three premises are entry, preservation and exit. Those three are the loop's verification conditions, arrived at before the deck has defined vc at all.

theorem Triple.whileDo {inv : Assertion}
    (h : Triple (fun σ => I σ ∧ c.eval σ = true) body I) :
    Triple I (.whileDo c inv body) (fun σ => I σ ∧ c.eval σ = false) := by
  intro σ σ' hI hstep
  exact Triple.whileDo_aux h hstep rfl hI

theorem Triple.whileDo' {inv : Assertion}
    (hpre : ∀ σ, P σ → inv σ)
    (hbody : Triple (fun σ => inv σ ∧ c.eval σ = true) body inv)
    (hpost : ∀ σ, inv σ → c.eval σ = false → Q σ) :
    Triple P (.whileDo c inv body) Q :=
  Triple.consequence (Triple.whileDo hbody) hpre (fun σ h => hpost σ h.1 h.2)

A first verified program, twice

The rules are now enough to verify something. swapProg exchanges x and y through a temporary, and the first proof composes the rules backwards from the postcondition by hand, closes the gap to the specification with consequence, and lets grind do the state bookkeeping using the two [grind =] lemmas about get and set from the automation lecture . It is correct but manual: one rule application per statement, written out.

The second proof is the one that matters, because it is a shape rather than an ad hoc term . Only the apply friendly rules appear, seq' and assign', and the proof follows the structure of the program, one rule per statement, receiving each intermediate state with intro. That is symbolic execution, carried out in the deep embedding by the tactic framework.

def swapProg := [Imp|
  t := x;
  x := y;
  y := t;
]

theorem swap_correct' (a b : Int) :
    Triple (fun σ => σ⟦x⟧ = a ∧ σ⟦y⟧ = b)
      swapProg
      (fun σ => σ⟦x⟧ = b ∧ σ⟦y⟧ = a) := by
  unfold swapProg
  apply Triple.seq'
  apply Triple.assign'
  intro σ₁ h₁
  apply Triple.seq'
  apply Triple.assign'
  intro σ₂ h₂
  apply Triple.assign'
  intro σ₃ h₃
  simp [Expr.eval] at *
  grind

The generator, and its soundness theorem

Doing that by hand for every program is not a verifier. The deck's next move is to take the backwards composition and write it down as a function . Stmt.pre maps a statement and a postcondition to a precondition, structurally, and on a loop it simply returns the annotation. The invariant field that the semantics ignored finally earns its place in the syntax.

def Stmt.pre : Stmt → Assertion → Assertion
  | .skip, Q => Q
  | .assign x e, Q => fun σ => Q (σ.set x (e.eval σ))
  | .seq s₁ s₂, Q => s₁.pre (s₂.pre Q)
  | .ite c s₁ s₂, Q => fun σ => if c.eval σ then s₁.pre Q σ else s₂.pre Q σ
  | .whileDo _ inv _, _ => inv

def Stmt.vc : Stmt → Assertion → Prop
  | .skip, _ => True
  | .assign _ _, _ => True
  | .seq s₁ s₂, Q => s₁.vc (s₂.pre Q) ∧ s₂.vc Q
  | .ite _ s₁ s₂, Q => s₁.vc Q ∧ s₂.vc Q
  | .whileDo c inv body, Q =>
    (∀ σ, inv σ → c.eval σ = true → body.pre inv σ) ∧
    (∀ σ, inv σ → c.eval σ = false → Q σ) ∧
    body.vc inv

Anyone who followed section 2 will recognise the first function immediately: the seq clause is WP(e₁ ; e₂, Q) = WP(e₁, WP(e₂, Q)), the assign clause is substitution done semantically, and the conditional clause is the same case split. The deck is explicit that this is the textbook construction, naming Nipkow and Klein's Concrete Semantics section 12.2.2, which defines pre and vc under those very names over annotated commands, alongside Gordon's Hoare logic notes and the Hoare2 chapter of Software Foundations .

Stmt.vc collects what remains to be proved . Assignment and skip contribute nothing, since pre already handles them exactly; loops contribute preservation of the invariant and the exit implication. So on a loop free program vc is a conjunction of Trues and there are no proof obligations at all, with pre alone carrying the meaning.

Then comes the slide the whole lecture is arranged around .

vcgen_sound (s : Stmt) (Q : Assertion) (h : s.vc Q) : Triple (s.pre Q) s Q

theorem Stmt.verify (s : Stmt) (P Q : Assertion)
    (hvc : s.vc Q) (hpre : ∀ σ, P σ → s.pre Q σ) : Triple P s Q :=
  Triple.consequence (vcgen_sound s Q hvc) hpre (fun _ h => h)

Discharge the verification conditions and the triple holds. The proof is by induction on the statement, and the loop case is Triple.whileDo' applied to the induction hypothesis, which is why the three premises of that rule were arranged to match the three conjuncts of vc on a whileDo. A two line tactic macro then packages the whole thing for users: vcg applies Stmt.verify and unfolds the computed vc and pre .

macro "vcg" : tactic => `(tactic|
  apply Stmt.verify <;>
    try simp [Stmt.vc, Stmt.pre, Expr.eval, BExpr.eval])

def copyProg (a : Int) := [Imp|
  y := 0;
  while (0 < x) invariant (fun σ => σ⟦x⟧ + σ⟦y⟧ = a ∧ 0 ≤ σ⟦x⟧) {
    x := x - 1;
    y := y + 1;
  }
]

theorem copy_correct (a : Int) :
    Triple (fun σ => σ⟦x⟧ = a ∧ 0 ≤ a)
      (copyProg a)
      (fun σ => σ⟦y⟧ = a) := by
  unfold copyProg
  vcg <;> grind

On swapProg, which is loop free, no verification conditions survive and the single remaining goal is the entailment between the written specification and the computed precondition, which grind closes . On copyProg the loop's obligations do survive, and the same vcg <;> grind discharges them, with state bookkeeping by E-matching and the arithmetic by cutsat . Two notes on the slides guard against overclaiming. On the loop free fragment pre genuinely computes the weakest liberal precondition, weakest provably and not merely by name, and liberal means partial correctness, where Dijkstra's wp would additionally demand termination. On loops pre returns the annotation, which is sound but only as strong as the invariant you wrote. Choosing the invariant remains the one creative step, exactly as it was in section 2.

Where this meets sections 1 to 5

Sections 1 to 4 wrote WhyML, and Why3's verification condition generator turned it into proof obligations that SMT solvers discharged. Section 5 wrote Viper, whose front ends encode Rust, Go or Python programs into an intermediate verification language, and whose obligations again go to an SMT solver. In both cases the program logic is a feature of the tool. You can read section 2's table of weakest precondition rules and believe it, because it is a correct presentation of a calculus whose soundness is a theorem in the literature, but nothing the tool produces is that theorem, and nothing the tool checks depends on it.

This lecture makes the same object out of parts you can open. Stmt.pre is section 2's table, written as a Lean function you can print. vcgen_sound is the soundness theorem for that table, stated about the semantics on page 16 and proved by induction. Triple.assign is the assignment rule with a derivation five lines long. When the user runs vcg <;> grind and Lean accepts it, what has been produced is a proof term for Triple P s Q, and unfolding that term reaches vcgen_sound, the Hoare rules, and finally the constructors of BigStep. The kernel checks the lot.

The practical difference is where the trust boundary sits. Section 5 stated Viper's honestly and threefold: you must trust the SMT solver, Viper itself, and the encoding performed by the front end. Here the corresponding list has two entries. You must trust that BigStep says what you meant by the language, which is an irreducible obligation that no amount of proof removes and which every one of the industrial systems on pages 5 to 10 also carries. And you must trust Lean's kernel, which is small, fixed, and shared with every other proof in the system. The verifier is not on the list, because it was proved. That is what the abstract meant by no external tools and no trusted code generators.

The same programs, shallowly embedded

The deck now removes the object language . Imp was a deep embedding, where programs are data and the semantics is a relation. The shallow alternative is to write programs as ordinary monadic Lean code in StateM, which is the style of mvcgen, Velvet and Aeneas .

def Triple (P : S → Prop) (k : StateM S α) (Q : α → S → Prop) : Prop :=
  ∀ s, P s → Q (k s).1 (k s).2

def double : StateM Nat Unit := do
  let s ← get
  set (s + s)

The judgment is the same Hoare triple; only the semantics changed. A StateM program is a function, so quantifying over every terminating run collapses to running it: what was BigStep σ s σ' becomes the pair (k s).1, the returned value, and (k s).2, the final state. No inductive semantics is needed, and partial and total correctness coincide, because these programs are total and deterministic. Everything else carries over verbatim : Triple.get has the shape of assign', Triple.bind is seq' with the result value passed to the continuation, and rules for pure, set, modify, ite and consequence complete the set. Proving a small program is again apply the rule for the head, intro the reached state, repeat .

That loop is mechanical, and mechanical is the cue for a metaprogram . A tactic in Lean is a Lean program, so sym_step reads the goal, checks it is a Triple, inspects the head of the program, and applies the matching rule. Twenty lines. The reason it dispatches on the head rather than trying rules blindly with apply is performance: unification would send the elaborator unfolding >>= and StateT looking for a match.

open Lean Elab Tactic in
elab "sym_step" : tactic => do
  let goal ← getMainGoal
  let tgt ← goal.withContext do instantiateMVars (← goal.getType)
  let_expr Triple _ _ _ k _ := tgt.headBeta
    | throwError "sym_step: not a `Triple` goal"
  let app (r : Name) : TacticM Unit := do
    evalTactic (← `(tactic| apply $(mkIdent r) <;> intro _ _))
  match k.getAppFn.constName? with
  | some ``Bind.bind => evalTactic (← `(tactic| apply Triple.bind))
  | some ``get       => app ``Triple.get
  | some ``set       => app ``Triple.set
  | some ``modify    => app ``Triple.modify
  | some ``pure      => app ``Triple.pure
  | some ``ite       => evalTactic (← `(tactic| apply Triple.ite <;> intro _ _))
  | _ => throwError "sym_step: no rule for{indentExpr k}"

macro "sym_run" : tactic => `(tactic| repeat' sym_step)

With sym_run the pattern extends to recursion, and the slide's title is the point: recursion becomes induction . Verifying addN is an induction on n, generalizing a because the recursive call starts from a different state, where sym_run executes symbolically up to the recursive call and the induction hypothesis plays the role the loop invariant played in part A. Triple.consequence bridges the hypothesis to the goal, the same role it had there.

What it costs to scale

The last part is engineering, and it starts by naming the idiom just built as an industrial one: Aeneas verifies Rust by translation to Lean, Velvet is a Dafny style verifier built in Lean, and mvcgen is Lean's own generator for monadic programs . The slide adds that verification condition generation inside proof assistants has historically not scaled, documented for Rocq by Chlipala's group, and that the same held in Lean. Two bottlenecks are marked on the diagram: the generator is superlinear, and the obligations share many hypotheses which a naive pipeline reprocesses for every obligation.

Andres Erbsen distilled that into a minimal benchmark at the Lean at Google hackathon: symbolically execute a generated n step program, which is exactly this lecture's apply and simp loop at size n . On Lean's general purpose tactic framework, MetaM, the curve is superlinear: 2073 ms at n = 100, and failure before n = 700. The diagnosis is a list of things the loop needs and a general framework does not provide : efficient apply without unification search, which is why sym_step dispatches on the head; efficient metavariable management; term sharing preserved by every operation, with no copied trees; simplifier results cached and reused across obligations and steps; and no repeated traversal of the same subterms.

The answer is SymM, a monadic framework for symbolic simulation and VC generation now in the Lean sources . Its key invariant is that the local context grows monotonically, with no reverts and no deletions, which makes pointer equality a valid cache key and lets automation state survive from one verification condition to the next. Around that sit precompiled backward rules matched mostly syntactically on the hot path, a new simplifier with pointer keyed caches on maximally shared terms, and grind state threaded through the loop so facts learned once are reused. On the same benchmark the result is 16 ms at n = 100 against 2073 ms, roughly a hundredfold, and linear out to n = 700 . Ported frameworks report the same shape : mvcgen linear to n = 1000; Velvet, previously about three times slower than Dafny, faster on 24 of 27 benchmarks after the port, with the difference in kind that Dafny trusts its VC generator and an SMT solver while Velvet's chain is checked by the kernel; and DyLean, on cryptographic protocols, a fiftyfold speedup in VC discharge.

The closing summary reads the four lectures back as one argument : dependent type theory with the kernel as the single arbiter; inductive types, type classes and macros, with lemmas designed so that proofs follow definitions; automation that is inspectable, extensible and kernel checked, with AI as a user of the same machinery; and verification as Hoare logic in the form of theorems, VC generation as a verified function, symbolic execution as a metaprogram, and the engineering that scales it, all inside Lean, where one kernel checks the programs, the specifications, the proofs and the verifier itself. The exercises are Lecture4.lean for the generator and Lecture4b.lean for the shallow embedding with sym_step, both with full solutions .
